# MoonBlokz Blockchain PRD — FR/NFR Navigation Index

> **Non-authoritative navigation aid.** The authoritative source for every requirement listed here is [`moonblokz-blockchain-prd.md`](./moonblokz-blockchain-prd.md); on any divergence the PRD wins. Each functional requirement has a short subject label and a **digest** — one to three sentences stating its normative core (what the module shall do, when, with which key outcomes and exceptions). A digest is a compressed reading aid, not requirement text: it omits detail, rationale, and sub-cases. Use it to understand a requirement's role and to decide which FRs to open; before relying on a detail, read the requirement itself in the PRD.

## How to read a single requirement without loading the whole PRD

The PRD is large and most functional requirements are a single very long line, so reading the file in full is costly. To read just one:

1. Search the PRD for the requirement's anchor — functional requirements begin a line with `- FR<n>:` and non-functional requirements with `- NFR<n>:`. For FR52 the anchor pattern is `^- FR52:`; for NFR12 it is `^- NFR12:` (the trailing colon keeps `FR5`/`FR52` and `NFR1`/`NFR12` distinct).
2. Read from that line up to the next line starting with `- FR`, `- NFR`, or `#`. Most requirements are one line, but FR10, FR21, FR22, FR23, FR27, FR43 and FR64 continue in further paragraphs (annotations, lists, or continuation text) that a single-line read misses.

Search by anchor rather than citing a line: anchors are stable across edits, line numbers are not.

## Functional Requirements (FR1–FR72)

### Chain Lifecycle & State Progression
| FR | Subject | Digest |
|----|---------|--------|
| FR1 | Collecting-state initialization with not-ready gating for dependent behaviors | Starts with an empty chain in collecting state. It stays there until an FR2 stopping condition holds, and only that condition triggers processing (FR3). While collecting, these return a not-ready indication to every caller, including peers' requests forwarded by the radio: FR40, FR41, FR42, FR43, FR44, transaction intake (FR14/FR10), FR55 local transaction creation and FR46 replenishment. Block intake and staged validation (FR9, FR10, FR16) and outbound FR19 parent recovery stay active. |
| FR2 | Dominant-chain acquisition stopping conditions and deterministic tip selection | While collecting, keeps checking the block-tree and leaves collecting as soon as a continuous segment of connected, parseable blocks qualifies. It qualifies if it is genesis-anchored (from #0, any length) or at least W long, and it must contain a chain-config block in scope. "Continuous" means every block except the earliest has its `previous_hash` resolved locally. The highest tip sequence wins; ties go to the lowest tip hash (big-endian). This pick is bootstrap-only: branch value (FR21) is not used while collecting. |
| FR3 | Processing-state transition executing full-chain reconstruction forward pass | Moves to processing and runs a non-resumable reconstruction pass (Algorithm 2B). (1) Backward-mark the candidate. (2) Preload its chain-config, which must be byte-identical across the candidate, else FR5; this config is used instead of FR8's tentative one for chain-config-derived checks. (3) Forward-rebuild roster/keys, balances, votes (FR37), creator order (FR38), available-UTXO bits (set on deriving a block, cleared on spend) and `snake_chain` state. Uses per-node seeding with pre-seed auto-accept. A window-anchored candidate trusts a UTXO input referencing a block below its anchor, declared amount included, if it is at most `W` back; more than `W` back is invalid everywhere. The `max_known_node_id` watermark starts from the earliest balance block, or at 0 for genesis (FR54). Any failure → FR5; a restart → discard and re-collect (FR59). |
| FR4 | Ready-state entry conditioned on successful chain validation | Ready state only after chain validation succeeds. |
| FR5 | Atomic working-set rollback and durable-deletion recovery on validation failure | When FR6 fails in the FR3 pass, it recovers atomically: discards all derived working state and deletes the earliest offending block (or, if that cannot be identified, the candidate head). All transitive descendants go too; sibling subtrees stay. It then returns to collecting and re-runs FR2. A local failure (storage read error, missing vote parameter, or an inconsistency of its own block-tree index) deletes nothing and is retried later; a parent reference to a freed slot is unlinked. Ready-state Tier 2/3 failures delete the block and its descendants without rollback or reversion. Deletion is limited to the listed paths, followed by FR19 `chain_heads` updates. |
| FR6 | Full candidate-chain block and transaction invariant verification before ready | Before ready, replays the candidate forward and checks the state-dependent invariants: `previous_hash` links, creator signature, vote fields, `block_size_limit`, the held configuration's `max_block_UTXO_output` (also before the lock, DEC-133), payload structure, `mined_amount` = `mining_reward`, and creator credit (FR36). Transaction checks (Algorithm 13) cover balances, signatures, no duplicates, stride-1 `new_node_id` and absorbed `registration_price`. They also cover UTXO/inputs, approval evidence, twin evidence (FR71) with its FR72 effects, node existence ≤ `max_known_node_id`, no self-vote (node #0 exempt), creator selection and byte-identical chain-config. Structural invariants are left to Tier 1. Older `snake_chain` obligations are trusted. Any failure → FR5. |
| FR7 | Chain-config content-signature validation against node-zero trust anchor | Every chain-config block must carry node #0's signature over the canonical config bytes. This signature never changes and is copied byte-identically into FR49 replays. It is checked at intake (Tier 1) against `node_zero_public_key` (FR69), whatever the block's connection, FR50 coverage or FR8 lock state. A failure is exact evidence, so the block is not stored. The FR6 creator-signature check applies separately. |
| FR8 | Chain-config tentative-load and durable-lock commitment phases | Tentative phase (collecting): the first chain-config block with a valid FR7 signature that `configuration_module` accepts is tentatively loaded. Later ones are stored but do not override it, and a rejection is exact evidence (FR16). Acceptance requires `max_block_UTXO_output` ≤ `UTXO_UNSPENT_BITS`, `W` ≤ `SNAKE_CHAIN_LENGTH_MAX`, `1 ≤ H ≤ W`, `W + 2·H` ≤ block-storage capacity, and `required_support` ≥ 1. Before FR4, the candidate's chain-config must byte-match the tentative one. On a match: one set-once durable commit, and mismatching chain-config blocks are deleted with their descendants. On a mismatch: clear, adopt the candidate's config, then restart processing or return to collecting (FR3/FR5). |
| FR9 | Three-status block lifecycle and three-tier validation check system | Block statuses Stored/Connected/Active, governed by Tier 1/2/3 checks. Collecting: everything Stored. Processing: FR3 runs all tiers and makes the candidate Active in one step. Tier 1 (intake) is the exhaustive list of intake-time exact evidence. Tier 2 does ancestry and FR34 lookups, including the structural `snake_chain` checks: FR58's switch bound keeps their reference blocks retained. A UTXO reference below `S_tail` within `W` is trusted; registration-key uniqueness is Tier 3. A ready-state block whose parent is Connected or Active (not the head) is judged at Tier 2 before storing. Tier 3 replays derived state via FR3, FR23, or for head extensions and stored head children. Pacing soft-fail → Deferred, block kept, no FR5. Tier 1 also caps a block's UTXO outputs (bitfield width before the lock) and checks the header vote form. In ready state a bad creator signature is exact evidence at Tier 1 for a direct head extension, and for any block whose creator's key is branch-independent (node #0, or seeded at or below `S_tail`). A verified signature is marked on the block and not re-verified. Tier 3 checks the FR37 vote snapshots. Chain-config-derived failures count only after the durable lock, except the FR3 `W` bound and FR6 UTXO-output cap (DEC-129, DEC-133). Invalid deletes the block at once with its descendants, and only through the listed paths. |
### Block & Transaction Intake
| FR | Subject | Digest |
|----|---------|--------|
| FR10 | Block-intake deterministic five-outcome classification | Every submitted block gets exactly one deterministic, origin-independent outcome. Accepted-new means stored. Already-known. Invalid-evidence (including a bad creator signature in an FR9 Tier 1 exact-evidence case) and Out-of-Snake-Chain-Window mean not stored; the forward out-of-window case logs per FR60. Deferred means stored and carries `remaining_wait_time`. Accepted-new may add at most one optional component per call (FR12 support, FR13 transaction or FR45 block); any others come through `NextCall`. Transactions get one FR14 outcome with no payload, and not-ready in collecting/processing. Annotation: enum mapping; a valid block storage can't persist is reported Already-known; causes go only to the FR64 log. |
| FR11 | Already-known duplicate detection via in-memory block-tree index | The in-memory retained block-tree is the only duplicate-detection index. Checking means one lookup by `(sequence, block_hash)`, without consulting durable storage, because the tree is rebuilt at startup (FR59) and kept consistent. A match returns Already-known, with no re-store and no further intake processing. |
| FR12 | Deviating-block endorsement support-message eligibility and generation | Applies when a deviating block is accepted (its creator is not top of the creator-order) and is parseable, connected and signature-verified. The module emits a signed support message (over proposer, sequence and block hash) only if all of these hold: the creator is inside the Algorithm 5 grace window; the local node is in A (FR72-excluded nodes are not) and among the m = min(2·`required_support`−1, \|A\|) smallest `node_value`; it has issued no conflicting support; and no tail replay (FR49/50/51) is pending. Otherwise nothing is sent and no reason is given. It also defines `supporter_vote_sum`. |
| FR13 | Under-disseminated mempool transaction re-dissemination on block intake | Applies to an externally delivered block accepted into the active chain that holds at least one ordinary transaction. The module looks for mempool transactions with a higher fee-per-byte than the block's lowest ordinary transaction that would also have fit within `block_size_limit`. If any exist, it picks one at random (own transactions first, per FR45) and returns it as an addendum. Replay-only blocks and locally created (FR45) blocks never trigger this. FR63 determinism does not apply, and callers that don't relay just discard the addendum. |
| FR14 | Transaction-intake five-outcome classification in ready state | Ready state only; in collecting/processing the answer is not-ready, with no classification or admission. Outcomes, deterministic and origin-independent: Accepted-to-mempool (competing spends allowed), Already-confirmed, Duplicate-in-mempool, Deferred (held with a marker) and Rejected (can never become valid). Window: transfer/balance-input `anchor_sequence` ≥ `S_tail` with no upper bound, and UTXO `block_sequence` ≥ `S_tail`; registrations are exempt. Uniqueness keys are defined per type. An unknown vote target is always Deferred. |
| FR15 | Deferred mempool transaction re-evaluation on active-chain changes | After every new active-chain block or chain switch, every Deferred transaction is re-checked. It is Promoted only if it now meets the FR14 Accepted-to-mempool conditions; otherwise it remains Deferred, including when it is Already-confirmed or out of window. FR15 never rejects or removes a transaction. Only Promoted entries are visible to FR45, FR46 and FR13. FR31/FR33 eviction and FR14 intake-time window expiry are separate paths that can still remove Deferred entries. |
| FR16 | Block stored unless Tier 1 exact invalidity evidence exists | Every incoming block is stored unless there is exact evidence against it. The FR9 Tier 1 failures (minus the opportunistic signature side effects) are the complete list of such evidence; the examples given are illustrative only. For a ready-state direct extension of the active head, any Tier 2 or Tier 3 failure at intake is also exact evidence, so the block is not stored; the same holds for the Tier 2 failure of a block whose parent is Connected or Active but not the head. Other signature-invalidity decisions (outside the FR9 Tier 1 signature cases) wait for Tier 3 or FR3. Out-of-window blocks (FR60) are silently discarded. |
| FR17 | Chain-config content-mismatch blocks silently discarded post-durable-lock | Once the config is durably locked (FR8 or FR54), any chain-config block whose content differs byte-wise is silently discarded at intake. It is not stored, not added to the tree and gets no FR9 processing. This is FR16 exact evidence and applies to original and replay blocks alike. An FR64 `chain-config-mismatch-discarded` log record is emitted with the block's hash, sequence and creator. Reconciling across a config boundary is out of scope, as with the FR60 long disconnect. |
### Chain Knowledge, Branching & Reconciliation
| FR | Subject | Digest |
|----|---------|--------|
| FR18 | Per-block block-tree metadata retention requirements | Keeps a bounded block-tree that holds enough to rebuild ancestry. Each block's metadata: sequence; mandatory block hash (its identity, the FR11 index key and the parent-ref target); a parent reference (wire `previous_hash` or an internal pointer, either way deterministic and bounded); creator id; payload type; FR9 status (Stored/Connected/Active); `is_on_active_chain` bit; `head_ref_count` (FR19). Local arrival timestamp kept at least for every chain-head block (FR9 Tier 3 pacing, FR46, FR10). Invalid is not stored: the block is removed atomically. Block storage follows FR16. |
| FR19 | Missing-parent recovery scheduling via bounded chain_heads table | A `chain_heads` table indexes every tip, whatever its status, capped by `chain_heads_max_capacity`, a per-node build-time capacity (`MAX_BRANCH_COUNT`), not chain-config. Fields (a)–(g) include tail-point and `last_request_timestamp` (Stored heads only) and `branch_value` (Connected heads; the active branch's value is held once beside `active_chain_head_id`). Each tick, the eligible Stored head with the oldest `last_request_timestamp` sends one parent request (ties: `head_sequence`, then `head_block_id`). Defines mutation events (i)–(v). Eviction removes the lowest-`head_sequence` non-active head: walk back, decrement `head_ref_count`, delete at 0, stop at >0. Closed deletion list: this eviction, FR5, FR16, FR17, FR57, FR48 tail-drop, FR58. |
| FR20 | Multiple candidate branches simultaneously retained in block-tree | Keeps several candidate branches at once, each tracked through FR19 `chain_heads`. Retention is bounded by the `snake_chain` window (FR48) and the verification horizon (FR58); blocks below the horizon need not be kept. A branch need not reach genesis; its tail-point only has to be in the retained tree. Normal intake never prefers or collapses side branches. The only intake refusals are FR16 exact evidence, FR17 and FR59 silent discards. Silent branch removal only via FR19 eviction, FR5, FR8 lock-mismatch cleanup, FR57, the FR48 tail-drop release and FR58 reclamation. Branch selection belongs to FR21/FR23. |
| FR21 | Branch-value computation and highest-value active-branch selection | Active branch = the admissible Connected/Active head with the highest `branch_value`. Value = sum of per-block values above `S_tail` (normal block: `consumed_votes`; evidence block: FR12 `supporter_vote_sum`; replay blocks between deviation and evidence: 0). Updated incrementally on (i)–(v): a tail advance subtracts the new `S_tail` block's value; FR5 precedes all values, so (v) is a ready-state Tier 2 deletion's retargeted entry. FR23 switches leave it unchanged. Admissible: tip-ending segment of ≥`W` blocks, or before maturity the whole genesis-anchored chain. Maturity and admissibility derive from the window, so no flag is kept: `tip.sequence ≥ S_tail + W − 1` once mature. Ties: larger tip size, then lowest tip hash (no creator criterion). A deviation block is never worth more than the normal block it replaces (FR37 pre-credit snapshots). Approval-less deviation branches cannot overtake; equal votes tie. |
| FR22 | Active-branch re-evaluation on non-active head value increase | Re-evaluation is local and runs on exactly two triggers: a non-active Connected/Active head is extended (including a new fork), or a head goes Stored→Connected. Only the affected head is compared with the active head (`branch_value`, then FR21 tie-break), once per admission. When several heads change, the highest-ranked admissible one is compared. Only if it is admissible and wins does FR23 run. Before Story 6.3 a win is reconsidered at that head's next trigger or a restart. Listed non-triggers: active-head extension, replay blocks, `S_tail` slide, FR23 itself, other FR19 mutations, and approval-less deviation blocks. FR5 deletions follow FR5. |
| FR23 | Chain-switch reconciliation as atomic step-wise backward/forward walk | Every derived projection, mempool included, is per-block reversible. An active-branch change runs atomically: find the common ancestor, undo blocks walking back (their transactions return to the mempool), then apply blocks walking forward (their transactions leave it). It flips `is_on_active_chain`, demotes abandoned blocks without deleting them, and updates `chain_heads` (no head loses its connection; `head_ref_count` and `branch_value` unchanged). In-place, with `W` retained blocks back from the ancestor; FR58 admits only switches that have them, so ready state has no full-reconstruction path. |
| FR24 | Consistent single-branch derived state visible to all callers | Derived state must always match exactly one selected active branch. No caller may see a mix of pre-switch and post-switch balance, UTXO, vote or mempool values: only the full before state or the full after state. |
| FR25 | Chain-switch and approval-evidence paths treated as first-class behaviors | Chain-switch reconciliation, deferred signature validation once creator keys become known, legitimacy changes from approval evidence, and putting stale-looking transactions back into the mempool are ordinary first-class paths, not exception or error flows. They are observable through the same event and state surfaces as normal block intake. |
| FR26 | Support-message intake, validation rules, and relay classification | Takes support messages in collecting, processing and ready (FR1 gating unchanged). Returns only Accepted (relay) or Rejected (drop, no relay), deterministically and regardless of transport origin. Checks: (i) format, always; (ii) supporter signature, only if the key is derivable; (iii) tuple coherence, only if an active chain exists; (iv) if the deviation is on the active chain, supporter is in the ADR-015 subgroup and no evidence exists yet; (v) LRU dedupe. If the deviation is not on the active chain, (i)+(v) suffice. A proposer also accumulates per FR27. |
| FR27 | Approval-evidence block construction and accumulation by deviation proposer | Only the proposer, from deviation creation (FR45), collects Accepted subgroup supports; at `required_support` it builds the evidence block (`payload_type=4`: FR12 `supporter_vote_sum`, aggregated signature, supporter ids). The accumulator is not durable, is bounded by `MAX_BLOCK_SIZE`, and is dropped on restart or when FR23 demotes the deviation branch. Only the deviation creator may extend that branch; any other creator is FR16 exact evidence. It emits due replay blocks first, in tail-fallout order. Header overrides: `consumed_votes=0`, `first_voted_node`=self. No FR44 or FR45 gating. |
| FR28 | Deviation-block immediate acceptance and two-stage branch scoring | A deviating block accepted as an active-chain extension is authoritative immediately. It updates balance, vote, mempool and tail-advance state through FR35/FR36/FR45 like any ordinary extension. Its branch is never higher in value than the matching normal branch under FR21/FR22 until the FR27–FR29 evidence block arrives; equal votes tie, and the FR21 tie-break decides. Most of the FR is rationale for this two-stage scoring. |
| FR29 | Snake_chain replay precedence preserved during deviation-approval workflow | Essential replay blocks (FR49/FR50/FR51) may come before an evidence block, and the approval workflow must stay correct. On the deviation branch, the proposer waits a chain-config insertion delay (from `configuration_module`, FR56) after the deviation block before the first replay block, and between replay blocks. No delay applies before the evidence block. Pacing never affects block validity. |
### Mempool, Balances & Vote State
| FR | Subject | Digest |
|----|---------|--------|
| FR30 | Mempool as separate module with compacted bounded storage | The mempool is a separate `mempool_module`. The blockchain module changes it only through that module's typed surface (add, remove, evict, reconcile per FR23/FR32, reads for FR45/FR43/FR40). Every change is driven by chain state, and by the FR63 seeded PRNG for FR33 eviction (replayable per node; correctness does not depend on eviction outcomes). Not persisted: empty on restart (FR59). Storage: one contiguous byte buffer plus a fixed index (`start`, `length`, `hash_crc32`, `transaction_fee`, `expiry_sequence`, `is_deferred`, `is_own`). Capacity is compile-time and enforced via FR33. |
| FR31 | Mempool add invoked only on Accepted-to-mempool outcome | Calls add if and only if FR14 classifies the transaction Accepted-to-mempool or Deferred (Deferred keeps its not-yet-evaluable marker). The add updates the buffer and index atomically and stores the fee resolved during validation. On overflow, FR33 eviction frees as much space as the transaction needs (one draw for non-own, repeated draws for own) and the transaction is admitted. If eviction cannot make room (for example, the new transaction is drawn), the add is rejected and reported as Rejected. |
| FR32 | Mempool reconciliation on forward extension and chain-switch events | Reconciles the mempool whenever the authoritative chain changes. Forward extension: steps 2–3. Chain switch: steps 1–2 for each block on the walk, step 3 at the end. (1) Transactions of blocks leaving the chain are re-added via FR31, subject to FR33. (2) Transactions of blocks joining the chain are removed. (3) Transactions whose `anchor_sequence` is outside the acceptance window of the new head are removed. Step 3 replaces time-based aging, so no periodic aging timer exists. |
| FR33 | Randomized mempool eviction with own-transaction priority preservation | Picks eviction targets uniformly at random; the method depends on whether the incoming transaction is own. Own: node-transfer or registration initializer = local id; complex transaction with ≥1 input and a local balance-input initializer or balance-output receiver. Non-own incoming: evict one random non-own transaction; if none exist, draw from own + incoming, and drawing the incoming means Rejected. Own incoming: evict random non-own, then random own (never the incoming), until it fits; never rejected. The FR63 seeded PRNG makes a node's evictions replayable from its own seed; no correctness depends on outcomes, which differ across nodes by design. |
| FR34 | Six derived operational-state projections maintained from active chain | Maintain six derived projections of the active chain: per-node balance (including the FR36 creator credit), accumulated vote (FR37, including anti-capture interest), `node_id`→`public_key` map, max-node-id watermark, per-node `seed_source_sequence` (FR50), and a block-navigation-and-UTXO cache. The cache is compile-time sized at one slot per storage slot, is not durable, and is rebuilt on restart. Each slot holds sequence, hash, parent slot and an available-UTXO bitfield (1 = the output exists and is unspent; DEC-132), so spent or missing inputs and the FR51 obligation are decided without a block read. A block's UTXO outputs above `max_block_UTXO_output` are rejected (FR9). No separate live UTXO set is kept. All six must be recomputable from the active chain plus replay blocks, and must never be exposed inconsistently across FR24. |
| FR35 | Derived projections incrementally updated on two trigger event types | Update the FR34 projections only on (1) forward extension of the active chain and (2) a chain switch (FR22/FR23), handled as the FR23 step-wise walk: the inverse per-block update on rollback, the forward update on replay. The per-block set covers balances (FR36), votes (FR37), the key map and watermark for registrations, `seed_source_sequence` (restored on rollback by a bounded backward scan, FR50), and the cache slot plus available-UTXO bits (own outputs set, consumed inputs cleared). Diff-patching in place is forbidden. Other effects belong to FR32/FR15, FR37, FR51 and ADR-016. |
| FR36 | Block-creator mining reward, transaction fee, and replay-reward credit | On forward extension, credit the creator once with (a) `mined_amount` (= `mining_reward`, FR6), plus (b) fees: the explicit fee for type 1/2 (`registration_price` excluded and absorbed by the network), input−output for type 3, zero for FR51 carry-forward; plus (c) `replay_block_reward` (FR56) for each replay-bearing block (FR49/50/51), including the proposer's intervening replay blocks (FR27). Rolled back and re-applied on a switch (FR23). Breaking the FR6 balance invariant is exact evidence (FR5 in the pass; FR9 deletion in ready). Genesis #0/#1 are excluded. |
| FR37 | Accumulated-vote accumulation, anti-capture interest growth, and creator reset | A `vote` target missing from the active roster is Deferred at FR14 intake (FR15) and is exact evidence in FR6 candidate validation (FR5). `vote=0` is always valid. Per accepted block, in this order: (1) every node gets `min(floor(av×vote_interest/vote_scale), vote_scale)`; (2) +`vote_scale` per transaction vote, except FR51 carry-forward; (3) the creator resets to 0. `consumed_votes` is the creator's value after step 1 and before step 2, so a block's own credits never count; a deviation's `consumed_votes_from_first_voted_node` takes the same snapshot of the originally-top node. Checked `u32`: an overflow is invalid. The `first_voted_node` reset applies when the deviation block is accepted. A twin evidence block resets the equivocating creator (FR72). |
| FR38 | Creator-order projection derived and refreshed from vote state | Maintain the creator order as a derived projection of FR37: descending accumulated vote, ties broken by ascending node id. Zero-vote nodes are included as the tail, so node 0 heads the order in the all-zero bootstrap state. It is refreshed only under the two FR35 triggers. The grace-period penalty and replay blocks are not separate triggers. The top entry is the expected creator; later entries form the FR44 fallback progression. FR72-excluded nodes are left out. |
| FR39 | Rollback-sensitive derived-state correctness through FR23 reconciliation | On a branch change, available-UTXO bit updates, FR32 mempool reconciliation and the FR38 refresh are part of the FR23 walk itself, with no post-walk passes. The walk finishes before the new branch is exposed (FR24). Transactions confirmed only on the abandoned branch return to the mempool. UTXO references re-resolve during forward replay; one below `S_tail` within `W` is trusted pre-window history (DEC-129). Available-UTXO bits are never re-derived from zero in ready state; only the collecting → ready FR3 pass derives them from scratch. No residue of the abandoned branch may remain. This is a first-class path, not an error handler. |
### Queries & Retrieval
| FR | Subject | Digest |
|----|---------|--------|
| FR40 | Transaction-state query returning Unknown, In-mempool, or Confirmed | A query by canonical transaction hash returns exactly one of: Unknown; In-mempool (deferred, not-yet-evaluable transactions included, no sub-state exposed); or Confirmed with depth `(head − confirming) mod 2^32` (FR53), bounded by `W`. It resolves only against the active chain and the mempool, never side branches. Confirmed is deterministic across nodes. In-mempool vs Unknown is best-effort only, because FR33 eviction makes mempools diverge. Confirmed carries a disputed flag while an unresolved FR70 twin lies at or below the confirming block. |
| FR41 | Node-balance and address-UTXO unspent-output query surfaces | Two queries, both against the active chain only. Node-balance returns balance and accumulated vote, plus an optional depth of the last affecting block (`mod 2^32`, FR53), which callers may omit. Address-UTXO returns the unspent `(block_sequence, output_index, amount)` entries for a public key from the FR34 available-UTXO bits (ADR-016), with amounts after custodian-fee reduction. References are valid only against the current active chain and must be re-resolved after chain-switch or carry-forward events (FR64). There is no side-branch leakage. |
| FR42 | Active-chain block retrieval by sequence or hash, ready-state only | Block retrieval is served only in ready state; collecting (FR1) and processing return not-ready. Lookup by sequence or by hash, active chain only. A side-branch, absent or out-of-window block returns not-available. The response is the canonical `Block` struct (`moonblokz-chain-types`), exposing the exact serialized bytes and typed accessors. Any caller (local interface or radio layer) may use it. |
| FR43 | Top-mempool-items replenishment exchange read-only surface | Ready state only; collecting and processing get not-ready, with nothing returned. Exclude mempool transactions whose `hash_crc32` (FR30) appears in the requester's snapshot (collisions are accepted as over-exclusion). No size-fit check. Return at most one transaction, at random among those whose fee-per-byte (FR45) beats the lowest snapshot-matched entry, otherwise at random among all non-excluded. Deliberately non-deterministic, not the FR63 RNG. Annotation: sync read-only `query_top_mempool_items`, borrowed `TransactionView`, no `NextCall`. |
### Block Creation & Timeout Recovery
| FR | Subject | Digest |
|----|---------|--------|
| FR44 | Local creator determination and grace-period fallback set expansion | The local node is the current creator only if it is the FR38 top entry, in which case it starts FR45 assembly. Otherwise it waits for a grace-period expiry. Each expiry only widens the Algorithm 5 admitted prefix and re-checks local admission (which may lead to a deviation block). There is no vote reset and no order shift. The originally-top node stays top and may create at any time until its own block or an accepted deviation block (FR37 reset). There is no pre-computed fallback set. |
| FR45 | Block-creation triggers, content-assembly priority, and header construction | Ordinary creation starts when (a) the mempool reaches the fill-threshold % of `block_size_limit`, or (b) an FR46 timer fires after the configured interval and at least one transaction is includable. Pending FR49/50/51 replays come first, as soon as the node is FR44-eligible (or is the FR27 proposer). A replay mirrors the dropping block's payload type, at most one category, and always fits. Never mix type 2 and type 3. An FR71 twin evidence block comes after due replays and before ordinary content, and a creator never signs a second child of a parent (FR70). Order: fee-per-byte, own, `hash_crc32`, bytes. No empty blocks; stalling is not an error. Sets header fields, e.g. `mined_amount`=`mining_reward` and FR37 `consumed_votes` (post-interest, pre-credit). |
| FR46 | External time-driver next-wakeup query and tick callback contract | After every invocation, report the earliest deadline as a delay, or a no-wakeup sentinel. On a tick (driver-supplied monotonic time), fire all due behaviors and recompute. Tracked deadlines: block-creation interval (current creator, below threshold, an includable transaction); grace-period expiry (widens the prefix, no reset, FR47); missing-parent re-query (global cooldown, per-head retry window, most-overdue Stored head, at most one request per tick); mempool replenishment (ready only, below threshold, on any node, served via FR43). No other clock is used. |
| FR47 | Grace-period expiry advancing fallback cycle without accumulated-vote reset | When the grace-period deadline fires, advance the Algorithm 5 window by one creator and re-evaluate whether the local node may now create per FR45. No accumulated vote is changed; the originally-top node's reset belongs to FR37 at deviation-block acceptance. Fallback activation is a first-class, observable path (FR25), not an error. |
### Snake_chain & Tail Preservation
| FR | Subject | Digest |
|----|---------|--------|
| FR48 | Bounded active-chain length and pre-drop essential-state preservation check | Keep the active chain at most `W` long in steady state. During bootstrap growth (FR21) the tail does not advance. At head-extension time (before acceptance or creation), if the chain would exceed `W`, check the dropping tail for FR49/50/51 essential state. If none, extend and advance the tail. If at risk, the head must be or carry the preserving replay block, and a non-preserving inbound head is rejected. One dropping block is always replayable in one head. Below the tail the FR58 verification horizon is retained: outside the active chain, never evicted by FR57, holding the reference blocks FR23 switches need. |
| FR49 | Chain-config replay block emitted before dropping chain-config block | Before a chain-config block drops out of the window, schedule a chain-config block with identical content as the very next head block, the one whose acceptance would drop it. No lookahead, no early scheduling. This is permanent and unaffected by FR50 Trigger 2. It takes priority over ordinary mempool transactions and over FR27 evidence-block emission. |
| FR50 | Balance-block replay triggers and per-node seed-source coverage invariant | Emit a balance block on Trigger 1 (a node's `seed_source_sequence == S_tail`: one mandatory entry per such node). Otherwise, at lower precedence, on Trigger 2: chain length is `W`, no other replay is due, and blocks since the last balance block exceed `⌈W/⌈N_active/K_max⌉⌉` (empty mandatory set). Then bonus-pack entries in ascending `seed_source_sequence` then `node_id`, up to `block_size_limit`. NodeInfo carries the state at sequence−1. A non-canonical set, a NodeInfo mismatch, an entry owner above `max_node_id`, or a `max_node_id` mismatch (from the earliest balance block on wherever the projection is re-derived from block #0) is exact evidence (FR5 in the pass / FR9 in ready). |
| FR51 | UTXO carry-forward with custodian-fee reduction for unspent outputs | For a dropping transaction block with unspent UTXOs (available-UTXO bit 1, decided without a block read), create one zero-input carry-forward transaction whose outputs are exactly those UTXOs minus the custodian fee; outputs below the fee are discarded. On acceptance, verify (i)–(v): the tail advances by exactly one; the dropping block is `payload_type=1` with UTXOs; the multiset matches; below-fee outputs are omitted; there are no extra outputs. Any failure is exact evidence (FR9; FR5 in the pass). The block may add mempool transactions but no registrations. Carry-forward is vote-neutral (FR37). |
| FR52 | No UTXO-saturation detection, backpressure, or special-case handling | Defines no saturation mechanism at all: no detection, status reporting, log emission, mempool admission backpressure or replay deferral. When unspent UTXOs plus `snake_chain` replay obligations fill most of `block_size_limit`, block creation continues as usual per FR45, and FR51's custodian fee eventually restores capacity. There is no saturated/non-saturated distinction and nothing a caller can observe. FR14 admission is unchanged. Saturation is not long-disconnect (FR60) and does not change FR63, FR21/22/45/51/57. |
| FR53 | Sequence u32 ceiling with explicit u32::MAX block refusal | `sequence` (u32) starts at 0 at genesis and goes up by exactly 1 per forward extension. In MVP no block with `sequence == u32::MAX` may be created or accepted. FR45 never produces one, and head-advance stops at `u32::MAX − 1`. An inbound `u32::MAX` block is exact evidence (FR16), rejected at intake whatever its `previous_hash`. There is no wrap-around (post-MVP), so every sequence comparison (FR2, FR14, FR48, FR59, FR9 Tier 1, FR21) uses plain unsigned ordering. FR63 determinism holds. |
### Genesis & Bootstrap
| FR | Subject | Digest |
|----|---------|--------|
| FR54 | Genesis initiation, bootstrap block creation, and validation exceptions | `initiateGenesis` is accepted only if `local_node_id == 0` (FR67); otherwise it returns a deterministic error and creates nothing. It creates block #0 (node #0 registration plus a self-transfer of `initial_total_network_currency`) and block #1 (chain config with the FR7 content signature), durable-locks the config and enters ready immediately, without FR2/FR3. Exceptions (a)–(i) need both sequence 0/1 AND a content match (block #0 also needs an all-zeros `previous_hash`); otherwise standard FR9 applies. Locally built genesis blocks skip the Tier 1 re-check. |
### External Input Contracts
| FR | Subject | Digest |
|----|---------|--------|
| FR55 | Local transaction-creation surface with Created, Held, Rejected outcomes | A local transaction-creation surface separate from FR14/FR10. The caller supplies a fully assembled, signed `moonblokz-chain-types` transaction (type 1/2/3). The module changes no field (including `vote`) and never consults `scoring_module`. It applies the same readiness and validation as FR14/FR10, including vote-target (FR37) and no-self-vote (FR6). Outcomes: Created (in mempool, evaluable); Held(`deferred`) (in mempool with the FR14 Deferred marker, re-evaluated per FR15); Rejected(`not-ready` / `validation-failed(kind)`), meaning not inserted. The scoring-commit protocol is external. |
| FR56 | Chain-configurable parameters accessed via configuration_module accessors | Hands parameter resolution to the external `configuration_module`. Each parameter has its own no-argument accessor, reached through an optional active-config handle that says whether the config is tentative or durable. Accessors run through the `moonblokz-vm` mini-VM (literal or bytecode) with three tiers: override, then default, then fallback literal, each with a fresh budget. With no handle, the FR9 stage cannot advance. Values and the handle are not cached beyond the invocation. Initial currency, node #0 key and capacities are excluded. It lists the minimum parameters and their bounds, including the verification horizon `H` (literal-only, `1 ≤ H ≤ W`, `W + 2·H` within block-storage capacity). |
### Storage & Retention Policy
| FR | Subject | Digest |
|----|---------|--------|
| FR57 | Capacity-pressure eviction removes single lowest-value side branch | When storage or the block-tree is full and a newly admitted block has no slot, exactly one side branch is evicted. The victim is the branch whose tip has the lowest cumulative branch value; ties go to lowest tip sequence, then lowest creator id, then lowest big-endian tip hash. Eviction runs backward from the tip to the nearest ancestor shared with another retained branch or the active chain. Active-chain and verification-horizon blocks, and the node's own blocks above `S_tail`, are never removed. Bookkeeping is refreshed before the next intake. |
| FR58 | Verification horizon and the chain-switch depth bound | Keeps the `H` active-chain blocks that last left the window. `H` is chain configuration (`verification_horizon`): identical on every node, `1 ≤ H ≤ W`, `W + 2·H` within block-storage capacity. A higher-value candidate with divergence point `D ≥ S_head − H + 1`, against the node's own head, gets an in-place FR23 switch; a branch with `D ≤ S_head − H` never becomes active and is reclaimed when it moves out of the bound. No deep zone: FR3 runs only on collecting → ready. A stalled partition side can still rejoin; two sides that both advance more than `H` past the divergence stay forked. Stored fragments whose missing parent lies at `q ≤ S_head − H − 1` are reclaimed too; FR57 never evicts the horizon (DEC-159–DEC-161). |
### Lifecycle & Recovery
| FR | Subject | Digest |
|----|---------|--------|
| FR59 | Durable-storage scope, restart reconstruction, and intake suspension | Durable storage holds only: `node_id`, the private key (never given to the module, see FR68), the `chain_config` block with its locked flag, and retained block-tree blocks. No lifecycle marker, projection or replay buffer is persisted, and the mempool is empty after restart. On restart the module always enters collecting: (1) rebuild the block-tree, (2) evaluate FR2, (3) if met, run the FR3 pass and go to ready, (4) otherwise stay collecting. All intake is suspended from (1) until ready or collecting-idle. There is no resumable partial processing. |
| FR60 | Out-of-snake-chain-window classification and long-disconnect diagnostic log | Ready state only: a block with `S_new ≥ S_head + W` or `S_new < S_tail` is classified Out-of-Snake-Chain-Window (FR10) and is not stored, not added to the tree and not validated further. In collecting state every block is admitted at Stored, and outcomes reduce to Accepted-new / Already-known / Invalid-evidence. The forward case, in ready state only, also emits a diagnostic `long-disconnect-detected` FR64 log (`S_new`, hash, `(S_tail, S_head)`) with no state change. The result is a permanent fork; resync needs an operator and is out of MVP scope. |

### Simulation, Observability & Public API
| FR | Subject | Digest |
|----|---------|--------|
| FR62 | Same moonblokz-blockchain crate build for simulator and embedded runtime | The simulator embeds the same `moonblokz-blockchain` build as RP2040-LoRa, with no fork and no conditional paths that bypass validation, scheduling or chain-switch logic. External crates (storage, crypto, time driver) may differ via feature flags, but only for platform functionality. Trait contracts, signatures, types and semantics stay identical. The simulator may not use flags or backends that relax determinism, reorder events or weaken validation. |
| FR63 | Deterministic replay from sealed event sequence and PRNG seed | The replay event set is exactly: block intake, transaction submission, top-mempool exchange, support-message intake, local transaction creation (full signed FR55 transaction), genesis initiation (FR54) and time-driver ticks (FR46). The same sequence on the same initial state must give the same state and outcomes (FR10/16, FR55, FR44, FR34 including available-UTXO bitfields, FR35/FR39 recomputations). All randomness (e.g. FR31/FR33 eviction) comes from a seeded PRNG. The seed is a construction input: fixed in test/sim, different per node in deployment. No other input may affect state. |
| FR64 | Structured log records emitted for every internally significant event | Mostly an enumerated contract: a structured log record for every internally significant event. Inbound events, outcomes, queries and introspection are separate typed entry points using enums/structs. Direct indexing is allowed only when bounds are proven locally, otherwise `.get()` is used. Introspection is feature-gated; everything else is always available. |
| FR66 | Adjacent components consume blockchain state only via public API | The radio layer and the local interface read blockchain state only through the crate's public API (FR40, FR41, FR42, FR44, FR64). Storage is not a consumer, and there is no telemetry module. No external caches, memoization or mirrors are allowed; every read is a fresh API call. FR34 projections exist only inside the module. Nothing may be derived from raw radio traffic, storage inspection or mempool snooping. |
### Initialization Parameters
| FR | Subject | Digest |
|----|---------|--------|
| FR67 | local_node_id immutable code-level node-identity parameter | `local_node_id: u32` is a construction-time parameter and the module's canonical local identity (used by FR44, FR45, FR12, FR13, FR27, FR55). It is not chain-config, not exposed by `configuration_module`, and cannot be changed at runtime. The module does no authority check: an unregistered id gives `local-is-not-current-creator` and no block creation until it is registered. A wrong id makes other nodes reject the node's blocks (FR9 Tier 1/3), while chain-following stays correct. |
| FR68 | All signing delegated to crypto module; no private key held | The module never holds, receives or inspects the signing key. `moonblokz-crypto` produces every signature through `sign()` or `multi_sign()` (the latter where FR27 aggregation applies): FR45/FR54 block signatures, FR12 support messages, the FR54 block-#1 content signature and the FR55 genesis `new_key_signature`. The crypto `public_key()` must match the FR34 key bound to `local_node_id` (at genesis: `node_zero_public_key` if id is 0). On mismatch, every FR45/FR12/FR54/FR55 signing attempt returns a deterministic error. The mismatch is logged per FR64, and an operator must fix it. |
| FR69 | node_zero_public_key immutable code-level trust-anchor parameter | `node_zero_public_key` is an immutable construction-time trust anchor with the same properties as FR67. Any received or locally created artifact that asserts a different node #0 key is exact evidence (FR16) and is rejected at the earliest evaluable point. The enforcement sites are FR9 Tier 1 checks: (i) registration with `new_node_id == 0`, (ii) balance-block `owner == 0` entries, (iii) the FR7 content signature. All are evaluable at Tier 1 intake. If the anchor is wrong, the node never converges, and an operator must re-initialize it. |
| FR70 | Same-parent equivocation (twin blocks): definition, signature preimage, prevention, detection, hold | Twins share creator, sequence and `previous_hash` and differ in hash; different parents are legitimate. The creator signature signs the header with `H(payload)`, so a header plus payload hash proves a twin. A node never signs a second child of a parent (own blocks above `S_tail` are not evicted). Conflicts are detected at intake or from a twin vote. A ready node never switches across a twin to the other twin without an FR71 verdict: it keeps the twin it adopted first. The chain does not freeze. FR40 flags confirmations above an unresolved twin as disputed. |
| FR71 | Twin verdict and twin evidence block (`payload_type=5`) | Subgroup from the state at the shared parent `P` (seed `H("twin" ‖ hash(tail_P) ‖ c ‖ s)`, `A` without `c`, `m = min(2r−1, \|A\|)`). Members sign one vote for their first-adopted twin; restarted nodes abstain below their ready-entry head; one round, no retry. The entitled creator of the branch emits the evidence block after due replays: the other twin's header and payload hash (proof), `c`'s vote snapshot, and with a quorum a signer bitmap plus aggregated signature. Normal `consumed_votes`, no extra value. A verdict for a candidate's twin lifts the FR70 hold. About 1.93 KB with Schnorr and `r = 50` (bitmap required). |
| FR72 | Equivocation penalty: W-block exclusion from block creation | While a twin evidence block for `c` is in the window (`W` blocks), `c` is left out of the creator order (no top, fallback or deviation proposer) and out of the active set `A`; the evidence block resets `av(c)` to 0. Transactions, balance and incoming votes are unaffected. Derived from the window, no persisted state. |
