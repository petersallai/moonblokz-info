## Product Requirements Document

## Executive Summary
moonblokz-blockchain is an internal-first Rust crate that serves as the authoritative blockchain interpretation boundary for MoonBlokz under constrained embedded and radio-network conditions. It reconstructs the best currently defensible common blockchain state from best-effort, partial, delayed, and conflicting radio-delivered knowledge, and exposes that interpretation through a semantically coherent API to adjacent MoonBlokz components.

The MVP is a correctness-critical platform foundation rather than a toy proof of concept. It must support deterministic blockchain validation, bounded active-chain retention through snake_chain replay, branch competition and chain-switch reconciliation, transaction intake and mempool management under partial knowledge, creator selection and fallback block creation, and robust observability and replayability for simulator-driven validation.

## Success Criteria
- The blockchain module deterministically reconstructs the same authoritative active-chain interpretation from the same retained blockchain knowledge.
- The module preserves correctness across delayed knowledge arrival, missing parents, branch divergence, chain switches, and active-window tail advancement.
- Adjacent MoonBlokz components can consume blockchain-facing truth exclusively through the crate’s public API without duplicating authoritative-state reasoning.
- Simulation and replay workflows can drive the same semantic module build used in runtime and reproduce identical state transitions and outcomes.
- Developers and validator engineers can inspect correctness-critical behaviors through structured observability without reverse-engineering across subsystems.

## Product Scope
### In Scope
- Authoritative blockchain interpretation from partial and delayed knowledge
- Active-chain selection and chain-switch reconciliation
- Transaction intake, mempool management, and derived-state projection
- Bounded active-chain retention via snake_chain replay
- Creator selection, grace-period fallback behavior, and deviating-block approval workflow
- Runtime and simulator embedding through one semantically identical Rust crate
- Public API for adjacent MoonBlokz component integration

### Out of Scope
- Automatic recovery from long-disconnect states in MVP
- Simulator-specific semantic shortcuts or bypasses
- Alternative authoritative blockchain reasoning in adjacent components
- Resumable partial reconstruction after restart in processing state
- Reconciliation across chain-config content boundaries (foreign-chain merging).

## User Journeys
1. **Radio-layer intake journey** — The radio layer receives blocks or transactions from the network and submits them to the blockchain module, which stores, stages, validates, and integrates them into its current authoritative interpretation.
2. **Local-interface transaction creation journey** — The local interface requests creation or submission of a transaction; the blockchain module obtains the externally selected vote target, validates and classifies the transaction, and exposes resulting state through deterministic query surfaces.
3. **Branch divergence journey** — Competing branches arrive under partial knowledge; the blockchain module retains multiple candidates, resolves missing parents, computes branch value, and performs structured chain-switch reconciliation when a different branch becomes authoritative.
4. **Creator-role journey** — The blockchain module determines whether the local node is currently expected to create the next block, schedules time-driven deadlines, triggers ordinary or fallback block creation, and applies deviation-accounting when required.
5. **Simulator/validator journey** — The simulator embeds the same crate build as runtime, drives it through block, transaction, support-message, and timer events, and inspects structured logs to validate correctness-critical behaviors.

## Domain-Specific Requirements
- Blockchain truth is defined by the module’s current authoritative active-chain interpretation, not by incidental local storage or network observations.
- The environment is constrained, intermittently connected, and resource-bounded; responses and internal representations must respect embedded limits.
- Snake-chain bounded retention is mandatory: essential state must be replayed forward before older blocks can leave the active window.
- Rare paths such as chain-switch reconciliation, delayed key discovery, fallback creation, and approval-evidence legitimacy changes are first-class behaviors, not exceptional error branches.

## Innovation & Novel Patterns
- Best-effort authoritative blockchain reconstruction under missing, delayed, and conflicting block knowledge
- Snake_chain-based preservation of configuration, balances, and live UTXOs in a bounded active window
- Deterministic creator selection with vote-based anti-capture dynamics and grace-period recheck iteration
- Simulator-embedding and replay determinism as core product capabilities rather than optional tooling extras

## Developer Tool Specific Requirements
- The blockchain module must expose a semantically typed public Rust API suitable for internal-first integration and external understanding.
- Simulation, testing, and validation workflows must run against the same crate semantics as embedded runtime usage.
- Structured logs must be sufficient for deep observability without separate introspection-only APIs.

## Project Scoping & Phased Development
### MVP Focus
- Correct authoritative interpretation of a bounded active chain
- Processing-state full-chain validation and rollback/deletion handling
- Branch retention, branch value comparison, chain-switch reconciliation
- Mempool, derived state, creator ordering, block creation, and approval evidence
- Snake_chain replay and tail-preservation mechanisms required for correctness
- Deterministic replay, simulator embedding, and structured logging

### Post-MVP Extensions
- Sequence wrap-around handling — extend the `u32` sequence space with modular comparison semantics, wrap-block / genesis discrimination, and ancestry-based comparison rules to support indefinite chain growth across the `u32::MAX` boundary; MVP explicitly refuses chain extension beyond `u32::MAX` per FR53.
- Operational recovery flows for long-disconnect states
- Additional developer ergonomics beyond required public API and log surfaces

## Main Conceptual Limitations
- Balance-state preservation capacity is bounded by balance-block packing: a single balance block can carry only a bounded subset of node entries under `MAX_BLOCK_SIZE`, so chains with many registered nodes depend on the collective active-window coverage rule of FR50 rather than on full enumeration in any one balance block.

## Functional Requirements
### Chain Lifecycle & State Progression
- FR1: The blockchain module shall initialize an empty chain in collecting state. The module shall remain in collecting until the accumulated block-tree satisfies a dominant-chain acquisition stopping condition as defined in FR2; that condition alone triggers the processing transition per FR3. While in collecting state, ready-state-dependent outward behaviors shall return a not-ready indication: block-retrieval queries (FR42), transaction-state queries (FR40), balance/UTXO queries (FR41), creator-role determination (FR44), top-mempool-items exchange per FR43, transaction intake per FR14 / FR10, local transaction creation per FR55, and mempool replenishment scheduling/emission per FR46. Transaction intake is a ready-state-dependent behavior because FR14's classification inputs — the `anchor_sequence` acceptance window, Already-confirmed detection against the active chain, and Deferred evaluation against the active-chain node roster — are all defined against the current active chain, which does not exist in collecting state. Mempool replenishment is likewise ready-state-dependent because its outbound request/response behavior depends on the authoritative mempool ordering and block-fit comparison defined in FR43 / FR45 against the current active-chain-governed transaction-selection rules. Block intake and staged validation per FR9, FR10, and FR16 remain active. The not-ready indication returned for FR40, FR41, FR42, FR43, and FR44 applies uniformly to every caller, including block-retrieval requests forwarded by the radio layer on behalf of peer nodes. A collecting-state node therefore does not serve blocks or participate in mempool replenishment exchange with the network; MoonBlokz's collecting-phase convergence relies on peers already in ready state to supply blocks from their active chain via FR42. A collecting-state node acts purely as a receiver through the intake surface (FR9) and its own outbound parent-recovery requests (FR19), which remain active in collecting state.
- FR2: While in collecting state, the blockchain module shall continuously evaluate the accumulated block-tree against the dominant-chain acquisition stopping conditions (Algorithm 2A) and shall transition out of collecting as soon as at least one candidate continuous segment satisfies any of the following: Genesis-anchored segment: a continuous chain of connected, parseable blocks exists from block #0 (genesis) up to a branch tip, even if shorter than the configured active-chain length. Active-length-satisfying segment: a continuous chain of connected, parseable blocks exists whose length is greater than or equal to the configured active-chain length (`snake_chain` window size), regardless of whether its ancestry reaches #0. `Continuous` means every block in the segment except the segment's earliest (lowest-sequence) block has its `previous_hash` resolved to another block present in local storage. The segment's earliest block is the segment's start point and is not itself required to have a locally retained predecessor — its `previous_hash` may reference a block absent from local storage, and that absence is precisely what defines the earliest block as the start of the segment. For the genesis-anchored segment case the earliest block is block #0 (which has no `previous_hash` predecessor by definition per FR54); for the active-length-satisfying segment case the earliest block may be any retained block whose `previous_hash` is unresolved locally, and its missing predecessor does not break segment continuity above it. When multiple candidate segments independently satisfy a stopping condition, the module shall select the candidate whose tip has the highest sequence. If two or more candidates share the same highest sequence, the module shall break the tie deterministically by the lowest tip block hash interpreted as a big-endian unsigned integer — an in-memory total order (distinct blocks have distinct hashes) that preserves replay determinism under FR63. This collecting-phase tie-break is only a bootstrapping choice of which candidate to reconstruct first; it does not determine the final authoritative chain, which branch value governs per FR21 / FR22 / FR23 once the node reaches ready state (a branch-value re-evaluation chain-switches away from the FR2 pick if it was not the authoritative branch). Aligning this tie-break with the fuller ordered rule of FR21 — larger tip serialized size, then lowest tip creator node identifier, then lowest tip hash — is a deferred optimization, not a correctness requirement (ratified 2026-07-22): it would only avoid one otherwise-unnecessary chain-switch in the rare case where two equal-sequence candidates also carry equal branch value. The MVP uses the hash-only rule because a node's in-memory block-tree metadata does not retain tip serialized size or creator node id (RAM-budget discipline), so applying the size / creator criteria would require reading tip block content; adopting the fuller rule remains a valid post-MVP optimization. If the selected candidate subsequently fails FR6 validation, the FR5 deletion-and-reversion policy returns the module to collecting state, where the remaining candidates are re-evaluated against this rule on the next iteration. Branch-value evaluation per FR21 applies only in ready/processing states; it shall not be used as a collecting-phase selection criterion.
- FR3: Upon a FR2 stopping condition being met, the blockchain module shall transition from collecting to processing and execute a dedicated full-chain reconstruction pass over the candidate segment selected by FR2, per Algorithm 2B, consisting of: Backward traversal from the candidate tip to mark which stored blocks belong to the selected chain. Candidate chain-config preload — immediately after the backward traversal and before forward traversal begins, the module shall locate the chain-config block(s) (`payload_type=3`) within the marked candidate segment, verify per FR6's chain-config compliance invariant that every such block's configuration content is byte-identical (rolling back per FR5 if not), and use that candidate-segment configuration content as the basis for every chain-config-derived check (per the chain-config-derived trigger list of FR9's Invalid status preamble) during the subsequent forward traversal; the tentatively loaded `configuration_module` content of FR8 shall not be consulted for these chain-config-derived checks during forward traversal. The tentatively loaded configuration is consulted only afterwards, by the FR8 final-check phase, to decide whether the durable-lock can proceed against the candidate-segment configuration directly or whether the tentative must first be replaced per FR8's mismatch path. If the candidate segment contains no chain-config block in scope, the segment cannot satisfy FR6 chain-config compliance and shall be rolled back per FR5 / FR8. Forward traversal from the earliest marked block toward the tip, progressively rebuilding operational state: node roster and public-key mapping, per-node balances, accumulated vote (including anti-capture interest growth per FR37), creator-order projection (FR38), per-block UTXO spent-bit vectors (FR34 / ADR-016), and `snake_chain` essential-state bookkeeping. Per-node seed rule — for every registered node `N` whose state must be tracked, derived state is seeded from `N`'s earliest seed source within the marked candidate segment: either the earliest balance-block entry that contains `N` (seeding balance, accumulated vote, public key from the entry's content), or `N`'s registration transaction within the segment (seeding balance = 0, accumulated vote = 0, public key = `new_public_key`, per the registration-as-seed equivalence of FR50, with `registration_price` absorbed by the network per FR6 and no balance credited to the new node). Different nodes may be seeded at different sequences within the segment; the seed sources collectively realize the `snake_chain` coverage invariant of FR50. The `max_known_node_id` watermark of FR34 is initialized from the `max_node_id: u32` field of the earliest balance block in the segment when such a balance block exists in the marked candidate segment; otherwise — i.e. when the candidate segment is genesis-anchored and contains no balance block ahead of block #0's registration — the watermark is initialized to 0 per FR54's bootstrap-only exception (h), block #0's registration is accepted with `new_node_id == 0` (replacing the `max + 1` rule for that single registration), and the watermark is not incremented by block #0's registration. From block #2 onward, the watermark is incremented by exactly one on every subsequent registration encountered during forward traversal, and shall match the `max_node_id` field of every later balance block at that block's sequence; any divergence is exact evidence of invalidity per FR5 / FR6's `snake_chain` preservation invariants. Pre-seed transaction acceptance — for any node `N` whose registration is not within the marked segment (i.e., `N` already existed before the segment), transactions involving `N` that occur in the segment before `N`'s earliest seed source within the segment fall in `N`'s pre-seed zone; in that zone, all per-`N` state-dependent checks are auto-accepted (including `N`'s balance sufficiency for any input contributed by `N`, `N`'s signature validity against its yet-unseeded public key, and `N`'s vote restrictions), grounded in the atomicity of FR3 / FR6 (the candidate either fully validates from the per-node seed points to the tip or is fully rolled back per FR5) combined with the network-attestation implicit in the candidate's continuous, signed, hash-linked, creator-voted existence at length `≥W`. Per-node seeding therefore does not affect blocks whose constituent transactions involve only nodes already past their seed sources, nor does it affect structural, payload-level, or chain-config-derived checks that do not depend on a specific node's pre-state. UTXO spent-bit vectors are tracked globally throughout the forward pass for every block in the marked candidate segment regardless of pre-seed-zone status: each block's spent-bit vector is initialized to all `0` at backward-traversal time, and forward traversal sets a bit to `1` exactly when the corresponding output is consumed by a transaction's UTXO input — including pre-seed-zone consumptions; the structural input-existence checks of ADR-016 (referenced `block_sequence` within the segment, `output_index` within the block's UTXO-output stream) apply to every UTXO input regardless of pre-seed-zone status, since UTXO-input signature verification uses the address (public key) carried in the referenced output itself and does not depend on per-node seeding. Each block is validated only when, for every transaction in the block, the pre-state of every involved node is either already derivable from prior per-node seeding and forward replay, or the involved node is in its own pre-seed zone for that block and the transaction is auto-accepted under the rule above; every block-level and transaction-level invariant of FR6 is otherwise checked at the point it becomes checkable. Rollback on failure — if any invariant violation, missing prerequisite, or contradiction is detected during traversal, the module shall apply the FR5 deletion-and-reversion policy and return to collecting state. The processing pass is not resumable: if interrupted by restart, all partially reconstructed derived state is discarded and the module re-enters collecting per FR59, rebuilds the in-memory block-tree from the retained durable blocks, and re-runs the FR2 / FR3 path to re-derive projections. The transition from processing to ready shall occur only after the forward traversal has completed successfully against every invariant of FR6.
- FR4: The blockchain module shall transition to ready state only after chain validation succeeds.
- FR5: When the full active-chain validation of the processing phase (FR6) fails, the blockchain module shall execute an atomic recovery that combines reconstruction working-set rollback and durable-storage deletion. This recovery applies under exact evidence per FR16, extended to cover processing-phase semantic proofs such as signature invalidity against a now-known creator key, duplicate-transaction detection, negative-balance outcome, vote- or creator-rule violation, chain-config non-compliance, or `snake_chain` preservation failure. The recovery shall be performed as a single atomic step with the following rules: Working-set rollback: the derived operational state accumulated during FR3's forward traversal — per-node balances, accumulated vote (including anti-capture interest), per-node public-key mapping, max-node-id watermark, creator-order projection, per-block UTXO spent-bit vectors, and every other derived projection defined in FR34 — shall be discarded in full and atomically, regardless of which durable-deletion path is chosen below. This rollback always applies and leaves the module in a clean baseline state with no residual derived projections before phase reversion. Offending-block identification: FR6 re-execution shall record the earliest block at which an invariant was violated; that block is deleted from durable storage. Fallback when the offending block cannot be precisely identified: the module shall delete from durable storage exactly one block — the candidate chain's head — on the assumption that the failing branch will not progress further and that advancing the tip under deeper uncertainty is not worth more aggressive pruning. Transitive descendant deletion: every transitive descendant of a deleted block — i.e., every block whose `previous_hash` chain passes through that block — shall also be deleted from durable storage, since `previous_hash` is immutable and a single block has exactly one parent link, so the broken connection cannot be reconstructed via any other path. This explicitly includes every block on the candidate chain between the offending block and the pre-failure tip when the offender is precisely identified. Sibling subtrees rooted at other branches of the block-tree (blocks whose `previous_hash` chain does not pass through any deleted block) are unaffected and remain in durable storage. Phase reversion: the module shall return to collecting state and re-evaluate the remaining block-tree against the FR2 dominant-chain acquisition stopping conditions. Storage deletion remains bounded to this rule, to FR16's exact evidence conditions during normal intake, to FR17's chain-config silent-discard, to FR19's chain_heads-eviction, and to FR57's capacity-pressure eviction. Following any FR5 deletion the module shall update FR19 `chain_heads` per its block-tree-mutation rules (remove any chain_heads entry whose `head_block_id` was deleted; index the childless tip the deletion creates at the deleted subtree root's surviving parent; recompute cache fields and demote Connected heads that lost their active-chain connection to Stored with `last_request_timestamp = 0` — see FR19 event (iv) for why that demotion antecedent cannot arise under this rule).
- FR6: Before transitioning from processing to ready state, the blockchain module shall re-execute the candidate active chain forward from its earliest block and verify for every block and every transaction within it that: Block-level invariants (note: header `version` support is a structural intake-time check enforced at FR9 Tier 1 / FR16 in every lifecycle state, so it is not re-evaluated here): `previous_hash` links to the immediately preceding block in the candidate chain, block creator signature is valid against the creator's public key derived from the candidate chain, `consumed_votes`, `first_voted_node`, and `consumed_votes_from_first_voted_node` are consistent with the vote state derived from the preceding chain, block size does not exceed the configured `MAX_BLOCK_SIZE`, payload structure conforms to the declared `payload_type`, for `payload_type=1` transaction blocks the registration / complex-transaction mutual-exclusivity invariant holds — i.e., the block does not simultaneously contain at least one registration transaction (`type=2`) and at least one complex transaction (`type=3`, including zero-input UTXO carry-forward complex transactions per FR51); a violating block constitutes exact evidence of invalidity per FR5 and triggers the deletion-and-reversion policy. The rationale is that allowing both kinds in the same block would force a single dropping tail block to trigger both UTXO carry-forward (FR51) and balance replay (FR50) at once, breaking the per-payload-type single-replay invariant the carry-forward and balance-replay scheduling rules of FR45 / FR48 / FR49 / FR50 / FR51 rely on. Beyond this mutual-exclusivity rule, `mined_amount` is consistent with the chain-config reward rule in scope at that sequence, and the block creator's resulting balance reflects the mining reward and transaction-fee credit defined in FR36. Transaction-level invariants (per Algorithm 13): Node transfer: initializer has sufficient balance for amount + fee; block sequence > `anchor_sequence`; transaction signature is valid; no duplicate of an already-confirmed node transfer with identical `(initializer, receiver, amount, anchor_sequence, comment)` exists in the candidate chain. Registration: initializer is an existing node with sufficient balance for `registration_price` + fee; `new_public_key` is globally unique within the candidate chain (no earlier accepted registration on the candidate chain — including earlier registrations within the same block — has the same `new_public_key`; `new_public_key` is also the canonical uniqueness key under which a registration is treated as Already-confirmed or Duplicate-in-mempool per FR14); `new_key_signature` proves possession of the corresponding private key; initializer signature is valid; `new_node_id` equals `max_known_node_id + 1` at inclusion point, where `max_known_node_id` is incremented by exactly one each time a registration transaction is accepted — including transaction-by-transaction within a single block. A block may therefore contain multiple registration transactions; their `new_node_id` values shall form a strictly increasing sequence with stride 1 starting from `max_known_node_id_before_block + 1`. A block whose registrations violate this within-block monotonic incrementation rule, or whose any registration's `new_node_id` does not match the watermark at its own intra-block position, constitutes exact evidence of invalidity per FR5; the `registration_price` is absorbed by the network — it is debited from the initializer's balance and credited to no node's balance, reducing the network's total currency by exactly `registration_price` upon inclusion of the block into the active chain. The transaction fee is a separate amount and is NOT covered by this absorption rule; its distribution follows the creator-credit rule of FR36, under which transaction fees are credited to the block creator. Complex transaction (with at least one input): every referenced UTXO input resolves against the candidate chain: the block at `block_sequence` exists within the retained window, `output_index` is within the bounds of that block's UTXO-output stream, and the corresponding bit in that block's spent-bit vector is 0 (unspent) at the point of inclusion; every balance input is valid against the derived balance state; every input signature is valid for its declared signature scope; total inputs are greater than or equal to total outputs; applying the transaction results in no negative node balance; no duplicate of an already-confirmed complex transaction with the identical full input set (every UTXO input matched by `(block_sequence, output_index)` and every balance input matched by its full bytes including `(initializer, anchor_sequence, amount, comment)`, every input matching) exists in the candidate chain — the input set in this exact form is the canonical uniqueness key for complex transactions under FR14. A zero-input complex transaction is not subject to any of the rules in this clause (in particular not to the total inputs ≥ total outputs rule). Whether a given zero-input complex transaction is a valid `snake_chain` UTXO carry-forward (per FR51) is NOT evaluated in this phase, because the candidate active chain is by construction exactly `snake_chain_length` long and the dropping-block context required for carry-forward validation lies outside this phase's scope. The accepting node trusts that the ready-state validators that previously appended these blocks at the active-chain tip have already verified carry-forward correctness via the FR9 Tier 2 / Tier 3 gating (FR51 carry-forward state-side validity, FR51 acceptance-time validation). The only carry-forward-related constraint enforced in this phase is the structural mutual-exclusivity rule stated above (a block carrying a zero-input complex transaction shall not also carry a registration transaction). Approval evidence block (`payload_type=4`): every referenced supporter belongs to the deterministic supporting subgroup applicable to the referenced `proposed_sequence`; every included support signature is valid over the canonical support-message content; the aggregated support count meets or exceeds `required_support` at the referenced `proposed_sequence`; and the evidence does not exceed the maximum aggregated-signature capacity supported by the cryptographic backend. Vote and creator invariants: every transaction's `vote: u32` field shall reference a `node_id` that exists on the candidate chain at the point of the transaction's inclusion (per the candidate-projected node roster derived during forward traversal). A transaction whose `vote` field references a `node_id` not present on the candidate roster — including `node_id` values that have never been registered, or values that name a registration that occurs only later in the candidate chain — constitutes exact evidence of invalidity per FR5. Genesis exception: per FR54 bootstrap-only exception (i), the vote-target validity rule does not apply to transactions in block #0; those transactions carry `vote == 0`, which is treated as a valid vote target since node #0 is established by the same block #0 registration and is the only node existing at genesis time. No transaction violates the no-self-vote rule, defined as follows: the transaction's `vote: u32` field shall not equal the `node_id` of any initializer present in that transaction's structure, with the permanent node-#0 self-vote exception below. The rule has two structural application sites: for node transfer (`type=1`) and registration (`type=2`), the transaction-level `initializer` field shall not equal `vote`; for a complex transaction (`type=3`) with one or more balance inputs, every balance input's `initializer` field shall not equal `vote` (a violation against any one balance input's `initializer` is sufficient for invalidity). A complex transaction containing only UTXO inputs has no transaction-level or balance-input-level initializer field and is therefore not constrained by the no-self-vote rule structurally. Permanent node-#0 self-vote exception: when the initializer is node #0, `vote == 0` is always permitted. This applies in every block from #0 onward and is not confined to genesis. Together with the permanent node-#0 vote-target exception of FR37 above (also rooted in this same chain-wide rule), it guarantees that node #0 always has at least one valid vote choice (itself), which is the mechanism that prevents the early-chain bootstrap deadlock between block #2 and the registration of the first non-genesis node. From block #2 onward the no-self-vote rule applies unchanged for every initializer other than node #0. Creator selection at every block is consistent with the accumulated vote state and with Algorithm 3. Chain-config compliance: every block conforms to the rules defined by the active chain-config block in scope at its sequence, including fee policy, registration policy, custodian-fee rate, approval majority threshold not exceeding the maximum aggregated-signature capacity supported by the cryptographic backend, and any other configuration-driven limits. Additionally, every chain-config block (`payload_type=3`) on the candidate active chain — both the original block #1 and every replay chain-config block emitted per FR49 — shall carry configuration content byte-identical to the chain's durable-locked configuration (or, during the processing pass that produces the durable lock, byte-identical across all chain-config blocks within the candidate segment). Any chain-config block whose configuration content diverges from this invariant constitutes exact evidence of invalidity per FR5 and triggers the deletion-and-reversion policy. Note on `snake_chain` preservation invariants: the candidate active chain validated in this phase is by construction exactly `snake_chain_length` long, so the per-block `snake_chain` preservation invariants — which describe how the chain evolves when new blocks are appended at the active tip and when older blocks drop out of the active window — are NOT in scope during the FR6 processing-pass validation. Those invariants (essential-state replay presence per FR49 / FR50, UTXO carry-forward correctness per FR51, custodian-fee reduction and below-fee discard, carry-forward acceptance-time validation per FR51, and replay-precedence ordering per FR29) are enforced only in the ready state, when a new block is appended to the active chain at the tip, via the FR9 Tier 2 gating (chain-config replay block presence per FR49 at every drop point on the candidate ancestry; balance replay block coverage of the per-node seed-source invariant of FR50; replay-precedence ordering per FR29; FR51 carry-forward acceptance-time validation (1:1 tail-drop mapping)) and the FR9 Tier 3 gating (carry-forward transaction state-side validity per FR51 — correct identification of unspent outputs in the dropping block, custodian-fee deduction, below-fee discard). A failure of any of the FR6 invariants above shall trigger the deletion-and-reversion policy defined in FR5 and return the chain to collecting state. The chain shall enter ready state only after all of these invariants have been verified against the full candidate active chain.
- FR7: The blockchain module shall validate every chain-config block (`payload_type=3`) against a content-level signature produced by node #0's persistent registering key, in addition to the ordinary block-creator signature defined in FR6. The chain-config payload shall carry, alongside the configuration content, a signature by node #0 over the canonical bytes of that content; this content-signature is invariant across the lifetime of the chain and is reproduced byte-identically in every replay chain-config block emitted under FR49, regardless of which node creates the replay block. On intake, the module shall verify the content-signature against `node_zero_public_key` — the code-level trust anchor supplied to the module at construction per FR69. Because the trust anchor is available from module construction onward, this verification is always evaluable at FR9 Tier 1 and does not depend on the connected ancestry of the receiving block: every chain-config block is checked against the trust anchor at intake, irrespective of whether the chain-config block is connected to the active chain, irrespective of FR50 balance-replay coverage, and irrespective of the chain-config tentative-vs-durable-lock state of FR8. A content-signature that fails to verify against `node_zero_public_key` is exact evidence of invalidity under FR16 / FR69 and the chain-config block shall not enter durable storage. The block-creator signature requirement of FR6 applies independently and unchanged.
- FR8: The blockchain module shall manage chain-config commitment in two distinct phases. Tentative phase (collecting state) — the first chain-config block whose node #0 content-signature is verifiable per FR7 and whose configuration content is accepted by the `configuration_module` per FR56 shall be tentatively loaded into the `configuration_module` so that configuration-derived parameters become available for staged validation. The chain-config block itself is retained in durable block storage. Subsequent chain-config blocks received during collecting state shall be stored in the block-tree subject to FR16 and shall not override the tentative configuration. Rejection of the configuration content by the `configuration_module` constitutes exact evidence of invalidity for the offending chain-config block and shall be handled per FR16; no tentative load occurs. Compile-time-bound check: in addition to the `configuration_module`'s acceptance check, the chain-config block's `max_block_UTXO_output` value (per FR56) shall be validated against the compile-time `UTXO_UNSPENT_BITS` parameter (the bit count of the FR34 block-navigation-and-UTXO cache's per-block `utxo_unspent_bitfield`); a chain-config whose `max_block_UTXO_output` exceeds `UTXO_UNSPENT_BITS` is exact evidence of invalidity per FR16 and shall not enter durable storage, because the local node's compile-time-fixed cache could not represent the unspent status of that many outputs. Chain-config values smaller than `UTXO_UNSPENT_BITS` are permitted (the cache simply uses only the first `max_block_UTXO_output` bits per block). Approval-threshold lower-bound check: in addition to the `configuration_module`'s acceptance check, the chain-config block's approval majority threshold value (per FR56) shall satisfy `required_support ≥ 1`; a chain-config whose approval majority threshold is below 1 is exact evidence of invalidity per FR16 and shall not enter durable storage, because the deterministic subgroup-selection formula `m = min(2 · required_support − 1, |A|)` of FR12 / ADR-015 would otherwise yield a non-sensical `m = -1`. Final-check and durable-lock phase (processing→ready transition) — before the FR4 ready transition completes, the module shall verify that the candidate active-chain segment selected per FR2 contains at least one chain-config block in scope, and that the configuration content of every such chain-config block on the candidate segment matches the tentative configuration byte-identically. On match, the durable chain-configuration commit is performed once via the storage layer's set-once chain-configuration operation, the configuration is locked for the lifetime of the chain, and every chain-config block already present in durable storage or in the block-tree — whether on the candidate active chain, on retained side branches, or unconnected — whose configuration content does not match the now-durable-locked configuration is removed from durable storage under this FR's durable-lock mismatch cleanup rule, with transitive descendant deletion applied per the FR5 deletion-and-reversion policy. On mismatch, the module shall clear the `configuration_module`, remove the tentative chain-config block from durable storage, adopt the candidate segment's chain-config block content as the new tentative (re-running FR7 verification against it), and restart the processing pass or return to collecting state per the rollback rules of FR3 / FR5 as applicable. When the candidate segment contains no chain-config block in scope, the segment cannot satisfy FR6 chain-config compliance and shall be rolled back per FR5. Tentative-configuration visibility is not a concern: the tentative phase exists only during collecting state, in which no derived state-projections (per-node balances, accumulated vote, public-key mapping, UTXO spent-bit vectors, etc.) have been computed yet and the external local query surface (FR40-series) is inactive — those projections begin in processing (FR3 forward traversal) and become externally observable only after the FR4 ready transition completes against the durable-locked configuration. FR24 coherence therefore does not apply to the tentative configuration, since no derived projections consume it during collecting state.
- FR9: The blockchain module shall maintain a three-status block-lifecycle state machine for each block in the retained block-tree, paired with a three-tier check categorization that governs status transitions and durable-storage retention. The state machine is fully active in ready state; in collecting state every retained block remains in the Stored status (no Connected or Active status is assigned because no active chain exists); in processing state the FR3 forward traversal performs the full Tier 1 + Tier 2 + Tier 3 check sequence atomically against the candidate, and on success transitions the candidate's blocks directly to Active in one step (the previously distinguished `Verified (full)` mid-process label is no longer separately exposed as a block status — it is the transient internal state of the FR3 pass that resolves to Active on success or to Stored / deletion on failure). Status definitions: Stored — a block whose bytes parse correctly against the block structure, whose declared `payload_type` matches a known payload schema, and which has passed every Tier 1 gating check applicable at intake; Connected — a Stored block whose `previous_hash` resolves to a block whose ancestry reaches the current active chain, and which has passed every Tier 2 gating check applicable; Active — a Connected block (or a block that transitioned directly from Stored via FR3) that is currently part of the selected active chain, having been verified at Tier 3 against the active-chain-derived state. Tier 1 (intake-time, gating, durable-storage admission condition; evaluable from the block bytes alone plus the durable-locked chain-config when available): header `version` is in the supported range; declared `payload_type` matches a known payload schema; (ready state, durable-locked chain-config) `block size ≤ MAX_BLOCK_SIZE`; (ready state, durable-locked chain-config) chain-config blocks (`payload_type=3`) carry configuration content byte-identical to the durable-locked configuration (FR17 silent-discard); (ready state) the block's sequence is within the active `snake_chain` window per FR60; for node-transfer transactions, `block.sequence > tx.anchor_sequence`; for complex transactions, `block.sequence > balance_input.anchor_sequence` shall hold for every contained balance input (a violation against any one balance input is sufficient for Tier 1 failure); registration transactions carry no `anchor_sequence` field and are not subject to this rule — registration replay is structurally prevented by the `new_public_key` global-uniqueness invariant (a single public key can be registered only once on the candidate chain), checked at Tier 2 against the active-chain node roster and at Tier 3 against the candidate-side roster; the no-self-vote rule of FR6 is satisfied for every transaction in the block (excluding block #0, for which the no-self-vote rule and the vote-target validity rule are waived per FR54 bootstrap-only exception (i)); complex transactions with at least one input satisfy the structural input/output amount summation `sum(declared input amounts) ≥ sum(declared output amounts)` (where any UTXO input whose referenced block is not yet locally resolvable at intake defers this completion to Tier 2); for `payload_type=1` transaction blocks, the registration / complex-transaction mutual-exclusivity invariant of FR6 — the block does not simultaneously contain at least one `type=2` registration transaction and at least one `type=3` complex transaction (including zero-input UTXO carry-forward complex transactions per FR51) — holds; this check is evaluable from block bytes alone, applies in every lifecycle state (collecting, processing, ready), and a violation is exact evidence of invalidity per FR16 / FR5, with the offending block rejected at intake and not entering durable storage; registration transactions: `new_key_signature` validity (cryptographic signature verification against `new_public_key`); FR69 node-zero trust-anchor checks (evaluable from block bytes alone against `node_zero_public_key`, available from module construction onward): (i) for any registration transaction whose `new_node_id == 0`, `new_public_key` shall equal `node_zero_public_key` (a mismatch is exact evidence of invalidity per FR16 / FR69 and the block is not stored); (ii) for any balance block (`payload_type=2`) whose NodeInfo array contains an entry with `owner == 0`, that entry's `public_key` shall equal `node_zero_public_key` (a mismatch is exact evidence of invalidity per FR16 / FR69 and the block is not stored); (iii) for any chain-config block (`payload_type=3`), the FR7 content-signature shall verify against `node_zero_public_key` (a verification failure is exact evidence of invalidity per FR16 / FR69 and the block is not stored). Tier 1 also includes a ready-state block-creator-signature rule with one exact-evidence exception and an otherwise opportunistic signature-verification side effect. Exception — when the received block directly extends the current active-chain head (`previous_hash = active_chain_head_hash`) and the creator's public key is derivable from the current active chain, a verification-failure outcome for the block-creator signature is exact evidence of invalidity and transitions the block to the terminal Invalid classification at Tier 1. Outside that direct-active-extension case, block-creator signature verification in ready state remains opportunistic. In ready state, for the block-creator signature and for each contained transaction's initializer signature (and for each newly mempool-admitted transaction's initializer signature), the module performs a public-key lookup against the active chain's per-node public-key projection (FR34) and, on lookup success, performs the cryptographic signature verification; outside the direct-active-extension exception, a public-key lookup failure or a verification-failure outcome at this side-effect stage shall not transition the block (or transaction) to Invalid — the authoritative signature decision is deferred to Tier 3, where the candidate-side-roster public key is the canonical reference. Failure of any Tier 1 gating check (other than the side-effect signature steps) transitions the block to the terminal Invalid classification per the deletion path defined below. Tier 2 (Connected promotion, gating, ancestry- and lookup-based; evaluable once the block's ancestry resolves to the current active chain, using the active chain's per-node projections of FR34 as lookup-only sources, without derived-state forward replay): `previous_hash` resolves to a block in the retained block-tree whose own ancestry reaches the current active chain; the block conforms to the durable-locked chain-config rules in scope at the block's sequence (fee policy, registration policy, custodian-fee rate, approval-majority threshold, and any other configuration-driven limits); `mined_amount` is consistent with the chain-config reward rule in scope at the block's sequence; complex-transaction UTXO-input structural completion (each UTXO input's referenced `block_sequence` is within the retained block-tree, the `output_index` is within the bounds of the referenced block's UTXO-output stream, and the referenced output amount is readable from the referenced block's bytes — completing any Tier 1-deferred `total inputs ≥ total outputs` check); registration `new_public_key` global uniqueness against the active chain's node roster (FR34 lookup); `snake_chain` preservation invariants on the structural side (chain-config replay block presence per FR49 at every drop point on the candidate ancestry; balance replay block coverage of the per-node seed-source invariant of FR50 — every registered node has at least one seed source, balance entry or registration transaction, within the candidate's W-window; replay-precedence ordering per FR29; FR51 carry-forward acceptance-time validation (1:1 tail-drop mapping)) — evaluable at Tier 2 only when the historical reference blocks the FR49 / FR50 / FR51 / FR56 / FR29 checks compare against are still locally retained. For active-chain extension this condition is automatic (the dropping tail block is by construction within the verification horizon). For an FR23 chain-switch candidate it holds only when the divergence point `D` lies in the cheap zone (`D ≥ S_tail + (W − H)` per FR58), so that the `D − W` historical reference block remains retained. For deep-zone divergences (`D ∈ [S_tail, S_tail + (W − H) − 1]`) the `D − W` reference has fallen out of the verification horizon, in-place Tier 2 lookup cannot validate the structural `snake_chain` invariants, and the check is deferred to Tier 3 — performed only via the FR58 deep-zone full-reconstruction path (or, for the bootstrap collecting → processing transition, via the FR3 processing-pass forward traversal). The deferred structural `snake_chain` check does not block the Stored → Connected promotion: if the rest of the Tier 2 gating passes (ancestry resolution, durable-locked chain-config compliance, `mined_amount`, UTXO-input structural completion, registration `new_public_key` uniqueness), the block is promoted to Connected. The deep-zone-deferred structural `snake_chain` check then runs at Tier 3 only when the FR58 deep-zone full-reconstruction is actually triggered against the candidate (per FR58's two-part trigger discipline) — until then, the block sits as a Connected side-branch member with the structural `snake_chain` check carried forward to that Tier 3 path. This differs from a missing-ancestry deferral (e.g., a parent still under FR19 parent-recovery), which keeps the entire Tier 2 evaluation pending and leaves the block in Stored. Failure of any Tier 2 gating check transitions the block to Invalid classification; while a Tier 2 check is not yet evaluable due to missing ancestry context (e.g., an ancestor still under parent-recovery per FR19), the block remains in Stored. Tier 3 (Active promotion, gating, derived-state-replay-based and authoritative; evaluable only via FR3 processing-pass forward traversal or via FR23 chain-switch reconciliation forward replay along the candidate's own derived projection from the common ancestor): block-level — `consumed_votes`, `first_voted_node`, and `consumed_votes_from_first_voted_node` consistency with the candidate-projected vote state at the block's sequence (per FR37 anti-capture interest, vote-field accumulation, and creator-reset rules); block-creator post-acceptance balance correctness (mining reward + transaction-fee credit per FR36, projected on the candidate); for balance blocks (`payload_type=2`), NodeInfo content correctness per FR50 — every NodeInfo entry's `(balance, vote_count, public_key)` triple shall be byte-consistent with the candidate-projected per-node state at sequence `block.sequence − 1` (the post-previous-block / pre-this-block state, per FR50's snapshot semantics, before the balance block's own acceptance effects of FR36/FR37 are applied), and the balance block's `max_node_id` payload field shall match the candidate's forward-traversal-tracked `max_known_node_id` watermark at that block's sequence; any divergence on either component is exact evidence of invalidity per FR5; transaction-level (per Algorithm 13 against the candidate's projection) — node-transfer initializer signature validity against the candidate's per-node public-key projection (cryptographic signature verification against `candidate_pubkey`); node-transfer initializer balance sufficiency for `amount + fee`; no-duplicate-confirmed transaction across the candidate ancestry; registration initializer signature validity (verified as above); registration `new_node_id == max_known_node_id + 1` against the candidate's max-node-id watermark, where the watermark is incremented per accepted registration transaction (transaction-by-transaction, not block-by-block) so that multiple registrations within a single block must form a strictly increasing `new_node_id` sequence with stride 1 starting from the pre-block watermark; registration initializer balance sufficiency for `registration_price + fee`; complex-transaction balance-input initializer signature validity (verified per balance input); complex-transaction balance-input validity against the candidate balance state; complex-transaction UTXO-input spent-bit `0` against the candidate's spent-bit-vector projection per ADR-016; complex-transaction no-negative-balance result; carry-forward transaction state-side validity per FR51 (correct identification of unspent outputs in the dropping block, custodian-fee deduction, below-fee discard); structural `snake_chain` preservation invariants per FR49 / FR50 / FR29 / FR56 — when this Tier 3 path runs via the FR58 deep-zone full-reconstruction (or, equivalently, via the FR3 collecting → processing initial-establishment forward traversal), the replay-presence (FR49), balance-replay coverage (FR50), replay-precedence ordering (FR29), and carry-forward acceptance-time validation (FR51) checks otherwise listed under Tier 2 are validated here against the candidate's own forward-replayed derived projections, replacing the Tier 2 lookup-only evaluation that is not feasible when the `D − W` historical reference is no longer retained; approval-evidence-block invariants (treated as a single coherent check-cluster) — supporter subgroup membership via ADR-015 deterministic seed against the candidate's `snake_chain_tail_hash` and active set `A`; aggregated support count ≥ `required_support`; aggregated-signature crypto verification against the candidate's per-node public-key projection; evidence size bounded by `MAX_AGGREGATED_SIGNATURES`; supporter vote-sum invariant on the evidence block's `supporter_vote_sum` payload field per FR21 / FR27; non-replay block-creation pacing rule (ready-state intake only, applies to `payload_type=1` transaction blocks whose payload contains at least one ordinary `type=1` / `type=2` / non-zero-input `type=3` transaction; pure zero-input UTXO carry-forward blocks and all replay-only blocks per FR49 / FR50 / FR51 are exempt) — when the submitted block satisfies both of (a) the actually-included payload size is below the chain-config-defined minimum block-fill threshold (the same `transactional block-fill threshold percentage of MAX_BLOCK_SIZE` parameter that governs FR45's creator-side trigger conditions), and (b) the wall-clock arrival-time difference between the submitted block and its parent block (`current_block.arrival_time − parent_block.arrival_time`) is less than the chain-config-defined inter-block creation wait time, the Tier 3 evaluation soft-fails in deferred mode. The local mempool's contents are NOT consulted for this check: the rule applies whether the mempool currently holds additional fitting transactions or is empty — pacing enforcement is independent of the local mempool snapshot, because mempool content can change during the wait window (new transactions may arrive, existing ones may become evaluable), and a uniform wait disciplines block-creation timing across all creators regardless of their local mempool state at submission time: the block is NOT promoted to Active, FR5 deletion-and-reversion is NOT triggered, the block remains in durable storage at its highest sub-Tier-3 status (Stored or Connected, whichever Tier 1 / Tier 2 admitted), and the FR10 classification returned to the caller is Deferred carrying `remaining_wait_time = inter_block_creation_wait_time − (current_block.arrival_time − parent_block.arrival_time)`. After the caller-driven timer event for `remaining_wait_time` elapses (per FR46), the block is re-evaluated; on success it transitions to Active and the caller re-disseminates it onto the network. The deferred soft-fail is intentional pacing enforcement, not provable invalidity, and is therefore distinct from every other Tier 3 failure mode. Failure of any Tier 3 gating check OTHER THAN the block-creation pacing rule during chain-switch reconciliation triggers FR5 deletion-and-reversion on the offending candidate block; failure during the FR3 processing pass triggers the same FR5 path. Tier 3 chain-switch reconciliation applies only to candidates whose divergence point `D` satisfies `D ≥ S_tail + (W − H)`, where `W` is the `snake_chain` length, `H` is the verification horizon size per FR58, `S_tail` is the current active-chain tail sequence, and `S_head` is the current active-chain head sequence; this ensures the `D − W` historical reference block needed for the candidate's `snake_chain`-preservation validation is locally retained. A divergence with `D ∈ [S_tail, S_tail + (W − H) − 1]` falls in the deep zone and is handled by the full-reconstruction path defined in FR58, not by in-place Tier 3 reconciliation. Triggers that depend on chain-config-derived values — including block-size limit (`MAX_BLOCK_SIZE`), chain-config compliance, custodian-fee-derived rules, anti-capture parameters `vote_scale` and `vote_interest`, approval-majority threshold, and any other check whose outcome is governed by a `configuration_module` accessor that depends on chain-config content — produce Invalid classification (and downstream deletion) only after the chain-configuration is durably locked per FR8 (post processing→ready transition) or per FR54 (genesis); while the chain-configuration is only tentatively loaded per FR8's tentative phase, a tentative-only failure of any such check shall not transition the block to Invalid, shall not be deleted from durable storage, and shall be re-evaluated whenever the tentative is replaced per FR8's mismatch path or whenever the durable lock is performed. Implicit transport- and storage-bounded block-size ceiling: even before the chain-config-derived `MAX_BLOCK_SIZE` becomes evaluable (i.e. during collecting state and during the FR8 tentative-only phase), every block reaching this Tier 1 surface has already passed through the radio layer's fragment-reassembly buffer (per FR61) and has been admitted into durable storage's bounded admission path (per FR16 and the storage layer's own structural limits). Both surrounding subsystems impose their own bounded buffers and refuse byte streams that exceed their compile-time / configuration-time capacity, so the blockchain module never observes a block whose serialized size exceeds the smallest of those external bounds. This implicit ceiling applies in every lifecycle state and is the structural reason the blockchain module does not need to enforce its own pre-chain-config block-size hard ceiling at Tier 1; the chain-config-derived `MAX_BLOCK_SIZE` check resumes as soon as the chain configuration is durably locked. Status transitions: Stored → Connected when ancestry resolves to the active chain and every applicable Tier 2 check passes; Connected → Active via FR23 chain-switch reconciliation success or FR35 forward-extension on the active head; Stored → Active in one atomic step via FR3 processing-pass success on the candidate; Active → Connected via FR23 chain-switch demotion of the block's branch to side-branch status (the block remains valid but its Tier 3 verification against the new active chain is stale-but-not-falsified, and Active re-promotion requires fresh Tier 3 verification on the next chain-switch event); Stored → [deleted, Invalid classification] on Tier 1 gating failure, or on FR8 durable-lock chain-config mismatch detection; Connected → [deleted, Invalid classification] on Tier 2 gating failure; Active → [deleted, Invalid classification] only via FR3 / FR23 Tier 3 gating failure with FR5 deletion-and-reversion or via FR57 capacity-pressure eviction (rare). Invalid is a terminal classification, not a stored status: no block in the retained block-tree carries Invalid status; entry into the Invalid classification is followed atomically by removal from durable storage and from the retained block-tree per the corresponding deletion rule, with transitive descendant deletion per FR5 (every transitive descendant of a deleted block — every block whose `previous_hash` chain passes through it — is also deleted, since `previous_hash` is immutable and a block has exactly one parent link, so reconnection is not possible). Storage deletion remains bounded to these paths (Tier 1 / Tier 2 / Tier 3 gating, FR5, FR8, FR17, FR19 chain_heads-eviction, FR57); no other deletion path is authorized. Callers shall not treat any pre-Active status (Stored or Connected) as ready-state confirmation: the local query surface (FR40-series) shall continue to report such blocks as not-yet-confirmed. Signature verification is performed as a direct cryptographic check, deterministic in its `(message, signature, public-key)` inputs, so it preserves FR63 replay determinism without any memoization. (An earlier revision specified a fixed-capacity signature-verification cache here; it was removed by design — block-tree `(sequence, block_hash)` duplicate detection per FR11 already prevents duplicate-arrival re-verification before Tier 1 runs, and the residual same-object Tier 1 / Tier 3 / chain-switch re-verification is expected-rare given deterministic creator selection, so the cache did not justify its RAM cost.)

### Block & Transaction Intake
- FR10: For every block submitted through the intake surface (from the radio layer, the local interface, or any other caller), the blockchain module shall assign exactly one of the following classification outcomes, deterministically derived from the block bytes and the current authoritative state: Accepted-new — the block is structurally parseable, is not already present in durable storage or the retained block-tree, and does not satisfy any out-of-snake-chain-window condition per FR60 or any exact-evidence unacceptability condition per FR16. The block has been stored per FR16 and has entered staged validation per FR9 at the Stored status (or higher, when ancestry, the creator key, and further semantic checks are already evaluable against local knowledge at the moment of intake). Already-known — the block's `(sequence, block_hash)` identity matches a block already present in the in-memory retained block-tree per FR11. The block is not re-stored, not re-advanced through FR9, and not forwarded into any further intake processing. Invalid-evidence — the block carries exact evidence of unacceptability per FR16, specifically: (a) parsing failure — the byte stream does not conform to any known block payload structure; (b) ready-state direct-active-chain-extension signature invalidity — the block's `previous_hash` equals the current active-chain head hash, the creator's public key is known via the current active `snake_chain`, and the block signature verifies as invalid against that key; (c) ready-state chain-config content mismatch — the block is a chain-config block whose configuration content does not match the durable-locked chain configuration per FR17; or (d) any other exact-evidence refusal defined by FR16, including chain-config content-signature failure against `node_zero_public_key`, `configuration_module` rejection of chain-config content, deviation-branch creator-exclusivity violation, or any FR69 node-zero trust-anchor mismatch. The block is not stored and is not added to the block-tree. Out-of-Snake-Chain-Window — the block's sequence cannot coexist with any locally retained active-chain block within a single `snake_chain` window per FR60 (either `S_new ≥ S_head + W` or `S_new < S_tail`). The block is not stored and is not added to the block-tree. The forward case (`S_new ≥ S_head + W`) additionally triggers the `long-disconnect-detected` structured log record per FR60; no other externally visible module state changes. Deferred — the block has passed Tier 1 intake gating per FR9 / FR16 and has been admitted to durable storage per FR16 (with FR9 status Stored or Connected, whichever Tier 1 / Tier 2 admitted), but the Tier 3 active-promotion evaluation has soft-failed under the FR9 block-creation pacing rule defined below in FR9 — i.e., the block's payload is below the chain-config-defined minimum block-fill threshold AND the parent-to-current block-arrival-time difference is below the chain-config-defined inter-block creation wait time (regardless of whether the local mempool currently holds additional fitting transactions). The block is NOT promoted to Active and is NOT subject to FR5 deletion-and-reversion (the soft-fail is a pacing enforcement, not provable invalidity). The response carries `remaining_wait_time = inter_block_creation_wait_time − (current_block.arrival_time − parent_block.arrival_time)` so that the caller — in MoonBlokz's current architecture, the radio layer per FR61 — can schedule a timer event that triggers re-evaluation after the wait elapses (per FR46); on the timer-triggered re-evaluation, if the block now passes Tier 3 (the pacing condition has elapsed, or the intervening chain state has otherwise resolved the soft-fail), it transitions to Active and the caller re-disseminates it onto the network. The classification shall be deterministic: two submissions of identical block bytes against identical current authoritative state shall always return the same outcome, and the outcome shall not depend on transport origin (radio layer vs. local interface). The response shall carry only the classification outcome. When the classification is Accepted-new, the response may additionally include (i) a single support message produced per FR12 if all FR12 eligibility conditions hold for the accepted block, (ii) a single re-dissemination transaction selected per FR13 if the accepted block is also promoted to the active chain as part of the same intake event and FR13's mempool condition holds, and/or (iii) a single newly-created block emitted per FR45 if the accepted block's promotion to the active chain establishes the local node as the next block's expected creator per FR44 (or as an eligible fallback creator per FR44 grace-period expansion, where applicable) and all FR45 trigger conditions for that creation type are simultaneously satisfied at the moment of intake — i.e., either an ordinary transactional block (mempool fill threshold reached, or external timer event with at least one eligible mempool transaction), or an essential `snake_chain` replay block (chain-config replay per FR49, balance replay per FR50, or zero-input UTXO carry-forward per FR51) emitted without waiting whenever a tail-drop replay obligation is pending. The newly-created block, the support message, and the re-dissemination transaction are independent optional response components — any subset of them may be present in a single Accepted-new response, including all three together. No other descriptive payload (no parent-missing reason, no current FR9 validation stage, no rejection reason, no log record reference) shall be returned, consistent with the minimal-response convention applied uniformly to both block- and transaction-submission events in this FR. Callers shall not observe any classification outside the closed set above. For transaction-submission events (also from the radio layer or the local interface), the blockchain module shall apply an analogous response convention: exactly one classification outcome from the FR14 set (Accepted-to-mempool, Already-confirmed, Duplicate-in-mempool, Deferred, or Rejected) shall be returned, the response shall carry only this status value and no additional descriptive payload (no confirming sequence, no prior-entry reference, no deferral reason, no rejection reason), so that callers in the constrained embedded environment do not have to allocate or process supplementary outcome fields, and callers shall not observe any outcome outside this set in ready state. In collecting state and in processing state, the only response observable by callers for a transaction-submission event is the not-ready indication defined in FR14 / FR1; the FR14 classification set is not available in those states.

  **Implementation annotation (architecture 2026-06-17):** The block-intake classification outcomes correspond to the blockchain `ReceiveBlockOutcome` enum variants defined in `intake.rs` (single-outcome scheduling-pull pattern — exactly one variant per call):
  - `Accepted-new` → `AcceptedSilently` (storage-only, no outbound) or one of the `AcceptedAndSend*` variants: `AcceptedAndSendBlock(BlockView)` for FR26 relay; `AcceptedAndSendSupport(SupportView)` for FR12 deviance support; `AcceptedAndSendReDisseminatedTx(TransactionView)` for FR13 re-dissemination; `AcceptedAndSendNewBlock(BlockView)` for FR45 chained creation; `AcceptedAndSendParentRecoveryRequest(ParentRecoveryRequest)` for FR19 missing-parent.
  - `Already-known` → `DuplicateKnown`.
  - `Invalid-evidence` → `Rejected(RejectReason)` with a granular `RejectReason` enum (signature invalid, chain-config mismatch, FR69 trust-anchor violation, etc.).
  - `Out-of-Snake-Chain-Window` → `Rejected(RejectReason::OutOfWindow)`.
  - `Deferred` → `Deferred { remaining_wait_time_ms }`.
  An analogous mapping applies to transaction-submission events via `ReceiveTransactionOutcome` enum (`AcceptedToMempool / AlreadyConfirmed / DuplicateInMempool / Deferred { reason } / Rejected(RejectReason)`).
- FR11: A submitted block is treated as already known when its `(sequence, block_hash)` identity matches a block currently present in the in-memory retained block-tree, which is the single authoritative duplicate-detection index. The blockchain module shall perform the duplicate check as one in-memory lookup against this index — keyed by `(sequence, block_hash)` — and shall not consult durable storage as a separate source: by construction the in-memory block-tree is a complete view of every durably retained block (it is reconstructed from durable storage at module startup per FR59 and kept consistent with durable storage on every subsequent admission, deletion, or eviction). On a match the module shall return an `Already-known` outcome to the caller and shall not re-store the block or forward it into further intake processing. This outcome enables the radio layer to avoid redundant re-forwarding of already-known blocks.
- FR12: When the blockchain module accepts a submitted block whose creator is not the top entry of the current creator-order — i.e. a deviating candidate — and the block is structurally parseable, connected, and signature-verified, the module shall evaluate whether the local node is eligible to endorse the deviation and, if so, produce a signed support message addressed to the deviating block's proposer. Eligibility and message generation follow the rules of ADR-015, with the concrete formulas restated here normatively (so that an implementation can verify them directly against the PRD without consulting the ADR). Active-node set `A` — every node that has been the creator of at least one block or transaction within the current active `snake_chain`; `A` is derived from active-chain state alone (per ADR-003 / ADR-008) and is bounded by `snake_chain_length`. Subgroup-selection seed — `seed = H(snake_chain_tail_hash ‖ proposer_node_id ‖ proposed_sequence)`, where `snake_chain_tail_hash` is the hash of the tail block of the local active chain at approval-evaluation time, `proposer_node_id` is the deviating block's creator, and `proposed_sequence` is the deviating block's sequence; no proposer-controllable content (block contents or hash) enters the seed, preventing grind attacks. Per-node ordering key — for every node `n ∈ A`, `node_value(n) = (H(seed ‖ node_id(n)) mod 2³²) · 2³² + node_id(n)`, a deterministic 64-bit value with the upper 32 bits derived from the seeded hash and the lower 32 bits `node_id(n)` as a deterministic tiebreaker. Subgroup size — `m = min(2 · required_support − 1, |A|)`, where `required_support` is obtained from the `configuration_module`; the first term makes `required_support` exactly a 50%+1 majority inside the subgroup, and the `|A|` cap covers shrunken-network cases. Subgroup membership — the subgroup is the `m` nodes of `A` with the smallest `node_value`; growing `m` only adds members (monotonicity), preserving earlier selections. Both `snake_chain_tail_hash` and `A` are resolved against the local active chain at the moment of evaluation. The eligibility checks producing the support message are then: Grace-period eligibility: the block's creator must belong to the eligible-creator set admitted by the current grace-period expansion window (Algorithm 5). If the expansion window has not yet reached the creator's rank in the creator-order, no support message is produced. Active-node membership: the local node must itself be in `A`. Deterministic subgroup membership: the local node's own `node_value` must rank among the `m` smallest values in `A`. Non-conflict: the local node must not have already issued a support message for a different deviating candidate at the same `proposed_sequence` with the same proposer. Replay-completion: every mandatory `snake_chain` essential-state replay obligation that has come due on the local active chain shall already have been satisfied at the moment of evaluation — i.e., the current active-chain tail block shall not be itself replay-pending (per FR48 chain-config replay, FR50 balance replay, or FR51 zero-input UTXO carry-forward). The local node shall not emit a support message while any tail block is awaiting its replay obligation, because the supporter's chain state would otherwise be derived from a tail-window not yet brought into structural `snake_chain` preservation, and the support signature would commit to a `snake_chain_tail_hash` whose replay-derived state is not yet self-consistent. When this check fails, no support message is produced; the check is naturally re-evaluated whenever new content advances on the local active chain (the next intake event refreshes the eligibility evaluation), so the support message is emitted as soon as the outstanding replay obligation is satisfied — provided the other eligibility checks continue to hold. When all of the above hold, the block-intake outcome returned to the caller shall include a support message consisting of the local node's signature over the canonical support-message content (`proposer`, proposed sequence, deviating block hash), produced by the blockchain module for transport by the radio layer. When any condition fails, no support message is produced, and no reason code is returned to the caller (consistent with the minimal-response convention). Issuing a support message shall not by itself alter active-chain selection or branch value. A locally created deviation block may already extend the current active chain and update active-chain state per FR45 / FR28, but an approval-less deviation-bearing branch remains branch-value-weaker than the corresponding normal branch and therefore cannot overtake a competing normal branch under FR21; the associated approval evidence block defined by FR27–FR29 is the mechanism that can later make the deviation-bearing branch competitive in retained-branch comparison. Evidence-block `supporter_vote_sum` formula: when the proposer of the deviating block constructs the matching approval evidence block per FR27, the `supporter_vote_sum: u64` payload field shall be computed by the closed-form formula `supporter_vote_sum = (m / 2 + 1) · deviance_creator_vote + original_creator_vote` (integer division for `m / 2`), where (i) `m` is the subgroup size defined above; (ii) `deviance_creator_vote` is the `vote_count` of the deviation block's creator at sequence `proposed_sequence − 1`, projected against the candidate chain that the deviation block extends; (iii) `original_creator_vote` is the `vote_count` of the node that would have been the creator at `proposed_sequence` in the absence of the deviation — i.e., the top entry of the creator-order projection at sequence `proposed_sequence − 1` whose deviation triggered this approval workflow — projected against the same candidate chain at sequence `proposed_sequence − 1`. This closed-form formula deliberately does not depend on which specific subset of subgroup members actually signed: the multiplier `(m / 2 + 1)` is a fixed function of the subgroup size determined by the candidate chain at the deviation point, and the remaining inputs are likewise fixed by chain projection. Two security consequences follow. (a) Forward dominance over the normal branch: the deviation-bearing branch's combined contribution at the deviation point — `deviance_creator_vote + supporter_vote_sum = (m / 2 + 2) · deviance_creator_vote + original_creator_vote` — strictly exceeds the corresponding normal-branch per-block contribution `original_creator_vote` at the same sequence (since `deviance_creator_vote ≥ 1` for any registered node and `m / 2 + 2 ≥ 2` for any non-empty subgroup), so a later normal-branch supplement at the same sequence cannot retroactively overtake the deviation-bearing branch under FR21. (b) No proposer-controlled value drift: because the result depends only on `m`, `deviance_creator_vote`, and `original_creator_vote` — all fixed by the candidate chain at sequence `proposed_sequence − 1` — the proposer cannot construct two competing deviation continuations carrying different `supporter_vote_sum` values by choosing which signers' aggregated signatures are admitted into the evidence beyond satisfying `required_support`.
- FR13: When a block accepted into the active chain per FR10 was delivered through the block-intake surface from an external caller (in MoonBlokz's current architecture, per FR61, this caller is the radio layer) and the accepted block contains at least one ordinary (non-replay) transaction — i.e., at least one node-transfer (`type=1`), registration (`type=2`), or non-zero-input complex transaction (`type=3`) — the blockchain module shall examine whether its mempool contains any transaction satisfying both of the following: (a) its fee-per-byte value (as defined in FR45) is higher than the lowest fee-per-byte value among the ordinary transactions included in the accepted block; and (b) it would have fitted into the accepted block under the `MAX_BLOCK_SIZE` budget — i.e., the mempool transaction's serialized size, added to the actually-included payload size of the accepted block, would not have exceeded `MAX_BLOCK_SIZE`. The size-fit check is operationally meaningful primarily for complex transactions (`type=3`), whose serialized size is variable depending on the input/output count; for fixed-size node-transfer (`type=1`) and registration (`type=2`) transactions the size-fit check resolves trivially in nearly all cases. A mempool transaction qualifies for re-dissemination only when both conditions hold — meaning the block creator could in principle have selected it over the actually-included lowest-fee-per-byte transaction without exceeding the block-size budget. Replay-only blocks — i.e., balance blocks (`payload_type=2`), chain-config blocks (`payload_type=3`), approval evidence blocks (`payload_type=4`), and transaction blocks (`payload_type=1`) whose payload contains only zero-input UTXO carry-forward complex transactions per FR51 — shall not trigger this re-dissemination heuristic, since their content was not selected from the mempool's fee-competition surface and the lowest-fee-per-byte rationale (some other-node transaction was preferred over a still-disseminating one) does not apply. If at least one such qualifying transaction exists, the blockchain module shall assume it is not sufficiently disseminated in the network, shall select one of the qualifying transactions via a non-deterministic random choice (the per-call random source is implementation-defined and need not be seeded, replayable, or consistent across nodes — see rationale below), prioritizing the local node's own transactions according to FR45's ownership tie-break rule if any such qualifying transactions exist, and shall return the selected transaction as a response addendum alongside the FR10 classification delivered to the submitting caller. Rationale for non-deterministic selection: when multiple under-disseminated transactions are competing in the local mempool, two nodes that hit this re-dissemination path simultaneously should ideally pick *different* transactions, so that the aggregate network surface covers a broader subset of pending mempool content — this is the exact opposite of a seeded-determinism guarantee. FR63's determinism requirement is scoped to chain-logic state transitions (block validation, branch-value computation, active-chain selection, replay determinism) and is intentionally NOT extended to mempool re-dissemination selection: mempool surface broadening favors divergent local choices, while chain logic favors convergent global agreement, and these are incompatible goals served by different selection mechanisms. The block-intake API signature is uniform for all external callers, and the FR13 addendum is emitted on the same terms regardless of caller identity. The addendum is operationally meaningful only for callers that perform network re-dissemination; in MoonBlokz's current architecture the radio layer is the only such caller and uses the returned transaction to re-disseminate it on the network. Callers that do not perform re-dissemination (for example, the local interface, if it ever submits an externally originated block) may observe the addendum and shall discard it without acting — this is an expected no-op and not a defect on either side. FR13 does not apply to blocks accepted through the local node's own creation path per FR45: that path has no external caller, no FR10 response is generated, and the block's content already reflects the local mempool's own prioritization, so re-dissemination prompting would be meaningless.
- FR14: Transaction intake per this FR shall be served only while the module is in ready state. In collecting state (per FR1) and in processing state (per FR3, for the duration of the reconstruction pass), every transaction-submission event shall receive a not-ready indication; no classification is performed, no mempool admission is attempted, no mempool entry is created, and no outcome outside the not-ready indication is returned. The remainder of this FR defines the classification rules that apply to transactions submitted while the module is in ready state: For every submitted transaction, the blockchain module shall assign exactly one of the following classification outcomes, deterministically derived from current authoritative state and from the transaction-validity rules defined in the blockchain algorithm document: Accepted-to-mempool — the transaction satisfies all structural and semantic validity checks applicable to its type, and the per-type acceptance-window rule below holds. Acceptance-window rule per transaction type — `W` denotes the configured `snake_chain` window size per FR56 throughout this FR. Let `S_tail` denote the current active-chain tail sequence, i.e. the oldest block currently present on the active chain. When the chain is shorter than `W`, `S_tail` is the chain start (sequence `0`), not a negative extrapolation of `active_chain_head_sequence − W`. The `anchor_sequence` acceptance-window's lower bound coincides with `S_tail` per FR56's correctness rationale, so no separate acceptance-window parameter exists: (i) Node transfer (`type=1`): the transaction's transaction-level `anchor_sequence` lies within the one-sided acceptance window relative to the current active-chain head — the window has no upper bound (`anchor_sequence` may equal or exceed the current head sequence) and is constrained only from below by the active-chain tail (`anchor_sequence ≥ S_tail`). (ii) Registration (`type=2`): registration carries no `anchor_sequence`; the acceptance-window rule does not apply. Anti-replay for registration is structural via the `new_public_key` global-uniqueness invariant — a single public key may be registered only once on the active chain — and is checked under the Already-confirmed / Rejected / Duplicate-in-mempool clauses below. (iii) Complex transaction (`type=3`): every balance input's `anchor_sequence` shall lie within the same one-sided acceptance window (`balance_input.anchor_sequence ≥ S_tail`); a violation against any one balance input's `anchor_sequence` is sufficient to fail the rule. UTXO inputs carry no `anchor_sequence`; their freshness is bounded structurally by the `snake_chain` window itself — every referenced UTXO output's `block_sequence` shall be within the active `snake_chain` window (`block_sequence ≥ S_tail`), and the spent-bit invariant of ADR-016 enforces single-spend semantics in place of `anchor_sequence`. A complex transaction with zero balance inputs and only UTXO inputs is therefore not subject to any `anchor_sequence` clause but remains subject to the UTXO `snake_chain`-window rule. The block-inclusion rule that the including block's sequence must be strictly greater than every applicable `anchor_sequence` (per FR6 / Algorithm 13) is enforced at validation time, not at mempool intake. The transaction is added to the mempool in compacted form. A transaction that spends the same UTXO as another transaction already in the mempool, or is otherwise a mempool-level duplicate-spend candidate, is still accepted: the mempool may legitimately hold such competing variants, and final single-spend enforcement happens at block inclusion and active-chain selection, not at mempool intake. Already-confirmed — an identical or functionally equivalent transaction is already present in a block on the current active chain. Functional-equivalence (uniqueness key) per type: node transfer — identical `(initializer, receiver, amount, anchor_sequence, comment)` tuple; registration — identical `new_public_key` (a public key may be registered only once); complex transaction — identical input set, where the input set is the ordered list of all UTXO inputs (each by `(block_sequence, output_index)`) and all balance inputs (each by its full bytes including `(initializer, anchor_sequence, amount, comment)`), with the entire set required to match for equivalence (any divergent input breaks equivalence). The transaction is not added to the mempool. Duplicate-in-mempool — a transaction sharing the same per-type uniqueness key as above with an entry already in the mempool is treated as a duplicate and is not added again. Deferred — the transaction is structurally parseable but cannot yet be classified definitively because required context is missing. Examples include: the claimed initializer is not yet known on the local active chain (the registering transaction may still arrive); a complex transaction references a UTXO whose creating transaction is not yet on the local active chain; a registration's key-uniqueness cannot yet be evaluated because the full node roster on the active chain is incomplete; the transaction's `vote` field references a `node_id` that does not appear in the current active-chain node roster — this case is always treated as Deferred (never Rejected), regardless of how complete the local roster currently appears, because a future registration transaction may still establish that `node_id` on the active chain. The transaction is held in the mempool with an internal not-yet-evaluable marker; its acceptance-window expiry behavior follows the per-type rule above and is enforced by the mempool-aging tick of FR46, and on becoming evaluable it is promoted to an ordinary mempool entry. Rejected — the transaction violates the validity rules in a way that makes it unacceptable against currently known authoritative state and cannot become valid by the arrival of additional chain information. Examples include: parsing failure; invalid signature verified against an already-known key; no-self-vote rule violation per FR6; registration `new_public_key` colliding with a public key already registered to another node on the current active chain (a genuine key-uniqueness conflict, as opposed to an inability to evaluate uniqueness — the latter is Deferred); `new_key_signature` failure; total inputs less than total outputs; node-transfer `anchor_sequence` below the accepted-window lower bound (`anchor_sequence < S_tail`); any complex-transaction balance input whose `anchor_sequence` falls below the same lower bound; any complex-transaction UTXO input referencing a `block_sequence` below the active `snake_chain` window's tail (`block_sequence < S_tail`). There is no upper-bound rejection rule for `anchor_sequence`, since a future-dated anchor remains legally includable in any later block whose sequence exceeds it. The classification shall be deterministic: two submissions of the same transaction bytes against the same current authoritative state shall always return the same outcome, and the outcome shall not depend on transport origin (radio layer vs. local interface).
- FR15: Whenever a new block is accepted into the active chain or the authoritative interpretation changes through chain-switch reconciliation, the blockchain module shall re-evaluate every mempool transaction currently marked Deferred against the newly available context. The re-evaluation has exactly two outcomes per transaction: (i) Promoted — the transaction is now fully classifiable AND meets FR14's Accepted-to-mempool conditions against the current active chain; it is removed from its internal not-yet-evaluable marker and converted to an ordinary mempool entry, becoming visible to the consumer surfaces of the mempool (FR45 block-creation content selection, FR47 mempool replenishment exchange, and FR13 re-dissemination addendum on block intake). (ii) Remains Deferred — every other case, including newly-classifiable-but-currently-unacceptable conditions such as the transaction having become Already-confirmed on the active chain, its `anchor_sequence` falling outside the active-chain acceptance window, the vote-target node still absent from the active-chain roster, a referenced UTXO no longer in active `snake_chain` scope, or any other FR14 outcome other than Accepted-to-mempool. The FR15 re-evaluation shall NEVER reclassify a transaction to Rejected and shall NEVER remove the transaction from the mempool, because every Deferred-time unacceptability condition above can become satisfied again under a later chain-switch reconciliation (a different candidate chain may carry a different node roster, a different `S_tail`, different UTXO scope, or a different inclusion history); preemptively discarding such mempool content would lose potentially useful pending transactions. The Deferred marker therefore functions as a "currently-excluded-from-consumer-surfaces but retained" filter: only Promoted (ordinary) mempool entries are exposed to FR45 / FR47 / FR13; Deferred entries remain in mempool storage and are re-considered on every subsequent FR15 trigger. Capacity-pressure eviction per FR31 / FR33 and the per-type acceptance-window expiry rules at FR14 intake time are independent removal paths and are unaffected by this FR — they may still remove Deferred entries when storage budgets or intake-time window-expiry conditions demand it.
- FR16: The blockchain module shall store each incoming block in the storage module unless it has exact evidence that the block is incorrect. The canonical exhaustive list of intake-time exact-evidence forms is the FR9 Tier 1 gating-check set: failure of any FR9 Tier 1 gating check (other than the explicitly opportunistic side-effect signature steps of FR9) constitutes intake-time exact evidence and the block is not stored. The most distinctive forms — listed here for cross-reference convenience but not narrowing the FR9 Tier 1 set — include: parsing failure; ready-state direct-active-chain-extension creator-signature invalidity (the block's `previous_hash` equals the current active-chain head hash, the creator's public key is derivable from the current active chain, and the block signature verifies as invalid against that key); chain-config content-signature invalidity (FR7 verifies against the FR69 trust anchor `node_zero_public_key`, evaluable for every chain-config block at intake); configuration-module rejection of chain-config content per FR8; ready-state chain-config content mismatch per FR17; deviation-branch creator-exclusivity violation per FR27; and FR69 node-zero trust-anchor mismatches — namely, a registration transaction whose `new_node_id == 0` and `new_public_key ≠ node_zero_public_key`, a balance block carrying a NodeInfo entry with `owner == 0` and `public_key ≠ node_zero_public_key`, and a chain-config block whose FR7 content-signature fails to verify against `node_zero_public_key`. Beyond these explicitly-named cases, the FR9 Tier 1 set additionally includes (without limitation): unsupported header `version`; declared `payload_type` not matching any known payload schema; intake-time `block.sequence > tx.anchor_sequence` violation for any node-transfer transaction (and the analogous balance-input rule for complex transactions); the no-self-vote rule of FR6 (excluding block #0 per FR54 bootstrap-only exception (i)); the structural input/output amount summation `sum(declared input amounts) ≥ sum(declared output amounts)` for complex transactions whose UTXO inputs are locally resolvable at intake; `new_key_signature` invalidity on a registration transaction; and (in ready state with durable-locked chain-config) `block size > MAX_BLOCK_SIZE` and active-`snake_chain`-window membership per FR60. The FR9 Tier 1 set is normative; this enumeration is illustrative only and shall not be read as narrowing it. Signature-invalidity decisions outside the direct-active-chain-extension case and outside the FR69 trust-anchor cases are not made at intake time — they are deferred to the FR9 Tier 3 chain-switch reconciliation path or the FR3 processing pass against the candidate-side public-key projection. Additionally, blocks whose sequence cannot coexist with any locally retained active-chain block within a single `snake_chain` window are silently discarded per FR60, without entering durable storage.
- FR17: Once the chain-configuration is durable-locked per FR8 or per FR54, every subsequently received chain-config block (`payload_type=3`) whose content differs byte-by-byte from the durable-locked configuration shall be silently discarded at the intake surface: such a block shall not enter durable storage, shall not be added to the block-tree, and shall not advance through the staged-validation progression of FR9. This content-mismatch detection constitutes exact evidence of invalidity under FR16 and applies uniformly to original and replay chain-config blocks. The module shall emit a structured `chain-config-mismatch-discarded` log record per FR64 carrying the discarded block's hash, declared sequence, and creator identifier. Reconciliation across a chain-config content boundary is out of scope and follows the same operational permanence as the long-disconnect condition of FR60.

### Chain Knowledge, Branching & Reconciliation
- FR18: The blockchain module shall maintain a bounded block-tree of every retained block together with the relationships needed to reconstruct ancestry, including for each block at minimum the following metadata: its sequence; its block hash (mandatory — it serves as the canonical identity of the block, the lookup key into the in-memory duplicate-detection index per FR11, and the target of every parent reference from descendant blocks); a parent reference resolving to its immediate ancestor in the block-tree (the implementation MAY satisfy this by retaining the wire-level `previous_hash` field byte-for-byte, or equivalently by an internal data-structure pointer / parent-index reference within the in-memory block-tree representation — both are acceptable as long as ancestry recovery and chain reconstruction remain deterministic and bounded; the wire-level `previous_hash` is the canonical ancestry signal in serialized form, but its in-memory representation is implementation-defined); creator identifier; payload type; the current block status drawn from the three-status state machine defined in FR9 (Stored, Connected, or Active); a single-bit `is_on_active_chain` flag indicating whether this block currently lies on the active chain (used by FR19 / FR23 to make the "does this branch reach the active chain?" check O(walk-back-until-flag-true) rather than scanning the entire active chain — implementations may store this as a single bit in a packed metadata word); and a `head_ref_count` field per FR19 (an unsigned integer branch-count — the number of distinct child-edges of this block that lead toward a `chain_heads` entry, operatively equal to the block's out-degree toward heads — sized to hold values up to `chain_heads_max_capacity`; FR19 is the authoritative definition and records why the superseded path-count gloss is inconsistent with the eviction rule) — used by FR19's chain_heads-eviction walk to detect blocks that may be deleted (count == 0 after decrement) versus blocks that remain shared with another head (count > 0). In addition, the module shall retain the local wall-clock arrival timestamp at least for every chain head block (the current active-chain head and any retained side-branch heads) so that the FR9 Tier 3 block-creation pacing rule (and any other rule that consumes the parent-to-current arrival-time difference, e.g. FR46 timer-event scheduling and FR4 Deferred-outcome `remaining_wait_time` computation) can be evaluated deterministically against the parent's recorded arrival timestamp; an implementation MAY retain the arrival timestamp for every block in the block-tree if its storage budget allows. The Invalid classification of FR9 is not a stored status: a block entering Invalid is atomically removed from the block-tree per the corresponding deletion path. Storage of the blocks themselves follows FR16.
- FR19: Operating principle (high-level summary). The blockchain module observes the block-tree's tip set and tracks every tip as a `chain_heads` entry. Stored heads (whose ancestry does not yet reach the active chain) carry a tail-point — the lowest-sequence block on their branch whose parent is missing — and a per-head `last_request_timestamp`. A throttled scheduler runs at chain-config-defined ticks; on each tick, the Stored head whose per-head retry interval has elapsed longest ago wins and a single parent-recovery request is emitted toward that head's tail-point's missing parent (head_sequence and head_block_id break ties for FR63 replay determinism). When the missing parent arrives, the tail-point migrates one block deeper, possibly merging the branch into another head's ancestry: if the merge reaches the active chain the head transitions to Connected; if it merges into another Stored head's branch both heads share a deeper tail-point. Per-block `head_ref_count` tracks shared-ancestry membership, so that bounded chain_heads-capacity-driven eviction (lowest non-active `head_sequence` wins) unwinds only blocks that no other head still uses. Wall-clock arrival timestamps are deliberately NOT used in any selection or eviction tie-break (they are not deterministic across nodes); all selection criteria are derived from chain-content (head_sequence, head_block_id) for FR63 replay determinism. The detailed rules below define the exact data fields, scheduling parameters, mutation events, eviction algorithm, and bootstrap behavior. To recover missing-parent ancestry deterministically and within bounded resources, the blockchain module shall maintain an explicit `chain_heads` table that indexes every block-tree tip — every block whose hash is not the parent reference of any other retained block — regardless of its FR9 status (Stored, Connected, or Active). The table is bounded by the chain-config parameter `chain_heads_max_capacity`. Per chain_heads entry the module shall maintain at minimum: (a) the head block's hash; (b) the head block's sequence; (c) a `connected` cache flag indicating whether the head's ancestry resolves to the current active chain; (d) a tail-point cache (the lowest-sequence block on the head's branch whose parent reference does not resolve in the retained block-tree) — populated only for Stored heads; (e) a connection-point cache (the highest-sequence block on the head's branch that lies on the current active chain) — populated only for Connected/Active heads; (f) `last_request_timestamp` — the local wall-clock timestamp at which a parent-recovery request was last emitted for this head — populated only for Stored heads and initialized to the epoch (so that the first scheduler tick following head creation immediately schedules the initial request); and (g) `branch_value` — the FR21 incrementally-maintained relative branch value of this head against the active-chain tail `S_tail` — populated only for Connected and Active heads (Stored heads have no branch value because their ancestry is not yet resolved into the active chain); updated per FR21's mutation rules on head extension, on Stored→Connected transitions, on active-chain tail evictions, and on FR5 atomic recovery deletions; unchanged by FR23 chain-switch reconciliation. The active chain head is identified by a single global field `active_chain_head_id`; no per-head `active` flag is required (active membership = `head_block_id == active_chain_head_id`). Tail-point and connection-point are caches: they are recomputable from the block-tree structure at any time, and shall be invalidated and recomputed whenever block-tree mutations affect their values (block admission, FR23 chain-switch, FR5 deletion). To track block sharing across heads in bounded form, the block-tree shall additionally retain per block a `head_ref_count` field (an unsigned integer branch-count — the number of distinct child-edges of this block that lead toward a `chain_heads` entry (a head-tip counts its own edge), operatively equal to the block's out-degree toward heads and bounded by `chain_heads_max_capacity` (ratified 2026-07-12, Story 4.4; the earlier gloss "the number of `chain_heads` entries whose ancestry path includes this block" describes a *path-count*, which is inconsistent with the eviction "decrement, stop at count > 0" rule — see the fork-mutation note below for the maintenance and the eviction-safety argument)). The ref-count is structural — derived from the block-tree graph, not from active-chain selection — and is therefore unaffected by FR23 chain-switch reconciliation events. Parent-recovery scheduling rule. The chain-config parameter `parent_recovery_per_head_retry_interval` defines the minimum wall-clock period between two consecutive parent-recovery requests emitted for the same head. (Superseded 2026-07-12, Story 4.4: the earlier `parent_recovery_global_tick_interval` "wall-clock period at which the scheduler ticks" parameter is **removed** — under the AR4 scheduling-pull contract the module returns the *exact* next instant a request can be emitted as `NextCall::At`, computed as the later of the earliest Stored-head per-head eligibility and the FR46 global-emit-cooldown clearing, so a fixed periodic tick cadence is unnecessary; the bridge wakes only when a request is actually due.) On every scheduler tick the module shall enumerate every Stored head whose `last_request_timestamp + parent_recovery_per_head_retry_interval ≤ now()` (i.e. those whose per-head retry window has elapsed); among that subset the head with the smallest `last_request_timestamp` is selected (ties broken deterministically by smallest `head_sequence`, then by smallest `head_block_id` interpreted as a big-endian unsigned integer, matching FR2 / FR21 tie-break for FR63 replay determinism), and a single parent-recovery request shall be emitted to the radio layer carrying the head's tail-point block's parent reference (the missing parent's hash) and the claimed parent sequence (`tail_point.sequence − 1`). The selected head's `last_request_timestamp` is updated to `now()`. If no Stored head's per-head retry window has elapsed at the tick, the tick produces no request. At most one parent-recovery request is emitted per scheduler tick, regardless of how many heads have elapsed retry windows. Block-tree mutation events affecting chain_heads. (i) New-block admission via FR9 Tier 1 — when the block extends an existing chain_heads entry (its parent reference resolves to a current `head_block_id`), that head's `head_block_id` and `head_sequence` advance to the new block, the new block's `head_ref_count` is set to the number of heads whose ancestry passes through it (typically 1 for a non-forking extension), the head's cache fields are recomputed, and (if the head is Connected/Active) the head's `branch_value` is incremented by the new block's per-block value per FR21; if the admission to the Active chain head causes the snake_chain window to slide (i.e., `S_tail` advances), the dropped tail block's per-block value is subtracted from the `branch_value` of every Connected/Active chain_heads entry per FR21 (the tail is the common reference point for all branches' relative branch values); when the block introduces a fork (its parent reference resolves to a non-head block already in the tree), a new chain_heads entry is created with `head_ref_count` of the new block set to 1, while the fork-point block's `head_ref_count` is incremented by 1 (a genuinely new branch now passes through it) and its ancestors *above* the fork-point retain their existing ref-counts — this is the **branch-count / out-degree** maintenance the eviction rule below requires (ratified 2026-07-12, Story 4.4: the original "fork-point block and its ancestors retain their existing ref-counts" wording was eviction-unsafe, since evicting one fork arm would then delete the shared fork-point; `head_ref_count[b]` is the number of distinct child-edges of `b` that lead toward a head, so eviction's "decrement, stop at count > 0" back-walk is exactly correct); when the block's parent reference does not resolve to any block in the tree, a new Stored chain_heads entry is created with this block as both head_block_id and tail-point, `last_request_timestamp = 0`, and `head_ref_count` of this block = 1. (ii) Tail-pointing parent admission — when an incoming block X resolves the parent reference of an existing Stored head H's tail-point T (i.e., X is the missing parent), walking back from X along its parent reference chain, each visited block's `head_ref_count` is incremented by 1; the walk terminates either at H's new tail-point (a block whose parent reference does not resolve in the tree — H remains Stored) or upon entering a region of the tree already part of another head's ancestry (in which case H either transitions to Connected if the connection point lies on the current active chain — its tail-point cache cleared, connection-point cache populated, `last_request_timestamp` removed, and `branch_value` computed per FR21's Stored→Connected rule (walk from active head back to connection-point and forward to H) — or remains Stored if the connection is to another Stored head's branch, with H's tail-point updated to the merged branch's shared tail-point); the walk length is bounded by the `snake_chain` window. After the walk, H's cache fields are recomputed. (iii) FR23 chain-switch reconciliation — when the active chain switches, `active_chain_head_id` is updated; every block on the previous active branch above the common ancestor has its `is_on_active_chain` flag flipped to false during the FR23 backward walk, and every block on the new active branch above the common ancestor has its `is_on_active_chain` flag flipped to true during the FR23 forward walk (the flag is also flipped per FR9 status updates); every Connected/Active head's `connected` flag and connection-point cache are recomputed (each recomputation is O(walk-back-until-`is_on_active_chain==true`) on the head's branch, exploiting the per-block flag); a previously Connected head whose branch no longer reaches the new active chain demotes to Stored, has its tail-point cache populated, `last_request_timestamp` reset to 0 for immediate parent-recovery scheduling, and its `branch_value` cleared — an antecedent that cannot arise under FR23's own definition of reconciliation, which walks back to the **common ancestor** and forward from it, leaving that common ancestor on the active chain; since the connection check walks back to the *first* block with `is_on_active_chain == true`, a head that reached the previous active chain still reaches the new one through the common ancestor, at worst via a deeper connection point (ratified 2026-07-30, Story 5.5); `branch_value` of every still-Connected/Active head is unchanged (per FR21, since `S_tail` and per-block values are unchanged); `head_ref_count` values are not affected (structural — independent of active-chain selection). (iv) FR5 atomic recovery deletion — any chain_heads entry whose `head_block_id` is among the deleted blocks is removed from chain_heads; the deleted subtree's root's surviving parent becomes a childless tip and shall itself be indexed, per this requirement's rule that chain_heads indexes **every** block-tree tip (an unindexed tip is invisible to FR2 candidate selection, to parent recovery, and to eviction, so the FR5 phase-reversion requirement to re-evaluate the remaining block-tree would be unreachable for the shortened branch; retargeting one of the entries being removed satisfies this while preserving that branch's cached tail-point, missing-parent hash and recovery schedule — ratified 2026-07-30, Story 5.5); surviving heads whose ancestry passed through any deleted block have their cache fields invalidated and recomputed, and if a Connected head loses its active-chain connection it demotes to Stored with `last_request_timestamp` reset to 0 — an antecedent that cannot arise under this deletion rule, since an FR5 delete-set is the complete subtree of the deletion target and therefore no surviving head's ancestry can contain a deleted block (ratified 2026-07-30, Story 5.5; the conditional is retained as the general rule for any future authorized delete-set, but no driver is to be built for it). Bounded chain_heads eviction. When admitting a new chain_heads entry would cause `chain_heads.count > chain_heads_max_capacity`, the module shall evict the non-active chain_heads entry (whose `head_block_id ≠ active_chain_head_id`) with the smallest `head_sequence`; if multiple candidates share the smallest sequence, the tie is broken by smallest `head_block_id` interpreted as a big-endian unsigned integer (matching FR2 / FR21 tie-break for FR63 replay determinism). Eviction proceeds by walking back from the evicted head's `head_block_id` along the parent reference chain: for each block visited, `head_ref_count` is decremented by 1; if the resulting count reaches 0 the block is deleted from durable storage and from the retained block-tree (this is an authorized deletion path complementing FR5, FR16, FR17, and FR57); if the resulting count remains > 0 the block is shared with at least one other head and the walk terminates. The evicted chain_heads entry is then removed from the table. Bootstrap. When the module starts with an empty block-tree, `chain_heads` is empty and no parent-recovery requests are emitted; the first admitted block creates the first chain_heads entry. If it is the genesis block (sequence 0, no parent reference), the head is created with `connected = true` and (if it is the only block on the active chain) `active_chain_head_id` set to it; otherwise the head is created Stored with `last_request_timestamp = 0` and the next scheduler tick emits the initial parent-recovery request. Determinism. FR63 replay determinism is preserved because the scheduling and eviction tie-breakers are deterministic functions of block-tree state (head_sequence, head_block_id); `last_request_timestamp` is local-clock-derived and may differ across nodes by absolute value, but within a single replay log its relative ordering is reproducible from the recorded scheduler tick events. The eviction criterion does NOT consult arrival timestamps (which are non-deterministic across nodes); it uses head_sequence (deterministic from chain content) so that two nodes processing the same block-tree state evict the same head. Storage deletion remains bounded to the chain_heads-eviction path defined here together with FR5, FR16, FR17, and FR57; no other deletion path is authorized.
- FR20: The blockchain module shall represent and retain multiple candidate branches simultaneously within the bounded block-tree, tracking each branch via the FR19 `chain_heads` table — every block-tree tip is indexed there with its head metadata (head_block_id, head_sequence, connected cache flag, tail-point cache for Stored heads or connection-point cache for Connected/Active heads, and `last_request_timestamp` for Stored heads). Branch ancestry retention is bounded by the active `snake_chain` window per FR59 and the verification horizon defined therein: blocks older than `S_tail` (the active-chain tail sequence) are not required to be retained, and a branch's `chain_heads` entry is not required to resolve back to the genesis block — for non-genesis-anchored branches it is sufficient that the head's tail-point lies within the retained block-tree (per FR19 the tail-point may be a Stored head awaiting parent-recovery, and parent-recovery requests ascend only as far as the bounded retention allows; ancestor blocks that have fallen out of the `snake_chain` window are not pursued). The module shall not silently prefer, discard, or collapse side branches during normal intake — FR16's exact-evidence intake rejections, FR17's chain-config silent-discard, and FR59's out-of-snake_chain-window silent-discard remain the only intake-time refusals; silent removal of a side branch's blocks is permitted only via (i) FR19 chain_heads-eviction (lowest non-active `head_sequence` wins, with per-block `head_ref_count` protecting shared-ancestry blocks), (ii) FR5 atomic recovery deletion (processing-phase invalidity), (iii) FR8 durable-lock chain-config mismatch cleanup, or (iv) FR57 capacity-pressure eviction, each governed by its own normative rule. Block-tree mutation events affecting branch state — block admission, FR23 chain-switch reconciliation, and FR5 atomic recovery deletion — propagate to the FR19 chain_heads cache fields (`connected` flag, tail-point, connection-point) per FR19's mutation rules; the per-block `head_ref_count` is structural (block-tree graph based) and is unaffected by chain-switch. Branch-value-based comparison and selection among retained branches is governed by FR21 (branch-value computation) and FR23 (chain-switch reconciliation); FR20 is concerned only with the retention and tracking discipline, not with which branch wins.
- FR21: The blockchain module shall determine the currently authoritative (active) branch by computing **branch value** per Algorithm 8 from header / payload fields. Branch value is computed **only for Connected and Active chain_heads** (per FR19 / FR20); Stored heads have no branch value because their ancestry has not yet resolved into the retained block-tree's connected region — once a Stored head transitions to Connected, its branch value is computed and recorded. Branch value is a **relative quantity computed against the current active-chain tail (`S_tail`)** as the common reference point: it is the cumulative sum of per-block values from `S_tail` (exclusive) up to the head, where each block contributes its own per-block value to the sum. Because every Connected/Active head uses the same `S_tail` as its reference, branch_value comparisons across heads are well-defined despite being "relative" — the relative-vs-absolute distinction does not affect ordering. Per-block value is determined by the block's payload type: the value of a normal block equals its `consumed_votes` (header field); the value of an approval evidence block equals the value carried in its `supporter_vote_sum: u64` payload field, computed by the closed-form formula defined in FR12 (`supporter_vote_sum = (m / 2 + 1) · deviance_creator_vote + original_creator_vote`, integer division), written into the evidence block's payload at creation time per FR27 and validated authoritatively at FR9 Tier 3 against the candidate chain's per-node accumulated-vote projection at sequence `proposed_sequence − 1`; the value of a `snake_chain` essential-state replay block (chain-config replay per FR49, balance replay per FR50, or zero-input UTXO carry-forward per FR51) intervening between a deviation block and its associated evidence block is zero per FR27 (such blocks carry `consumed_votes = 0` by FR27 header override). The deviation block's `consumed_votes_from_first_voted_node` field records the originally-top node's pre-penalty accumulated vote per FR37 for audit purposes only and does not contribute to any block's branch value.

The branch value is **maintained incrementally** in the FR19 / FR20 chain_heads table per Connected/Active head as a `branch_value` field (see FR19 metadata list). The module shall update `branch_value` on the following events: (i) **Head extension** — when a new block is admitted to the block-tree as a Connected/Active head's child, the head's `branch_value` is incremented by the new block's per-block value (`head.branch_value += new_block.value`). (ii) **Stored → Connected transition** (a tail-pointing parent admission causes a previously Stored head's ancestry to merge into the active chain): the new Connected head's `branch_value` is computed by walking backward from the current active head along the active chain to the connection-point (the highest-sequence block on the new head's branch that lies on the active chain), accumulating per-block values *forward-from-S_tail* — equivalently: `new_head.branch_value = active_head.branch_value − Σ(values of active blocks strictly above the connection-point) + Σ(values of new-branch blocks strictly above the connection-point up to the new head)`. The walk length is bounded by the divergence depth (typically near the active head, much shorter than the snake_chain window). (iii) **Active-chain tail eviction** — when a new block is admitted to the active chain causing the snake_chain window to slide, `S_tail` advances and the dropped tail block's per-block value is **subtracted from the `branch_value` of every Connected/Active chain_heads entry**, because `S_tail` is the common reference point for all branches. (iv) **FR23 active-chain switch** — chain-switch reconciliation does **not** change any head's `branch_value`, because both `S_tail` and the per-block values of every block remain the same; only `active_chain_head_id` is updated. (v) **FR5 atomic recovery deletion** — any Connected/Active head whose ancestry passed through a deleted block has its `branch_value` invalidated and recomputed from the active head (per (ii)'s walk method); if the head's `head_block_id` was itself deleted, the chain_heads entry is removed (per FR19 mutation rules).

The active branch is the operationally admissible candidate among Connected/Active chain_heads with the highest `branch_value`. A candidate is operationally admissible if it retains a continuous tip-ending segment long enough to cover the full `snake_chain` window: once the chain has matured to length `W`, this means at least `W` blocks on that candidate branch; before the chain first reaches length `W`, the admissible bootstrap case is a genesis-anchored candidate spanning the entire currently existing chain from block #0 to its tip. Because a deviation block is created only after the originally-top creator has failed to produce the ordinary winning block for that sequence, the deviation block's own `consumed_votes` is strictly lower than the ordinary top-creator contribution that would have won at that same sequence; accordingly, a deviation-bearing branch that does not yet contain its associated approval evidence block is branch-value-weaker than the corresponding normal branch and does not overtake it under this FR. The associated approval evidence block is the mechanism that can later make the deviation-bearing branch competitive.

Ties shall be resolved deterministically using the following ordered rule, preserving replay determinism under FR63 (FR2's collecting-phase tie-break is a hash-only simplification of this rule — see FR2): (a) the candidate whose tip block has the larger serialized size in bytes wins — this size-based secondary criterion ranks immediately below the cumulative branch value, ahead of any creator-identity or hash-based criterion, so that under equal cumulative vote-derived branch values the branch carrying more block content is preferred; (b) if the tie persists, the candidate whose tip block's creator has the lowest node identifier wins; (c) if the tie still persists — possible only under creator equivocation, where the same creator signed two different equally-sized blocks at the same sequence — the candidate whose tip block hash, interpreted as a big-endian unsigned integer, is the lowest wins.
- FR22: Active-branch re-evaluation is performed locally and only when an event raises the `branch_value` of a non-active Connected/Active chain_heads entry, or creates a new Connected/Active chain_heads entry. Specifically, re-evaluation shall be triggered on exactly two event classes per FR19 / FR21: (i) Head extension on a non-active branch — a new block is admitted as the child of a non-active Connected or Active chain_heads entry, including the special case where the parent reference resolves to a non-head block already in the tree (a fork-creating admission, in which a new chain_heads entry is created and its `branch_value` is initialized per FR21's Stored→Connected rule applied at the fork point or per the head-extension increment if the new branch ascends from an already-Connected ancestor); (ii) Stored → Connected transition — a tail-pointing parent admission causes a previously Stored head's ancestry to merge into the active chain (per FR19's tail-pointing parent admission mutation rule), and the head's `branch_value` is computed per FR21's Stored→Connected walk. In both cases the re-evaluation is local: the module compares only the affected head's `branch_value` (under the FR21 tie-break rule: tip block serialized size → lowest tip creator node identifier → lowest tip block hash) against the current `active_chain_head_id` head's `branch_value`. If the affected head's value (under the tie-break) exceeds the active head's value, the module shall trigger an FR23 chain-switch reconciliation toward the affected head; otherwise the active branch remains unchanged.

Events that do NOT trigger active-branch re-evaluation: (a) a new block extending the active head — only `active_chain_head.branch_value` increments, so no non-active head can have become superior; (b) acceptance of a `snake_chain` essential-state replay block (chain-config replay per FR49, balance replay per FR50, or zero-input UTXO carry-forward per FR51) — its per-block value is zero per FR27's header override and therefore does not change any branch_value; (c) S_tail eviction (the snake_chain window sliding when a new block is admitted to the active chain) — every Connected/Active head's `branch_value` is decremented by the same `dropped_tail.value` per FR21, so all pairwise differences and the resulting ranking are preserved; (d) FR23 chain-switch reconciliation itself — `S_tail` and per-block values are unchanged, only `active_chain_head_id` and the `connected` flags shift, so `branch_value` of every still-Connected/Active head is unchanged and no follow-on re-evaluation is needed; (e) ordinary FR19 mutation events that do not change any head's `branch_value` (parent-recovery scheduler ticks, request emissions, head_ref_count updates that do not transition a head's status); (f) acceptance of an approval-less deviation block on a non-active branch — although this is technically a head-extension event that does increment the non-active head's `branch_value`, the deviation block's `consumed_votes` is by FR21 strictly lower than the corresponding normal branch's top-creator contribution at that sequence, so the deviation-bearing branch is still branch-value-weaker than the corresponding normal branch and cannot become authoritative without the subsequent approval evidence block; the local comparison correctly resolves this case under FR21's tie-break rule. FR5 atomic recovery deletion is governed by FR5 itself (which may invalidate and recompute branch_value for affected heads, and may force a fresh active-head choice if the active head was deleted); FR22 does not re-trigger separately on FR5 events.
- FR23: Reversibility principle. The chain-switch reconciliation in-place workflow is possible because every derived-state projection maintained by the module (per-node balances, UTXO spent-bit vectors, accumulated vote including anti-capture interest, creator-order projection, public-key mapping, max-node-id watermark, per-node seed-source-sequence, **and the mempool**) is **per-block reversible**: the effect of accepting a single block on every projection can be undone deterministically using only the block's own contents (header + payload + post-state-snapshot fields encoded therein) — or, for the per-node `seed_source_sequence` projection of FR50, by bounded backward scan along the rolled-back chain segment (whose previous seed source for any affected node is guaranteed to lie within the active `snake_chain` window per the FR50 coverage invariant) — and re-applied forward in exactly the same way. The reconciliation therefore proceeds as a **block-by-block step-wise traversal**: walking *backward* one block at a time from the previous active head, undoing each block's effect on every projection (including putting the block's confirmed transactions back into the mempool), until reaching the common ancestor; then walking *forward* one block at a time from the common ancestor along the new active branch, applying each block's effect on every projection (including removing the block's transactions from the mempool). The mempool is not handled as a separate reconciliation step: it is one projection among the others, mutated step-wise within the same backward and forward walks (no distinct "mempool reintroduction" or "mempool reconciliation" phase exists).

When the active branch changes, the blockchain module shall execute the chain-switch reconciliation workflow defined in this FR (with the architectural realization in `moonblokz-blockchain-architecture.md` §4.2, `reconciliation.rs`) as an atomic unit: identify the common ancestor of the previous and new active branches; perform the backward step-wise rollback walk from the previous active head down to the common ancestor (each step undoes one block's per-projection effects on every derived state — balance, UTXO, vote, creator-order, public-key mapping, max-node-id watermark, and mempool); perform the forward step-wise replay walk from the common ancestor up to the new active head (each step applies one block's per-projection effects on every derived state, including mempool removal of newly-confirmed transactions); during the walks, update each visited block's `is_on_active_chain` flag (false on backward walk for blocks demoted to side-branch, true on forward walk for blocks promoted to active); update block-status markers per FR9 so that blocks on the new branch are marked Active and blocks on the abandoned branch are demoted to side-branch status without being deleted from storage; and update FR19 `chain_heads` per its FR23 chain-switch mutation rule (set `active_chain_head_id` to the new active head, recompute every Connected/Active head's `connected` flag and connection-point cache — these checks are O(walk-back-until-`is_on_active_chain==true`) on each affected head's branch — demote any Connected head whose branch no longer reaches the new active chain to Stored with `last_request_timestamp = 0` and clear its `branch_value` field; `head_ref_count` values are not affected since they are structural; `branch_value` values of every still-Connected/Active head are not affected by the chain-switch since both `S_tail` and per-block values remain the same per FR21).

In-place vs. full-reconstruction zone discriminator. The in-place reconciliation workflow above can complete its forward step-wise replay only when the node holds enough retained chain context *backward from the common ancestor* to validate every replay rule along the new branch — specifically, **the node must retain a `snake_chain`-window-sized continuous block sequence going backward from the common ancestor** (i.e., the verification-horizon-retained ancestry from `D` down to `D − W` must be locally available). With that backward context present, FR9 Tier 2 / Tier 3 structural `snake_chain` preservation invariants (FR49 chain-config replay presence, FR50 balance replay coverage, FR51 carry-forward correctness, FR51 acceptance-time validation, FR29 replay-precedence ordering) can be evaluated step-by-step at each new block during the forward walk: each new block is admitted with a fresh `snake_chain` window built from the retained pre-ancestor segment plus the already-applied new blocks above it, so the window always covers the full `W` historical positions required for the replay-rule check. Forward content (new-branch blocks above the common ancestor) does not need to be pre-retained as a `snake_chain` segment — those blocks are the *input* being consumed by the walk one block at a time. The backward-retained `snake_chain` segment alone defines the **cheap zone** of FR58. If the node does not hold the backward `snake_chain`-window-sized retained ancestry (i.e., the deep-zone case per FR58), step-wise replay validation cannot be performed and the module shall instead trigger the **FR58 deep-zone full-reconstruction path**: the module transitions from ready state into a dedicated FR3 processing-pass against the new active branch — equivalent to a fresh ready-state-establishment validation pass identical to what is done on the initial collecting → processing → ready transition — applying the full Tier 1 + Tier 2 + Tier 3 invariant set without relying on the per-block reversibility of the in-place workflow. FR58's two-part trigger discipline (mature side branch + branch-value comparison) and fallback-to-original-chain semantics on full-reconstruction failure govern this deep-zone path.
- FR24: While knowledge is partial, delayed, or conflicting, the blockchain module shall present derived state consistent with exactly one currently selected active branch at a time, such that no external caller observes a mixture of pre-switch and post-switch balance, UTXO, vote, or mempool values. Observers may observe the state before the switch or after the switch, never a partial blend.
- FR25: Chain-switch reconciliation, deferred signature validation once creator keys become known, approval-evidence-driven legitimacy changes, and reintroduction of stale-looking transactions into the mempool shall all be implemented as ordinary first-class paths of the blockchain module, observable through the same event and state surfaces as normal block intake, and not as exception paths or special-case error flows.
- FR26: The blockchain module shall participate directly in support-message dissemination as a first-class part of the deviance-resolution path; relaying is not a radio-only concern. Because deviance is a rare but time-critical network event, the goal is to converge on resolution as fast as possible — the module therefore accepts and processes inbound support messages in every lifecycle state (collecting, processing, and ready), and FR1's ready-state-dependent gating list is not extended by this FR. For every support message submitted to the blockchain module through the support-message intake surface (one of the externally supplied event types per FR63), the module shall return exactly one of two classification outcomes — Accepted or Rejected — deterministically derived from the message bytes and the current authoritative state, and shall use the same outcome to gate radio-layer relay: an Accepted classification means every applicable validation passed and the module signals relay to the radio layer (which may then re-disseminate the message), and a Rejected classification means at least one applicable validation failed and the module both drops the message and does not signal relay. The classification shall be deterministic per FR63 and shall not depend on transport origin. The response shall carry only the binary classification outcome and no additional descriptive payload, consistent with the minimal-response convention of FR10. Validation rules — a message is Accepted iff all of the following applicable checks hold; failure of any applicable check yields Rejected. (i) **Mandatory format validation**: message-type and message-length checks pass, and the message is parseable as the canonical support-message format — a normal block-header prefix followed by a payload comprising (`supporter_node_id`, `deviation_sequence`, `deviation_block_hash`, `signature_over_deviation_block_sequence_by_supporter`). Format check is unconditional in every lifecycle state. (ii) **Supporter signature validation**: the supporter's signature over the `deviation_block_sequence` value verifies as valid against the supporter's public key when that key is derivable from the local active chain plus `snake_chain` replay history. When the key is not yet derivable (typical in collecting state, or when the supporter's registration block is not yet on the local active chain), this check is unconditionally deferred and the message remains Accepted on the remaining applicable checks alone; when the key is derivable but the signature verifies as invalid, the message is Rejected. (iii) **Tuple coherence with the local active chain**: the referenced (`proposer`, `deviation_sequence`) tuple is coherent with the local active chain — `deviation_sequence` falls within the local `snake_chain` window, and the `proposer` is a known node on the active chain or its connected ancestry. This check is evaluable only when an active chain exists; in collecting state the check is unconditionally deferred. (iv) **Active-chain-on-deviation subgroup gate** — when the referenced deviation block (identified by `deviation_block_hash` at `deviation_sequence`) is locally resolved on the active chain, the supporter MUST be a member of the deterministic ADR-015 subgroup for the (`proposer`, `deviation_sequence`) tuple, AND no valid approval evidence block for this proposal MUST yet have been admitted on the local active chain. Failure of either condition is Rejected; failure of the no-evidence-yet condition specifically means the deviance has already been resolved and the support has no further role. When the deviation block is not locally resolved on the active chain, both conditions are not evaluable and are unconditionally deferred. (v) **LRU dedupe**: the message is not a duplicate of a previously cached entry under the module's fixed-size LRU relay-deduplication cache, keyed by (`deviation_sequence`, `crc32(deviation_block_hash || signature_over_deviation_block_sequence_by_supporter)`, `supporter_node_id`) — a compact composite key that identifies the message without storing the full hash and signature payload. A duplicate is Rejected (already-known) and not relayed again. Active-chain-coverage exception — when the deviation block is not locally resolved on the active chain (collecting state where no active chain exists, deviation block falling outside the local `snake_chain` window, or deviation block held only on a retained side branch), the active-chain-derived checks (ii signature against not-yet-derivable key, iii tuple coherence, iv subgroup-and-no-evidence) are not evaluable and are unconditionally deferred. In this case the message is Accepted on (i) format-validity and (v) LRU-non-duplicate alone — the others are skipped. This relay-friendly rule keeps support-message dissemination usable across the network during collecting-phase convergence and from nodes whose `snake_chain` window does not yet reach the deviation, so rapid propagation is preserved despite local knowledge gaps. LRU-cache trade-off — because the cache size is fixed and bounded, occasional duplicate relays may occur after an entry is evicted: this is an accepted trade-off — the dedupe cache shortens propagation rounds and lets them die out quickly without giving up bounded memory, and the rare-event nature of deviance makes occasional duplicates a tolerable cost. Proposer accumulation exception — when the local node is itself the proposer of the referenced deviation, an Accepted message is additionally accumulated per FR27 in addition to applying the relay logic above; storage of accumulated support is governed by FR27 (only the proposer retains support content as in-progress evidence-block state — non-proposer nodes do not retain support-message bytes beyond the relay decision; the LRU dedupe cache holds only relay-deduplication keys, not full message payloads). FR27's own subgroup-eligibility check is authoritative against the proposer's deviation-bearing branch; since the proposer creates the deviation block by extending its local active chain, this FR's intake-time subgroup gate (iv) always runs on the proposer's incoming support messages, so FR27's check is a confirming authoritative re-check rather than a backup path.
- FR27: When the local node is the proposer of a deviating block, the blockchain module shall accumulate every Accepted support message (per FR26) addressed to that proposal whose supporter belongs to the deterministic ADR-015 subgroup for the corresponding (`proposer`, `deviation_sequence`) tuple, evaluate whether the accumulated support satisfies the configured `required_support` threshold, and upon reaching that threshold construct an approval evidence block (`payload_type=4`). Proposer's-active-chain invariant: the proposer always has the deviation block on its own local active chain, because the proposer creates the deviation block by extending its local active chain (per FR45 / FR37 deviation creation). Consequently FR26's intake-time subgroup gate (iv) always runs on the proposer's incoming support messages — every Accepted message reaching this accumulator has already passed the intake-time subgroup check — and FR27's accumulator-time subgroup-eligibility check is therefore a confirming authoritative re-check rather than a backup path. If the proposer's local active chain subsequently switches to a branch on which the deviation block does not lie (the deviation-bearing branch is demoted by an FR23 chain-switch reconciliation), the accumulator is discarded and support collection stops on this proposal — the proposer no longer extends the deviation-bearing branch and no further evidence-block emission attempts are made for that deviation. Storage policy for support messages — only the proposer of a deviating block retains support content; non-proposer nodes do not store support-message bytes beyond the FR26 relay decision (FR26's fixed-size LRU dedupe cache holds only relay-deduplication keys, not full message payloads). The proposer's storage shape is the evidence-block-under-construction itself: as Accepted support messages arrive for the proposer's own (`deviation_sequence`, `deviation_block_hash`) tuple, their support signatures are aggregated into the in-progress evidence block's aggregated-signature accumulator and their supporter `node_id` values are appended to the evidence block's supporter-identity list, both following the cryptographic backend's incremental-aggregation contract. The proposer's working memory for this accumulation is therefore bounded by the eventual evidence-block size and shall not exceed `MAX_BLOCK_SIZE`. The proposer holds only as many supporter contributions as the deterministic ADR-015 subgroup admits — the cryptographic evidence-size cap of `required_support ≤ MAX_AGGREGATED_SIGNATURES(backend)` is enforced as in-memory work-set bound — and shall accept no further support contributions for the same (`deviation_sequence`, `deviation_block_hash`) tuple once the evidence block has been emitted onto the deviation-bearing branch. The accumulator is not durable: it is cleared on module restart per FR59 and on chain-switch reconciliation per FR23 if the deviation-bearing branch is demoted to non-active. Accumulator lifetime: the accumulator is created when the local node creates the deviation block per FR45 (and not earlier — non-proposer nodes never instantiate one), and is released once the corresponding evidence block has been emitted; if the deviation-bearing branch is demoted by FR23 chain-switch before the evidence block is emitted, the accumulator is discarded, and a new accumulator is created only if the local node again becomes the proposer of a deviation at a later sequence.

When the threshold is reached, the proposer constructs the evidence block. The evidence block's payload begins with the `supporter_vote_sum: u64` field — computed from the proposer's own chain-projection at evidence-block creation time per the closed-form formula defined in FR12 (`supporter_vote_sum = (m / 2 + 1) · deviance_creator_vote + original_creator_vote`, integer division), so that the value depends only on the subgroup size `m`, the deviation block creator's accumulated vote, and the would-have-been original creator's accumulated vote at sequence `proposed_sequence − 1` — followed by the aggregated support signature and the list of supporting node identifiers per ADR-015 and Section 9 of `moonblokz-blockchain-algorythm.md`. The proposer is the only node authorized to extend the deviation-bearing branch above the deviation block: every block whose `previous_hash` resolves to the deviation block, or to any further block on the deviation-bearing branch above it, shall have the deviation block's creator as its creator. A block on the deviation-bearing branch above the deviation block whose creator differs from the deviation block's creator constitutes exact evidence of invalidity per FR16. While the deviation-bearing branch remains under this approval workflow, no other node creates blocks on this branch. Whenever the FR29 precedence rule requires `snake_chain` essential-state replay blocks (chain-config replay per FR49, balance replay per FR50, or zero-input UTXO carry-forward per FR51) to be inserted between the deviation block and its associated evidence block, the proposer shall create those intervening replay blocks as well, before the evidence block. Replay-block ordering: the proposer emits the intervening replay blocks **in the order in which the corresponding tail blocks fall out of the active `snake_chain` window**, not in any fixed payload-type order — chain-config, balance, and UTXO carry-forward replays are scheduled by their respective FR48 / FR50 / FR51 tail-imminent triggers as the tail advances on the deviation-bearing branch, and the proposer's emission sequence on the post-deviation branch follows the same tail-fallout order. The proposer continues emitting replay blocks one at a time until the next replay obligation is satisfied, repeating until the evidence block is the next obligation that fits at the head; only then does the proposer emit the evidence block itself. Inter-replay pacing on the deviation-bearing branch is governed by FR29. Header construction for the evidence block and for every such intervening replay block shall override the corresponding clauses of FR45 with the following fixed values, applied uniformly to each successive block on the deviation-bearing branch above the deviation block: sequence continues to increment normally — exactly one greater than the immediately preceding block on the deviation-bearing branch; `consumed_votes = 0`; `first_voted_node =` the local node (i.e., the proposer / self); `consumed_votes_from_first_voted_node = 0`; `previous_hash =` the hash of the immediately preceding block on the deviation-bearing branch, computed under FR45's normal rule; `signature =` the proposer's block-creator signature over header plus payload, per FR45's normal rule. Because `consumed_votes` is fixed at 0 for these blocks, the proposer's accumulated vote per FR37 is not consumed by them. The proposer's accumulated-vote reset under FR35 / FR37 occurs when the deviation block is accepted onto the current active chain — including the local creation/extension path of FR45 — and does not wait for the later approval evidence block. The value attributable to the deviation block per Algorithm 8 / FR21 is determined by the deviation block's own `consumed_votes` recorded at its creation per FR45, not by the evidence or replay blocks above it (whose Algorithm 8 contribution follows the evidence-block valuation rule of FR21 in the case of the evidence block, and is 0 for the intervening replay blocks because their `consumed_votes` is fixed at 0). The proposer's authority to create these post-deviation blocks does not depend on the standard creator-order top-entry rule or on grace-period eligibility (both per FR44): it derives solely from the proposer's role as creator of the deviation block. The content-assembly priority of FR45 continues to govern any intervening essential replay blocks created on this branch. However, once the proposer has accumulated the required support package — i.e. the deterministic subgroup's required 50%+1 majority as represented by `required_support` — construction of the approval evidence block is triggered by that completed support package alone and is not gated by FR45's ordinary mempool-fill threshold, ordinary block-creation timer, or the presence of any ordinary mempool transaction. Only the header overrides above and the creator-eligibility override of this FR apply to these post-deviation blocks.
- FR28: A deviating block accepted on the current active-chain extension path is part of the authoritative active chain immediately and therefore updates balance, vote, mempool, and tail-advance state through the same FR35 / FR36 / FR45 mechanisms as an ordinary active-chain extension. Approval evidence is still required for branch-comparison competitiveness: because the deviation block's own `consumed_votes` is lower than the ordinary top-creator branch contribution at that same sequence, an approval-less deviation-bearing branch remains branch-value-weaker than the corresponding normal branch and does not overtake it under FR21 / FR22. The associated approval evidence block defined by FR27–FR29 is the mechanism that can later raise the deviation-bearing branch's cumulative value enough to compete during retained-branch comparison. Rationale for the two-stage scoring (deviation block alone is branch-value-weaker; only the deviation-block-plus-evidence-block pair is competitive against the corresponding normal branch): the approval workflow may take time, and during that window the originally-top creator's normal block at the same sequence may yet arrive on the network. As long as the approval evidence block has not been emitted onto the deviation-bearing branch, the corresponding normal branch — once received — branches-out-values the deviation-bearing branch under FR21 / FR22 and the network selects the normal branch. The two-stage scoring therefore preserves the originally-top creator's precedence whenever the original block actually shows up before the deviation is approved; only when the originally-top creator has demonstrably failed to produce its block (and the deterministic ADR-015 subgroup has supplied 50%+1 majority support) does the deviation-bearing branch become competitive via the evidence block.
- FR29: The blockchain module shall preserve the `snake_chain` replay precedence rule: essential-state replay blocks (chain-config replay per FR49, balance replay per FR50, or zero-input UTXO carry-forward per FR51) may be inserted before an approval evidence block, and the approval workflow must remain correct across such insertions. Inter-replay pacing on the deviation-bearing branch: when one or more `snake_chain` essential-state replay blocks have to be emitted between the deviation block and its associated approval evidence block (per FR27's replay-block-ordering rule), the proposer applies a configurable insertion delay between consecutive emissions on the deviation-bearing branch, obtained from the `configuration_module` per FR56 as a chain-config-derived parameter (the same accessor surface as other inter-block timing parameters), so that several replay obligations coming due in close succession do not flood the radio layer with back-to-back block transmissions. The pacing applies **before the first replay block as well as between subsequent replay blocks**: the first replay block on the deviation-bearing branch shall be emitted no sooner than this delay after the deviation block itself, otherwise the deviation block and the first replay block would collide on the radio layer (both freshly produced by the proposer in close temporal proximity). Subsequent replay blocks shall likewise be emitted no sooner than this delay after the immediately preceding replay block on the deviation-bearing branch. The pacing delay applies only to the inter-replay timing on this branch — it does not constrain the timing of the evidence block emission itself relative to the last replay block (the evidence block is emitted as soon as the support package is complete and the next obligation at the head fits, per FR27). Replay-bearing-block validity (`consumed_votes = 0` per FR27 header override) is unchanged by the pacing rule; the pacing rule governs only when consecutive emissions are radio-released, not their structural correctness.

### Mempool, Balances & Vote State
- FR30: The mempool is implemented as a **separate module** (`mempool_module`), structurally distinct from the blockchain module — analogous to `configuration_module` (FR55) and the external `scoring_module`. The blockchain module does not own mempool storage internally; instead, the `mempool_module` owns the mempool's runtime state and exposes a typed mutation/accessor surface that the blockchain module calls to add transactions, remove confirmed-or-window-expired transactions, perform capacity-pressure eviction, reconcile on chain-switch reconciliation per FR23 / FR32, and read mempool content for block creation per FR45 / for top-mempool-items exchange per FR42 / for local query surfaces per FR40. The mempool's authoritative runtime state remains chain-governed in its content: every mutation invoked on the `mempool_module` is driven by a deterministic blockchain-module call whose inputs are derived from the current authoritative chain state (and from the FR63 seeded pseudo-random generator for the eviction rule of FR33), so replay determinism is preserved across the module boundary. Membership is independent from durable blockchain truth: the mempool is not persisted across restarts as blockchain truth, and the `mempool_module` is empty on restart per FR59 — the implementation may recover mempool content from external transport retransmission after restart, but shall not treat pre-restart mempool contents as durable. Storage representation is the `mempool_module`'s implementation contract: it shall use a compacted representation (contiguous transaction byte buffer plus a fixed-size index with `start`, `length`, `hash_crc32`, `transaction_fee`, `expiry_sequence`, `is_deferred`, and `is_own`) so that storage usage matches actual per-transaction size rather than maximum transaction size; the contiguous-storage invariant shall be preserved across every mutation. Capacity is configured per FR55 (`mempool capacity` accessor of the `configuration_module`); the `mempool_module` enforces this capacity bound through the FR33 eviction rule when the blockchain module's add-call would otherwise overflow it. The blockchain module shall not bypass the `mempool_module`'s mutation surface — every mempool state change shall go through it — so that the contiguous-storage invariant, capacity enforcement, and eviction discipline remain the `mempool_module`'s sole responsibility.
- FR31: The blockchain module shall invoke the `mempool_module`'s add operation (per FR30) for a transaction if and only if the transaction has been classified as Accepted-to-mempool per FR14. The `mempool_module` updates the compacted byte buffer and index per the storage contract of FR30 atomically with the add, storing the transaction fee resolved by the blockchain validation path so later ordering and block assembly do not need to recompute UTXO-backed complex fees. When a transaction would push the mempool beyond its configured capacity (`mempool capacity` per FR55), the `mempool_module` applies the randomized eviction rule with own-transaction prioritization defined in FR33 to free exactly one slot, and then admits the new transaction. If the eviction fails to free sufficient space (e.g., the new transaction itself is the selected eviction target under the rule), the `mempool_module`'s add operation rejects the new transaction and the blockchain module surfaces the outcome to the caller as Rejected.
- FR32: Whenever the authoritative chain interpretation changes, the blockchain module shall reconcile the mempool by issuing the corresponding mutation calls to the `mempool_module` (per FR30). Two trigger cases drive this reconciliation, and they share the same operation set: **(A) Forward extension** — a new block is accepted onto the current active chain. This is a single-block-forward case: only step (2) and step (3) below apply, with step (2) running once for the newly accepted block. **(B) Chain-switch reconciliation** — the active branch changes per FR22 / FR23, processed as the step-wise backward+forward walk; all three steps below apply, with steps (1) and (2) running per block along the walk and step (3) running once at walk completion. The reconciliation is part of the same structured step defined by FR23 in the chain-switch case and is part of the forward-extension trigger of FR35 in the forward-extension case. The three operations are: (1) **Add transaction to mempool — backward-walk reintroduction (chain-switch only):** for each block leaving the active chain during the backward walk from the previous active head down to the common ancestor, every transaction confirmed by that block is re-added to the `mempool_module` via its add operation (per FR31), so that transactions previously confirmed on the abandoned branch but no longer on the new active chain return to mempool candidacy; this is subject to mempool capacity and to the eviction rules of FR33 enforced by the `mempool_module`. (2) **Remove transaction from mempool — confirmation removal:** for each block joining the active chain (under (A) the single newly accepted block; under (B) every block on the forward walk from the common ancestor up to the new active head), every transaction confirmed by that block is removed from the `mempool_module` (the `mempool_module` compacts the byte buffer per its FR30 storage contract), since these transactions are now confirmed on the new active chain and have no further role in the mempool. (3) **Window-expiry removal at completion:** once the relevant walk (A: trivial single-block forward, or B: the full backward+forward walk) completes, every remaining mempool transaction whose `anchor_sequence` has fallen outside the acceptance window relative to the new active-chain head shall be removed from the `mempool_module`. This window-expiry removal **replaces the previously time-driven mempool aging mechanism**: it is event-triggered by every active-chain extension or chain-switch completion, so a separate periodic mempool-aging timer is not required. The `mempool_module`'s contiguous-storage invariant shall be preserved throughout these operations as part of its FR30 contract.
- FR33: When applying random mempool eviction under full-capacity conditions, the `mempool_module` (per FR30) shall select eviction targets by uniform-random sampling. The eviction algorithm differs by the local own/non-own classification of the incoming transaction. A node-transfer or registration transaction is own when its transaction-level initializer equals the local node id. A complex transaction is own when it has at least one input and either any balance input initializer equals the local node id or any balance output receiver equals the local node id; UTXO-only and zero-input complex transactions are non-own. **Case 1 — incoming transaction is classified non-own:** (a) primary candidate set — every mempool transaction not initialized by the local node; one eviction target is drawn uniformly at random from this set whenever it is non-empty, freeing one slot, and the new transaction is admitted into that slot (per the FR31 "free exactly one slot" semantics for non-own incoming transactions). (b) fallback candidate set — used only when (a) is empty, i.e. every mempool transaction is locally initialized; the candidate set is the local node's own mempool transactions plus the newly arriving transaction, and one eviction target is drawn uniformly at random from this extended set; if the newly arriving transaction itself is selected it is not admitted, with the `mempool_module`'s add operation rejecting it and FR31 surfacing this as Rejected, otherwise the selected own transaction is evicted and the new transaction admitted. **Case 2 — incoming transaction is classified own:** the algorithm proceeds in two stages, in order, until enough capacity is freed for the new transaction's serialized size. **Stage 1: drain non-own first.** While the freed capacity is below what the new transaction needs and the set of non-own mempool transactions is non-empty, the `mempool_module` draws one non-own transaction uniformly at random and evicts it. The non-own set shrinks with each draw; the loop continues until either enough space is freed (proceed to admit) or the non-own set becomes empty (proceed to Stage 2). **Stage 2: drain own if still not enough.** Only entered when the non-own set is empty and the freed capacity is still below what the new transaction needs. While the freed capacity is below the requirement, the `mempool_module` draws one own transaction uniformly at random (excluding the newly arriving transaction itself from the draw) and evicts it. The loop terminates when enough space is freed and the new transaction is admitted. There is no rejection path in Case 2: by the structural invariant that the configured `mempool capacity` (per FR55) is always greater than or equal to the maximum possible transaction size (bounded by `MAX_BLOCK_SIZE`), draining all currently-present transactions empties the mempool and leaves enough space for any single new transaction, so termination with admission is guaranteed within at most a finite number of draws bounded by the mempool size. **Network-level preservation property:** the randomness across nodes is an **important network property**, not just a local design choice. Different nodes evict different transactions because each runs its own random draw against its own mempool snapshot, so at the network level the union of all nodes' mempools preserves any given transaction with high probability — even when individual nodes are forced to drop content under capacity pressure. This emergent network-level robustness is the primary reason the eviction is randomized rather than rule-based: rule-based eviction would tend to drop the same transactions across many nodes, collapsing network-wide retention; uniform-random eviction spreads losses, so the network as a whole has the best chance of holding onto every transaction somewhere. The seeded pseudo-random generator referenced by FR63 is a **testing aid only**: it lets simulator/replay test environments reproduce the same eviction outcomes for the same seeded input sequence, and is not a correctness invariant of the production runtime — random outcomes that differ across nodes in production are exactly the desired behavior for the network-level preservation property.
- FR34: The blockchain module shall maintain, as derived operational state projected from the current active chain, all of the following: Per-node balance — current money balance for every node currently represented on the active chain, including the block creator's per-block fee and mining-reward credit per FR36. Per-node accumulated vote — current accumulated vote relevant to block-creator selection (owned internally by the vote module per FR37), including the anti-capture vote-interest growth applied on each accepted active-chain block per FR37. Per-node public-key mapping — `node_id` → `public_key` for every node currently on the active chain, usable for signature verification of later blocks and transactions. Block-navigation-and-UTXO cache (per-block-slot in-memory projection) — a compile-time-fixed-size in-memory cache, sized in slots equal to the block-storage slot count (the same compile-time parameter that bounds durable block storage), running parallel to durable block storage one cache slot per stored-block slot. The cache is **not durable** and is **not co-located with blocks in durable storage**: it is rebuilt on module restart from the durable block-tree contents. Each cache slot, when occupied, holds: (i) `sequence: u32` — the block's sequence number; (ii) `hash` — the block's hash; (iii) `parent_slot_index: u32` — the cache slot index of the block's parent (resolved via `previous_hash`), with the sentinel value `slot_count + 1` denoting "parent not present in the cache" (the parent block is not currently in durable storage / has been evicted / has not yet been admitted); (iv) `utxo_unspent_bitfield: [u8; UTXO_UNSPENT_BYTES]` — a fixed-size byte array recording the spent/unspent status of the block's UTXO outputs (`0 = unspent`, `1 = spent`), addressed by row-continuous layout: the bits are laid out consecutively, transaction by transaction in the order the transactions appear in the block, and within each transaction the UTXO outputs in the order they appear in the transaction's output stream — so that for the k-th UTXO output of the j-th transaction, the bit position is the count of all UTXO outputs in transactions strictly before the j-th transaction plus the position of that output within transaction j. The byte-array size is `UTXO_UNSPENT_BYTES = ⌈UTXO_UNSPENT_BITS / 8⌉`, where `UTXO_UNSPENT_BITS` is a compile-time parameter denoting the maximum number of UTXO outputs per block addressable via this cache. The compile-time bit count caps the cache's per-block addressability; the chain-config-derived `max_block_UTXO_output` parameter (per FR56) governs the actual block-validation bound on per-block UTXO-output count and shall not exceed the compile-time `UTXO_UNSPENT_BITS` (a chain-config block whose `max_block_UTXO_output` exceeds the compile-time bit count is structurally rejected on chain-config intake per FR8 chain-config validation, since such a configuration could not be honored locally; chain-config values smaller than the compile-time bit count are permitted, in which case only the first `max_block_UTXO_output` bits are used per block and the remaining bits are unused). Block validation enforces the chain-config-derived `max_block_UTXO_output` bound on every accepted block: a block whose cumulative UTXO-output count exceeds `max_block_UTXO_output` is structurally rejected at intake. The cache's purpose is **fast block-tree navigation without loading block bytes**: the parent_slot_index field lets the module follow ancestry chains by slot-index hops rather than by re-reading durable block bytes and resolving `previous_hash` against them; the (sequence, hash) pair lets the module identify a block's identity for FR11 already-known checks and for active-chain projection lookups; and the utxo_unspent_bitfield lets the module evaluate UTXO-input validity (per ADR-016) without re-reading the referenced block's bytes for the spent-bit check. No separate in-memory live UTXO set is maintained; the unspent set at any moment is defined implicitly by all output positions whose bit is 0 across the cache's currently-in-window slots. Max-node-id watermark — the highest node identifier currently present on the active chain, used for registration-sequence validation. Seed-source-sequence — per-node `seed_source_sequence: u32` field, recording the active-chain sequence of the block currently serving as that node's latest balance/registration seed source (per FR50). It is used by FR50's two balance-block triggers (tail-imminent, spacing-driven smoothing) and by the deterministic bonus-pack ordering for balance-block content assembly. All six are derived projections: they are not durable blockchain truth and must be fully recomputable from the active chain plus the `snake_chain`-preserved replay blocks. The module shall not expose inconsistent combinations of these projections across the FR24 coherence boundary.
- FR35: The blockchain module shall update the FR34 derived projections in response to exactly two triggers. **Trigger 1 — Forward extension:** a new block is accepted onto the current active chain. **Trigger 2 — Chain-switch reconciliation:** the active branch changes per FR22 / FR23, processed as the step-wise backward+forward walk defined by FR23. Per-block update set — for each block-application step (under either trigger; under Trigger 2 the rollback half applies the inverse of the per-block update for every block leaving the active chain, and the forward half applies the per-block update for every block joining the active chain), the module shall update incrementally: per-node balances per FR36; per-node accumulated vote per FR37 (including anti-capture vote-interest growth for every node before creator resets and the deterministic intra-block ordering owned by FR37, including the creator accumulated-vote reset on successful block acceptance); per-node public-key mapping for any registration transactions in the block; the max-node-id watermark for any registrations; per-node `seed_source_sequence` per FR50 (on forward extension, the applied block's sequence is written to `seed_source_sequence[N]` for every node `N` named in a NodeInfo entry of an accepted balance block or for the new node `N` introduced by a registration transaction; on chain-switch rollback, `seed_source_sequence[N]` for each such affected node is restored by bounded backward scan along the rolled-back chain from the rolled-back block's predecessor — see FR50 / FR23); and the FR34 block-navigation-and-UTXO cache — the slot for the block being applied carries `(sequence, hash, parent_slot_index, utxo_unspent_bitfield)` with the bitfield zero-initialized when the block produces UTXO outputs, and the bitfield bits of every prior block whose UTXO outputs are consumed as inputs by the applied block are flipped to spent. Diff-patching the projections in place during chain-switch (without the FR23 rollback-then-replay walk) is forbidden — the walk model defined by FR23 is the authoritative shape of the update. All other consequential effects on derived state are governed by their owning FRs and are not re-stated here: mempool reconciliation under either trigger by FR32 (with FR15 Deferred re-evaluation); grace-period vote resets by FR37; `snake_chain` tail-advance handling — including custodian-fee reduction and below-fee UTXO discard for carry-forward — by FR51; spent-bit semantics by ADR-016.
- FR36: Upon acceptance of a block into the active chain via FR35's forward-extension path, the blockchain module shall credit the block creator's balance with the sum of the following two components, applied as a single balance update within the same forward-extension step: (a) Mining reward. The block's `mined_amount` header field (the mining reward in scope at the block's sequence per the chain-config reward rule validated by FR6). (b) Transaction fees. The total transaction fees paid by the initializers of the transactions contained in the block, computed per transaction type: Node transfer (`type=1`): the transaction's explicit fee field. Registration (`type=2`): the transaction's explicit fee field. The `registration_price` is not included — it is absorbed by the network per FR6's registration-validation rule (debited from the initializer's balance with no corresponding credit), reducing total network currency. Complex transaction (`type=3`): the non-negative difference between the sum of input amounts (UTXO inputs plus balance inputs) and the sum of output amounts, per Algorithm 13. A zero-input `snake_chain` carry-forward complex transaction produced per FR51 contributes zero fee, because it has no input source and its output value already reflects custodian-fee reduction. (c) Replay reward. When the accepted block contains an essential-state replay obligation — a chain-config replay block (`payload_type=3` not at genesis, per FR49), a balance block emitted as `snake_chain` replay (`payload_type=2`, per FR50), or a transaction block carrying a zero-input UTXO carry-forward complex transaction (per FR51) — the block creator's balance shall additionally be credited with the `replay_block_reward` amount obtained from the `configuration_module` per FR56. Per the replay-block content rule of FR45, each accepted replay block reproduces the essential state of one dropping tail block at the granularity of its payload type, so the reward is paid exactly once per replay-bearing accepted block (the multi-payload-type case of FR45 emits multiple consecutive replay blocks of differing payload types and pays the reward separately for each). The reward is intended to compensate the creator for maintenance work that does not generate ordinary transaction-fee revenue (replay content is structurally fee-neutral per FR36 (b)) and is a chain-currency credit drawn from the same network-absorbed pool as ordinary `mined_amount`. Attribution under approval workflow — every intervening `snake_chain` essential-state replay block emitted between a deviation block and its associated approval evidence block is created by the deviation block's creator (the proposer) per FR27 and FR45's approval-workflow exception; the proposer is therefore credited with one `replay_block_reward` for each such intervening replay block they produce, in addition to ordinary `mined_amount` per accepted block. The block creator's balance shall be credited exactly once per accepted block, applied as the sum of (a) + (b) + (c). On chain-switch reconciliation per FR23, this credit is rolled back along with the rest of the creator's balance state and re-applied along the new active chain per FR35's forward-replay rules. On `snake_chain` tail advance, when a scheduled balance replay per FR50 includes a NodeInfo entry for the credit-receiving block creator, that entry shall carry the creator's pre-credit balance (and pre-reset accumulated vote) per FR50's snapshot semantics — i.e., the state before this FR's creator credit was applied — and forward replay re-applies the credit and reset on top of the seeded value. Validation invariant. FR6's block-level validation shall include the invariant that the block creator's resulting balance, after applying the block's transactions to every affected node and applying this FR's creator credit, is consistent with: (i) the sum of initializer debits (transfer amounts, registration prices, and fees), (ii) the sum of non-creator credits (transfer receivers, UTXO outputs), and (iii) this FR's creator credit components (a) `mined_amount` + (b) transaction fees + (c) `replay_block_reward` when applicable per the rule above. A violation of this invariant constitutes a balance-invariant violation and triggers the FR5 deletion-and-reversion policy. Genesis exception. This FR does not apply to the genesis blocks #0 and #1 produced per FR54; those follow the bootstrap-only validation exceptions, and no `mined_amount` / fee credit is computed for them.
- FR37: The blockchain module shall maintain vote state relevant to block-creator determination as follows: Vote-target validity — the `vote: u32` field of every transaction shall reference a `node_id` that exists on the active chain (per the FR34 per-node public-key mapping projection at the moment of validation). A transaction whose `vote` field references a `node_id` not present on the active-chain node roster is handled differently depending on the validation context: at FR14 mempool intake it is always classified Deferred (regardless of how complete the local roster currently appears) and re-evaluated per FR15, because a future registration transaction may still establish that `node_id` on the active chain — there is therefore no "Rejected" path for vote-target absence at intake time; at FR6 candidate-chain validation it is treated as exact evidence of invalidity and triggers FR5 deletion-and-reversion, because the candidate chain is a fixed segment whose roster cannot grow further during validation. Permanent node-#0 vote-target exception: a transaction whose `vote` field equals `0` (node #0) is always treated as a valid vote target, in every block from #0 onward, regardless of whether node #0 is currently visible on the local public-key-mapping projection. Node #0 is established by genesis (block #0) and remains a valid target for the lifetime of the chain; this exception is not an unevaluability deferral but a permanent acceptance, and it is what unblocks early-chain registrations issued by node #0 itself before any other node exists. Vote accumulation on block #0's acceptance still applies in the ordinary FR37 step order: node #0's vote credits from those transactions are accumulated and immediately reset by FR37 step (3) (creator accumulated-vote reset), leaving node #0's post-genesis accumulated vote at 0. Accumulation source — the per-node accumulated vote is the result of **two components combined block-by-block** along the active chain, in the deterministic operation order specified at the end of this FR (steps (1) anti-capture interest growth, (2) vote credits, (3) creator reset). The first component, vote credits, is derived from the `vote` field of every transaction in every block on the current active chain, treating the target node identified by that field as the recipient of one vote credit whose numeric value is the chain-configured `vote_scale` parameter. The second component, anti-capture vote-interest growth, is applied to every node's pre-block accumulated vote on every accepted active-chain block, including the creator before the later reset (formula and rationale defined below in the "Anti-capture vote interest" paragraph). The accumulated vote therefore is **not** a simple `Σ vote_scale` over `vote`-targeted transactions: that sum captures only component (1) and ignores the compounding effect of component (2), so a node's actual accumulated vote can grow well beyond the simple credit sum after enough blocks have accumulated anti-capture interest on a non-zero baseline. Because the vote-target validity rule above is enforced at every validation point, the accumulator never encounters a `vote` value pointing to a non-existent node on the active chain. Votes carried by transactions held only in the mempool do not contribute to the accumulated vote until their containing block becomes part of the active chain. Creator reset — upon acceptance of a block into the active chain, the creator's accumulated vote shall be reset to zero, and the block's `consumed_votes` header field shall be consistent with the accumulated vote the creator held immediately before that reset, after step-(1) interest and step-(2) vote credits have both been applied. Grace-period penalty — the originally-top node's accumulated-vote reset is **applied via the deviation block when that block is accepted onto the active chain**, not at the moment of grace-period window expiry. The grace-period expiry per FR44 makes a fallback creator eligible to produce a deviation block; that deviation block records the originally-top node's pre-penalty accumulated vote in its `consumed_votes_from_first_voted_node` header field, and the actual accumulated-vote reset on the originally-top node takes effect as part of the forward-extension step that admits the deviation block into the active chain (per FR35's per-block update set, in the same step that applies all other derived-state effects of the block). This timing makes the penalty replayable from the chain content alone and locates the reset deterministically on the deviation block's sequence. The reset applies exactly once per fallback cycle and exclusively to the originally-top node identified by `first_voted_node` in the deviation block's header per FR45. The originally-top node is defined as the **top entry of the creator-order projection at the moment the previous active-chain head was accepted** — i.e., a snapshot taken at the start of the fallback cycle. Subsequent grace-period expansion steps within the same cycle do not change this snapshot; the deviating block's `first_voted_node` and `consumed_votes_from_first_voted_node` header fields therefore identify a single, expansion-step-independent node (namely the top-entry-at-cycle-start) regardless of how many grace-period expansion steps elapsed before the deviating block was created. Nodes admitted by later expansion steps that did not create the block are not recorded in the header and are not penalized — they retain their accumulated vote for future cycles; further grace-period expiries in the same cycle do not reset additional nodes' accumulated vote. If a chain-switch demotes the deviation-bearing branch (FR23), the reset is correspondingly rolled back as part of FR35's step-wise walk. Anti-capture vote interest — on each block accepted into the active chain, every node's accumulated vote, including the creator's accumulated vote before the later creator reset, shall be updated in integer arithmetic as `raw_bump := floor(accumulated_vote × vote_interest / vote_scale)`, `interest_bump := min(raw_bump, vote_scale)`, and `accumulated_vote := accumulated_vote + interest_bump`, where `vote_scale` and `vote_interest` are chain-configured parameters obtained per FR56 and `vote_scale` also caps the per-block anti-capture interest bump. The accumulated-vote update shall use checked `u32` arithmetic and shall not saturate: any active-chain step whose interest bump or vote credit would overflow `u32` is invalid for the reversible vote-state contract and must be rejected by the consuming validation path, because saturation would merge multiple pre-states into one post-state and violate FR23. `floor(a / b)` here denotes ordinary unsigned integer division. By construction, `floor(accumulated_vote × vote_interest / vote_scale)` evaluates to `0` whenever `accumulated_vote == 0`, regardless of the configured `vote_interest` / `vote_scale` ratio. This is intentional: a node with zero accumulated vote has no anti-capture growth surface, and the rule simply leaves such a node at `0` until it receives a positive vote credit through an accepted transaction's `vote` field per step (2). New nodes (just-registered, post-genesis-reset, or post-grace-period-reset) therefore start each fresh vote-accumulation cycle from `0` and accumulate exclusively through incoming `vote_scale` credits during the cycle's first block; anti-capture interest only contributes from the second accepted block onward (after the node has accumulated a non-zero accumulated vote from at least one transaction). Reconciliation under chain switch — on chain switch, vote state shall be rolled back to the common ancestor and replayed forward along the new active chain per FR35. Operation order on block acceptance is deterministic: (1) anti-capture interest is applied to every node's pre-block accumulated vote, including the creator; (2) the `vote` fields of the block's transactions are accumulated into the respective target nodes' accumulated vote, each contributing one `vote_scale` credit — **with the explicit exception that zero-input UTXO carry-forward complex transactions per FR51 do not contribute any vote credit, regardless of the value of their `vote` field**. The rationale for this exception is replay-safety against double-counting under `snake_chain` carry-forward repetition: the same UTXO output may be carried forward across multiple successive carry-forward transactions as it travels through the chain, and crediting the embedded `vote` field on each carry-forward emission would cause the same vote intent to accumulate multiple times for the same originating event. By design, a zero-input UTXO carry-forward transaction is a chain-maintenance mechanism that preserves unspent UTXO state across the snake_chain window, not a fresh expression of vote intent — only the original transaction whose `vote` field reflects an actual user choice contributes its credit at first acceptance, and subsequent carry-forward emissions are vote-neutral. (3) the creator's accumulated vote is reset to zero. This order ensures that votes contained in the newly accepted block do not benefit from anti-capture interest within that same block, and that a creator who happens to be voted for in their own block does not retain that vote under the reset.
- FR38: The blockchain module shall maintain, as a derived projection of FR37, the ordered list of next-eligible block creators, sorted descending by accumulated vote. Ties shall be resolved deterministically by ascending node identifier. The module shall refresh this ordered list under exactly the same two triggers that update the FR34 derived projections per FR35: (1) a new block is accepted into the active chain (forward extension), and (2) a chain-switch reconciliation per FR22 / FR23 (step-wise backward+forward walk; the creator-order is recomputed as part of the per-block update set on each walk step, consistent with FR35). Grace-period penalty is not a separate trigger: the originally-top node's accumulated-vote reset is applied via the deviation block when that block is accepted onto the active chain (per FR37), so the creator-order refresh that follows from that reset is already covered by trigger (1). `snake_chain` essential-state replay blocks are not a separate trigger either: the chain-config replay (FR49) and zero-input UTXO carry-forward (FR51) carry no `vote` field contributions, and balance replay (FR50) reproduces vote state via NodeInfo snapshots without independently changing the per-node accumulated vote beyond what the surrounding FR37 step (1)-(2)-(3) order already applies — the creator-order refresh on acceptance of any such replay block is therefore subsumed under trigger (1). The top entry of this list identifies the currently expected block creator; subsequent entries identify the fallback eligibility progression for the grace-period expansion rule of FR44. Nodes with zero accumulated vote are part of the order — they form its tail, ordered by the same ascending-node-identifier rule — so the projection is total over the node roster and, in the all-zero bootstrap state, node 0 heads the order and block creation can start (2026-07-04 clarification).
- FR39: When the active branch changes, the blockchain module shall preserve correctness of all rollback-sensitive consequences through the structured reconciliation workflow of FR23. Specifically, the module shall ensure that: No partial-state leak — no caller observes derived projections (FR34) that mix pre-switch and post-switch values, per the coherence requirement of FR24. Atomic reconciliation scope — spent-bit vector recomputation (per ADR-016 / FR34's block-navigation-and-UTXO cache), mempool reconciliation (FR32), and creator-order refresh (FR38) all happen as integrated parts of the FR23 step-wise rollback / forward-replay walk itself: each backward-walk step undoes a single block's effect on every projection (including the spent-bit bits the block flipped, the mempool entries it confirmed, and the creator-order shift it caused), and each forward-walk step applies the analogous effect on the new branch's blocks. None of these is a separate post-walk pass — they are the walk. The walk completes before the new active branch is exposed through any query or event surface (FR24 boundary). Previously-confirmed-transaction survival — every transaction that was confirmed on the abandoned branch but is not confirmed on the new branch is reintroduced into the mempool as part of the backward-walk add operation per FR32. UTXO reference resolution — UTXO input references of the form `(block_sequence, output_index)` resolve against whatever active chain the FR23 walk has produced at the moment of the resolution. Resolution itself is not a separate post-walk pass either: it is implicit in the forward replay, which re-evaluates every UTXO input on the new branch's blocks against the spent-bit state the walk has built up to that point. A reference whose `block_sequence` addresses a block on the new active chain with a matching unspent output resolves valid; a reference whose `block_sequence` addresses a block that existed only on the abandoned branch, or whose `output_index` now resolves to a spent or non-existent output, resolves invalid. The `(block_sequence, output_index)` pair is not a durable lifecycle identifier: carry-forward across the `snake_chain` window produces a new `(sequence, output_index)` for the carried-forward value, and callers holding pre-switch or pre-carry-forward references must re-resolve against the current active chain. Spent-bit recomputation — there is **no zero-init full re-derivation** of the spent-bit state in the cheap-zone reconciliation path. The forward replay applies each new-branch block's bit-flips incrementally, walking the FR34 cache from the common ancestor forward, so the resulting spent-bit state reflects the new branch by construction without ever materializing a from-scratch zero-baseline. The only situation in which a full from-scratch re-derivation runs is the **deep-zone case (FR58)**, when the divergence point has fallen outside the verification horizon and the in-place step-wise walk is no longer feasible: in that path, every derived view (balance, vote, public-key map, spent-bit bits, max-node-id watermark, creator-order) is reconstructed from scratch via the FR3 processing-pass forward traversal against the new branch, exactly as in the initial collecting → ready transition. No residue of the abandoned branch's spent-bit state remains in either path. Accumulated-vote honesty — accumulated votes after the switch reflect the new active chain's votes and anti-capture interest exactly as if the new branch had been the active branch from the common ancestor forward; no residue of the abandoned branch's vote state may remain (achieved by the same step-wise walk in the cheap-zone path or by full re-derivation in the deep-zone path). Chain-switch reconciliation is a first-class, observable path of the module; it shall not be implemented as an error handler or exception branch.

### Queries & Retrieval
- FR40: The local interface can query the state of a specific transaction, identified by its canonical transaction hash, through the blockchain module. The module shall return exactly one of the following states, determined from the current authoritative interpretation (active chain plus mempool): Unknown — the transaction hash is not present in the local active chain and not present in the mempool. In-mempool — the transaction is present in the mempool and not yet confirmed on the active chain. Transactions that are structurally parseable but not yet fully evaluable (awaiting missing context) are held inside the mempool under this same state; the caller is not exposed to an internal deferred sub-distinction. Confirmed — the transaction is present in a block on the active chain; the response shall carry the active-chain depth of the confirming block, expressed as `(active_chain_head_sequence − confirming_block_sequence) mod 2^32` per FR53's modular distance convention, so the caller can judge how deeply the confirmation is anchored in the active-chain window. The depth is bounded by the configured `snake_chain` window size `W` because confirming blocks outside the active window are not exposed through this query surface. The query shall resolve only against the current active chain and the current mempool; it shall not expose transactions that exist only on retained side branches. Determinism scope — the classification is **deterministic only for the chain-derived part**: a `Confirmed` outcome (with its `(sequence, hash)`-grounded depth) is reproducible across every node and across replays for the same canonical transaction hash against the same active chain. The `In-mempool` vs `Unknown` distinction is **best-effort**, not deterministic across nodes, because mempool content legitimately diverges between nodes due to FR33's uniform-random eviction (a network-level preservation property, not a consistency defect): the same transaction may be `In-mempool` on one node and `Unknown` on another at the same wall-clock instant, and either can later flip to `Confirmed` once the transaction lands in a block. Callers that need authoritative status shall rely on `Confirmed` outcomes; `In-mempool` is a local-knowledge hint about the node's current mempool snapshot and shall not be interpreted as a network-wide guarantee.
- FR41: The local interface can query current value state through the blockchain module, in two distinct query shapes corresponding to the hybrid value model: Node-balance query — given a node identifier, the module shall return the node's current balance and current accumulated vote as projected from the current active chain. The response shall optionally include the active-chain depth of the most recent block that affected the returned balance, expressed as `(active_chain_head_sequence − affecting_block_sequence) mod 2^32` per FR53's modular distance convention, so the caller can judge how deeply the balance is supported within the active-chain window. Address-UTXO query — given an address (public key), the module shall return the list of currently unspent UTXO outputs owned by that address on the current active chain, each entry containing `(block_sequence, output_index, amount)`, as projected from the spent-bit vector state of FR34 per ADR-016. The returned amounts reflect any custodian-fee reductions already applied through `snake_chain` carry-forward. The `(block_sequence, output_index)` pair is valid only against the current active chain: callers must re-resolve after observing chain-switch or carry-forward events through FR64 (see FR39, FR66). Both query shapes shall resolve only against the current active chain; side-branch UTXO or balance visibility shall not leak through the local interface. The depth-carrying variant of the node-balance query is optional at the API level and may be omitted by callers running in the most constrained memory profile.
- FR42: The blockchain module shall serve block-retrieval queries only while in ready state. In collecting state, the module shall return a not-ready outcome per FR1; in processing state, the module shall return a not-ready outcome because the active chain is not yet finalized. Queries served in ready state shall resolve against the current active chain and are available to any caller (local interface or radio layer) using one of two lookup keys: By sequence — return the block currently occupying that sequence on the active chain, if any. By block hash — return the block with that hash if and only if it is part of the current active chain. When the requested block exists only on a retained side branch, or is not present locally at all, or falls outside the current `snake_chain` window, the module shall return a not-available outcome rather than returning a side-branch block or leaking branch structure. The response shall carry the canonical `Block` struct defined in the shared `moonblokz-chain-types` crate. The `Block` struct exposes both the exact serialized block bytes (so that hashes and signatures remain verifiable by the caller after transport, byte-identical to the form stored locally) and a set of typed accessor methods over the parsed block content (header fields, payload type, transaction iterator, payload-specific accessors). Callers in the constrained embedded environment may use whichever surface they need — the serialized bytes for cryptographic verification or onward radio re-dissemination, the typed accessors for direct field reads — without parsing the bytes themselves; the `Block` struct is the canonical inter-component interface for retrieved blocks across the MoonBlokz codebase.
- FR43: The top-mempool-items exchange surface is available only while the blockchain module is in ready state. In collecting state and in processing state, any such event shall receive a not-ready indication and no transaction shall be returned. In ready state, the radio layer can deliver a replenishment snapshot from another node consisting of the hash CRC32 values of the requester's currently held top mempool transactions. The hash CRC32 of each mempool transaction is IEEE CRC32 over its canonical transaction hash and is the same `hash_crc32` value carried in the FR30 mempool index entry. Snapshot semantics: the responder shall treat any mempool transaction whose `hash_crc32` matches an entry in the received snapshot as already-known to the requester and shall exclude it from selection. CRC32 collisions across different canonical transaction hashes are accepted as a benign over-exclusion under this rule — the over-excluded transaction is simply skipped on this round and may be supplied on a later replenishment exchange — because `hash_crc32` is the compact FR30 replenishment identifier and no full byte comparison occurs at this surface. No size-fit check is performed at this surface: the returned transaction does not need to fit alongside the snapshot transactions within `MAX_BLOCK_SIZE`, because the requester can either extend its current candidate set with the returned transaction or replace a lower-priority transaction with it during its own block-content selection. Selection rule: from the set of responder's mempool transactions whose `hash_crc32` is **not** present in the received snapshot, the responder shall pick one transaction at random for return, with the following preference: (a) when one or more candidates have a fee-per-byte value (as defined in FR45) **higher than the lowest fee-per-byte value** among the responder's own mempool transactions whose `hash_crc32` IS present in the snapshot, the responder picks one of those higher-fee-per-byte candidates uniformly at random — these are "improvement" candidates that strictly raise the requester's content quality; (b) when no improvement candidate exists (every not-already-known candidate has fee-per-byte at or below the snapshot floor, or the snapshot intersection is empty), the responder picks one of the not-already-known candidates uniformly at random. The selection is **deliberately non-deterministic across nodes** — it is not driven by the FR63 seeded pseudo-random generator. Different nodes pick different transactions for the same snapshot, which spreads transaction propagation evenly across the network — analogous to FR33's network-level preservation property for eviction. The replenishment surface therefore offers no reproducibility guarantee across nodes; simulator/replay test environments may use a locally-seeded RNG in test builds to obtain reproducible test outcomes, but production runtime divergence across nodes is the desired behavior. The module shall return at most one transaction.

  **Implementation annotation (architecture 2026-06-17):** The top-mempool-items exchange is exposed as a blockchain **sync read-only** method `query_top_mempool_items(snapshot_hash_crc32s: &[u32]) -> Option<TransactionView<'_>>` defined in `queries.rs`. The method returns a borrowed `TransactionView` into the mempool compact buffer (no allocation, no `NextCall` side-effect, no scheduling change — read-only queries do not carry a `NextCall` per the single-outcome scheduling-pull pattern). The selection logic above is implemented in the `moonblokz-mempool` sub-crate's `top_n_for_exchange(n)` priority iterator over stored admission-time transaction fees; the iterator returns the selected borrowed `TransactionView` together with its stored fee.

### Block Creation & Timeout Recovery
- FR44: At any given moment, the blockchain module shall determine whether the local node is the currently expected block creator by comparing the local node identifier against the top entry of the creator-order projection maintained under FR38. The determination is binary: local-is-current-creator — the local node is the top entry; the module shall initiate block assembly per FR45. local-is-not-current-creator — the local node is not the top entry; no creation action at this moment, the module waits for the next grace-period expiry event. Grace-period expiries do **not** apply the originally-top node's accumulated-vote reset. The reset is applied only when the deviation block is accepted onto the active chain (per FR37 grace-period penalty timing). On each grace-period expiry within a fallback cycle, the module **only** advances the Algorithm 5 expansion window (first-and-second-ranked, then top-three, etc.), re-evaluates whether the local node now falls within the admitted set, and if so initiates block creation per FR45 — possibly producing a deviation block. The creator-order projection itself does not shift on grace-period expiry: the originally-top node remains the top entry with its full accumulated vote until either (a) it produces its own block (the ordinary outcome — its block is accepted and trigger (1) of FR35 applies its own creator accumulated-vote reset via FR37 step (3)), or (b) a fallback creator produces a deviation block and that block is accepted onto the active chain, at which point FR37's grace-period penalty applies the originally-top node's accumulated-vote reset as part of the deviation block's forward-extension update. Until either of those events happens, the originally-top node is free to produce its own block at any time during the expansion window — its branch remains branch-value-superior over any deviation-bearing branch lacking an evidence block (per FR28 two-stage scoring), so the network selects the originally-top node's block whenever it shows up before the deviation-bearing branch becomes competitive via the evidence block (FR21 / FR22). This design simplifies the grace-period bookkeeping: there is no per-expiry reset to apply, no per-expiry creator-order recompute beyond the expansion-window admission, and the chain's preference for the originally-top creator is preserved naturally through branch-value comparison rather than through a accumulated-vote reset. No pre-computed fallback set exists; the admitted set is simply the prefix of the creator-order admitted by the current Algorithm 5 expansion window, and the originally-top node remains a member of every prefix.
- FR45: When the local node is the currently expected block creator (per FR44) or becomes eligible as a fallback creator, the blockchain module shall initiate ordinary transactional block creation and essential replay block creation under the following conditions and rules: Trigger conditions — ordinary transactional block creation shall be initiated when either (a) the mempool contains enough eligible ordinary transactions to fill at least the configured transactional block-fill threshold percentage of `MAX_BLOCK_SIZE`, or (b) an external block-creation timer event arrives per FR46, enough time has passed since the previous block per chain configuration, and at least one ordinary mempool transaction can be included. A pending essential `snake_chain` replay obligation (chain-config replay per FR49, balance replay per FR50, or zero-input UTXO carry-forward per FR51) caused by impending tail drop shall be emitted as soon as the local node is eligible to create the next block per FR44 — i.e. the local node holds `local-is-current-creator` against the post-previous-block creator-order projection, or has been admitted as a fallback creator under FR44 grace-period expansion, or is the deviation-block proposer per the FR27 approval-workflow exception — without waiting for the transactional fill threshold or the ordinary inter-block timer. The replay-emission path is therefore co-located with the FR44 creator-eligibility decision: a non-eligible local node does not emit a replay block, and the obligation is satisfied by whichever node next becomes eligible. The "without waiting" phrasing means that, once the local node becomes eligible, the replay block is emitted ahead of any ordinary transactional content that would otherwise wait on the FR45 fill-threshold or inter-block timer; it does not bypass creator-eligibility, and it does not authorize a non-eligible node to produce the replay block. Replay-block content rule — each replay block emitted at the head shall reproduce every essential-state structure contained in the corresponding dropping tail block, subject to `MAX_BLOCK_SIZE`. The replay block's payload type matches the dropping block's content category: a dropping balance block (`payload_type=2`) is reproduced by a balance replay block (`payload_type=2`) carrying NodeInfo entries per FR50; a dropping chain-config block (`payload_type=3`) is reproduced by a chain-config replay block (`payload_type=3`) carrying the durable-locked configuration per FR49; a dropping transaction block (`payload_type=1`) is reproduced by a transaction block (`payload_type=1`) carrying zero-input complex transactions for unspent UTXO carry-forward per FR51, and may additionally carry ordinary mempool transactions up to `MAX_BLOCK_SIZE`. Under the FR6 / FR9 Tier 1 registration / complex-transaction mutual-exclusivity invariant, a single dropping transaction block (`payload_type=1`) can trigger at most one of UTXO carry-forward (FR51, when it contained `type=3` complex transactions with unspent UTXO outputs) or balance replay (FR50, when it contained `type=2` registrations whose seed source was the dropping block) — never both. A single dropping balance block (`payload_type=2`) triggers only balance replay; a single dropping chain-config block (`payload_type=3`) triggers only chain-config replay; a single dropping approval evidence block (`payload_type=4`) triggers no replay obligation. A single dropping tail block therefore requires replay across at most one payload-type category, and the prior multi-payload-type clause — formerly retained for the corner case of a transaction block containing both a registration seed source and unspent UTXO outputs — does not apply under the FR6 mutual-exclusivity invariant. The transient-multi-replay accommodation in FR48 is consequently a no-op invariant retained for forward compatibility and does not fire in steady-state operation. The order in which the consecutive replay blocks are emitted is determined by the content-assembly priority below applied to whichever payload-type categories remain pending. Each replay-bearing creator receives one `replay_block_reward` per FR36 (c) for the replay block they produce, and creator selection for each successive replay block follows FR44 from the post-acceptance creator-order projection so that the consecutive replay blocks are typically produced by different nodes through ordinary vote progression. Approval-workflow exception — under the FR27 approval workflow, the deviation block's creator (the proposer) is the only authorized creator of every block on the deviation-bearing branch above the deviation block; consequently every intervening `snake_chain` essential-state replay block required by FR29 between the deviation block and the associated evidence block is also created by the proposer. The replay-block content rule above still applies (each replay block reproduces the essential state of the dropping block matching its payload type), and the proposer accumulates one `replay_block_reward` per intervening replay block they create. Approval evidence block creation is governed separately by FR27 and is not subject to the ordinary transactional trigger conditions of this FR. No-progress is correct behavior: when the local mempool is empty, no replay obligation is pending, and no external mempool replenishment yields admissible content (e.g., the network as a whole has no transactions to disseminate), the trigger conditions of (a) and (b) are simply not satisfied and no block is created. This applies both in the very-early-chain regime (single-node post-genesis state) and at any later moment of organic transaction-traffic absence. The chain stalls until ordinary activity resumes; this is the intended behavior — the module shall not synthesize transactions or empty blocks to drive forward progress, and the absence of progress under these conditions is not an error, not a long-disconnect (FR60), and not subject to recovery action. Time-driver tick processing per FR46 continues normally throughout such stalls. Content-assembly priority — the content of the new block shall be assembled in descending priority: first, any pending `snake_chain` essential-state replay obligations (chain-config replay, balance replay, zero-input UTXO carry-forward) that cannot wait without losing state; then, ordinary transactions selected from the mempool according to the mempool's transaction-selection logic defined below; within the mempool selection, the local node's own (locally-initialized) transactions are prioritized over other-initialized transactions of equal fee-per-byte value. Registration / complex-transaction mutual-exclusivity in transaction-block assembly (per FR6's corresponding invariant) — a `payload_type=1` transaction block under construction shall not simultaneously contain a registration (`type=2`) and a complex transaction (`type=3`, including zero-input UTXO carry-forward per FR51). When the mempool holds candidates of both kinds and the block is not pre-committed by a pending UTXO carry-forward replay obligation, the block selects within one kind only — the kind whose highest-priority candidate (under the FR45 selection order: fee-per-byte → ownership → hash_crc32 → bytes) ranks first; the other kind waits for a subsequent block, with no carry-over priority adjustment. A pending UTXO carry-forward replay obligation per FR51 forces the block's content-class to `type=1` + `type=3` (no registration in the same block, even when registration candidates are present in the mempool); a pending balance-replay obligation per FR50 emits a separate `payload_type=2` block and does not constrain the same-sequence transaction-block content-class. Mempool transaction-selection logic. The fee-per-byte value of a mempool transaction is defined as its declared transaction fee divided by its serialized byte length. The transaction fee is determined per transaction type: for node transfer (transaction type=1) and registration (transaction type=2) the fee equals the explicit fee field — the `registration_price` is not part of the fee per FR6 and FR36; for complex transactions (transaction type=3) the fee equals the non-negative difference between total input amount and total output amount per Algorithm 13. Zero-input `snake_chain` carry-forward complex transactions are produced per FR51 and never enter the mempool, so they are not subject to this selection (their inherent fee is zero per FR36). The mempool's transaction-selection logic orders candidates by fee-per-byte value descending, with ownership prioritization applied as a higher-precedence sort key only among candidates of equal fee-per-byte value (own > other). Ties remaining after the value and ownership sort keys shall be broken deterministically by ascending `hash_crc32` (IEEE CRC32 over the canonical transaction hash; the index field maintained per FR30); on hash-CRC32 collision, by lexicographic comparison of the transaction bytes. This ordering is deterministic per FR63. Size bound — the assembled block shall not exceed the configured `MAX_BLOCK_SIZE`. The replay obligation content itself is **always guaranteed to fit** under `MAX_BLOCK_SIZE`: every replay reproduces essential state from a single dropping tail block whose serialized form already satisfied the same `MAX_BLOCK_SIZE` constraint when it was originally accepted into the chain (chain-config replay reuses the byte-identical configuration content of the dropping chain-config block per FR49; balance replay carries NodeInfo entries whose per-entry size is bounded by the dropping balance block's seed-source byte budget per FR50; zero-input UTXO carry-forward carries forward outputs whose combined byte budget is at most the dropping transaction block's UTXO output stream, with custodian-fee reduction never enlarging it per FR51). The size constraint therefore only governs **additional optional content** that the creator may pack alongside a replay obligation: when emitting a `payload_type=1` transaction block carrying a zero-input UTXO carry-forward (FR51), the creator may additionally include ordinary mempool transactions up to the remaining `MAX_BLOCK_SIZE` budget — extra mempool transactions are included only when they fit; they are simply skipped when they don't, and the block is **never discarded** for failing to fit additional content. There is no scenario in which a replay obligation forces the entire block to be the replay alone — that is normal: a chain-config replay is always its own block, a balance replay is always its own `payload_type=2` block, and a UTXO-carry-forward + extra mempool tx packing is bounded by the available budget without affecting the replay obligation's emission. Header construction — the block header shall carry the correct sequence, creator (local node identifier), `mined_amount` (per chain-config reward rule), `payload_type`, `consumed_votes` (equal to the local node's accumulated vote at the moment of creator selection, i.e., the state inherited from the acceptance of the previous active-chain head block, including any anti-capture interest applied at that acceptance, and excluding vote-accumulation from transactions contained in the block being created), `first_voted_node` and `consumed_votes_from_first_voted_node` (equal to the local node and zero respectively when the local node is the expected creator; set according to the grace-period deviation accounting when the local node is a fallback creator), `previous_hash` (hash of the current active-chain head), and `signature` (block creator signature over header plus payload). Post-creation effects — creation, including deviation blocks created as a fallback creator, shall update derived state via the same path as normal active-chain extension: creator accumulated-vote reset, anti-capture interest growth for all other nodes, mempool removal of included transactions, `snake_chain` tail-advance accounting for any replayed essential state, and application of the FR36 creator credit (`mined_amount` plus transaction fees plus `replay_block_reward` when the block carries replay obligations per FR36 (c)) to the local node's balance.
- FR46: The external time driver is a minimal "wake me after N time units" scheduler. The blockchain module owns all time-driven scheduling internally and shall expose the following two-part contract to the driver: Next-wakeup query. After every module invocation (event intake, query, or tick) the module shall be able to return the earliest remaining deadline among all its internally tracked time-driven behaviors, expressed as a delay relative to the monotonic time base supplied by the caller. The driver is responsible for calling the module back no later than that deadline. If no time-driven behavior is currently scheduled, the module shall return a sentinel indicating "no wakeup needed". Tick callback. When the driver wakes the module, it shall pass the current monotonic time. The module shall then evaluate every internally tracked deadline, fire each time-driven behavior whose deadline has been reached or passed (possibly multiple in a single tick), and recompute its next-wakeup value before returning. Tick processing is single-threaded. The module shall internally track at least the following time-driven behaviors, each with its own independently scheduled deadline, and shall fire the corresponding internal action when that deadline elapses: Block-creation interval — while `local-is-current-creator` holds and the ordinary-transaction content remains below the transactional fill threshold of FR45, this deadline marks when a time-driven transactional block may be produced if at least one ordinary mempool transaction can be included. It is not scheduled when the local node is not the current creator, or when no ordinary mempool transaction is includable and no replay obligation is pending. Pending tail-drop replay obligations may be emitted immediately per FR45 and therefore do not wait for this deadline once the local node is eligible to create the next block. Grace-period expiry — marks when the current grace-period window for the expected creator ends; firing triggers the reset-and-recheck iteration. Missing-parent re-query — the scheduler deadline driving parent-recovery request emission (Story 4.4, 2026-07-12: emitted at the *exact* next-eligible `NextCall::At` instant under the AR4 pull model, not on a fixed periodic tick — the `parent_recovery_global_tick_interval` parameter was removed; the per-head retry window and the global emit cooldown below are the only throttles) for unresolved `previous_hash` dependencies on Stored heads in the FR19 `chain_heads` table, with the following discipline: the module maintains a single module-scope `last_parent_request_emit_timestamp` (the wall-clock timestamp of the most recent parent-recovery request emitted across all heads, initialized to `0`); on each scheduler tick the module first evaluates the **global emit cooldown** — if `last_parent_request_emit_timestamp + parent_recovery_min_emit_interval > now()` the missing-parent re-query behavior performs no work this tick and returns immediately, with no eligible-head enumeration, no selection, and no emission; the global cooldown is independent of the per-head retry window, so a head whose per-head retry window has elapsed still waits for the global cooldown to clear before any parent-recovery request can be emitted. Only when the global cooldown has cleared does the module proceed: each Stored head carries `last_request_timestamp` (the local wall-clock timestamp of its most recent parent-recovery request, or `0` if no request has ever been emitted for that head); the module enumerates every Stored head whose retry window has elapsed (`last_request_timestamp + parent_recovery_per_head_retry_interval ≤ now()`, including the never-requested case where `last_request_timestamp == 0` so the head is immediately eligible); among that subset the head with the smallest `last_request_timestamp` is selected (most overdue first); ties are broken by smallest `head_sequence`, then by smallest `head_block_id` interpreted as a big-endian unsigned integer (matching FR19 / FR2 / FR21 tie-break for FR63 replay determinism); a **single** parent-recovery request is emitted to the radio layer for the selected head's tail-point's missing parent, the head's `last_request_timestamp` is updated to `now()`, and `last_parent_request_emit_timestamp` is likewise updated to `now()`. **At most one parent-recovery request is emitted per scheduler tick**, regardless of how many heads have elapsed retry windows — and the global cooldown additionally bounds the cross-tick emission rate so that, even if the scheduler tick interval is shorter than `parent_recovery_min_emit_interval`, no more than one parent-recovery request is emitted per `parent_recovery_min_emit_interval` window. The next eligible head is served on the next tick on which both conditions hold. The deadline is not scheduled when no Stored heads are present in the `chain_heads` table. Mempool replenishment — only while the module is in ready state and the local mempool content is below the transactional fill threshold of FR45, periodic outbound request for additional mempool items from the network, carrying the hash CRC32 values of the local node's currently held top mempool transactions in the FR45 selection ordering (the same `hash_crc32` values stored in the FR30 mempool index: IEEE CRC32 over canonical transaction hashes). Responding nodes apply FR43 against this hash-CRC32 list to exclude already-known transactions and supply at most one missing transaction. This behavior is not gated on the local node being the currently expected creator: within ready state it runs continuously on every node below the threshold, so that any node is already prepared with block-fill content if the creator role shifts to it through vote progression or grace-period expansion. The deadline is not scheduled in collecting state or processing state, nor while the mempool is at or above the threshold; it becomes eligible only after the module reaches ready state and resumes when the mempool drops below the threshold again (for example, after a block is accepted and its transactions are removed). The module shall not consult a local wall clock beyond the monotonic time value supplied by the driver on each tick. The driver shall not need to know which time-driven behaviors exist; the module is the sole owner of scheduling logic.
- FR47: Upon firing the grace-period expiry deadline per FR46, the blockchain module shall execute the fallback-cycle progression defined by FR44: advance the Algorithm 5 expansion window by one step (admitting one additional next-eligible creator into the admitted set), and re-evaluate whether the local node is now admitted to initiate block creation per FR45 under the FR37 grace-period vote-state rules. **Grace-period expiries do not apply any accumulated-vote reset** — the originally-top node's accumulated-vote reset is the responsibility of FR37 and is applied only when the corresponding deviation block is accepted onto the active chain (per FR37 grace-period penalty timing); FR47 firing only widens the eligible-creator set and does not itself mutate any accumulated vote. Fallback activation is a first-class path per FR25, observable through the same event and state surfaces as ordinary creator activation; grace-period expiry is not treated as an error condition.

### Snake_chain & Tail Preservation
- FR48: The blockchain module shall maintain the active chain at a bounded length at most equal to the configured `snake_chain` window size `W` in steady state. Until the chain has matured to length `W` (the bootstrap-anchored growth phase per FR21's bootstrap admissibility clause), the active chain spans block #0 to its current head and is shorter than `W`; the tail does not advance during this phase. Once the chain has reached length `W`, the steady-state head-advance / tail-drop mechanism applies. The preservation check is performed **at head-extension time, before the head is accepted (or, for a creator node, before it is created)** — not after the head has been added. Specifically: for every prospective head extension that would cause the chain length to exceed `W`, the module shall identify the active-chain tail block that would fall out as a result, determine whether essential state contained in that tail block requires preservation per FR49 (chain-config replay), FR50 (balance replay), or FR51 (UTXO carry-forward), and proceed as follows: (a) if no essential state is at risk, the head extension is accepted/created normally and the tail advances past the dropping block in the same step; (b) if essential state is at risk, the **head extension itself must be (or carry) the preserving replay block** per FR45's replay-block content rule — a creator node emits the appropriate replay block as the head extension, and an inbound head extension that does not preserve the at-risk essential state is rejected as invalid (it cannot be accepted onto the active chain because doing so would drop a tail block whose essential state has not been preserved). The tail shall never advance past a block whose essential state has not been preserved, and conversely the chain never reaches a state in which the tail is "about to drop" essential state without a corresponding replay already in place — the two operations are bound together at the head-extension decision. Single-block preservation invariant: under the FR6 / FR9 Tier 1 registration / complex-transaction mutual-exclusivity invariant, every dropping tail block triggers replay across **at most one** payload-type category (per FR45's replay-block content rule), and that one-category replay always fits into a single head block (per FR45's size-bound clause). Consequently a single dropping tail block is **always replayable in exactly one head block**, so the active chain's useful length is bounded at `W` at every moment — there is no operational regime in which the useful chain length exceeds `W`. Below-tail retention cache (FR23 cheap-zone efficiency): in addition to the active chain bounded at `W`, the blockchain module may retain an implementation-configured compile-time number of additional block records **beyond the active-chain tail** (i.e., blocks that have already left the active chain through tail-advance). These retained-below-tail blocks are **not part of the active chain** — they carry no derived-state contribution, they do not satisfy any preservation obligation, and the preservation logic above applies strictly to the `W`-length active chain regardless of how many extra blocks are held beyond the tail. Their sole purpose is to serve as a **chain-switch reconciliation cache** for FR23's cheap-zone path: when a chain switch lands inside the cheap zone (per FR23 / FR58), the local node may already have the historical block records needed for the step-wise backward+forward walk without requiring re-fetch from the radio layer. The retention count is a code-level constant (not a chain-configurable parameter, not exposed through the `configuration_module`), and the cache may be evicted at any time without affecting correctness — it only accelerates the cheap-zone reconciliation path and is not required by any other FR.
- FR49: When a chain-config block is about to fall out of the active-chain window, the blockchain module shall, before permitting the drop, schedule the creation of a new chain-config block at the head carrying identical configuration content. Scheduling discipline: the replay obligation shall be scheduled to be emitted in the next head block created after the drop becomes imminent — i.e. the head block whose acceptance would otherwise advance the tail past the dropping chain-config block — with no multi-block lookahead and no early scheduling. This single-block-ahead, immediate-pre-drop discipline is the **permanent rule for chain-config replay**, not an MVP simplification: chain-config blocks always replay exactly at the moment of fall-out into the head, and no look-ahead or forward-shift variant exists for them in any phase of the project. The FR50 balance-block spacing-driven smoothing emission (Trigger 2) is a separate mechanism that applies **only to balance blocks** and does not affect chain-config replay; chain-config replay always runs under this single-block-ahead discipline regardless of FR50 activity. The single-block-ahead discipline here preserves replay determinism (FR63) without requiring a chain-config-replay lookahead parameter. The replay obligation shall be treated as high-priority replay work per the content-assembly priority rule of FR45 and shall take precedence over ordinary mempool transactions and over approval evidence block emission per FR27.
- FR50: When the latest seed source for any registered node — i.e., a balance entry within some balance block, or (when no subsequent balance entry has yet been emitted for that node) the block containing the node's registration transaction — is about to fall out of the active-chain window, or when the spacing trigger below fires, the blockchain module shall schedule the creation of a new balance block at the head whose NodeInfo entries are determined by the trigger that fired. Each NodeInfo entry carries the affected node's balance, accumulated vote, and public key as they stood at the end of the previous block's acceptance, before any of the new balance block's own acceptance effects are applied. **Seed-source-sequence projection.** The blockchain module shall maintain, as part of the FR34 derived projections, a per-node `seed_source_sequence: u32` field — the active-chain sequence of the block currently serving as that node's latest balance/registration seed source. Update rule (applied by the FR35 per-block update set): on acceptance of a balance block containing a NodeInfo entry for node `N`, `seed_source_sequence[N]` is set to the accepted block's sequence; on acceptance of a registration transaction for new node `N`, `seed_source_sequence[N]` is set to the containing block's sequence. Under FR23 chain-switch rollback, the projection is restored by bounded backward scan along the rolled-back chain from the rolled-back block's predecessor until a balance block containing a NodeInfo entry for `N` — or `N`'s registration transaction — is encountered; this scan is bounded by `W` blocks per the coverage invariant below. The projection enables efficient identification of dropping-imminent seed sources and the deterministic ordering for bonus-pack selection (defined further below). **Two independent triggers, evaluated continuously after every active-chain extension; precedence order tail-imminent → spacing, only one trigger fires per next-head-block emission**: **Trigger 1 — Tail-imminent replay.** When any registered node has `seed_source_sequence[N] == S_tail` (i.e., the dropping tail block is its latest seed source), the next head block created by the local node shall emit a balance block. The trigger-1 mandatory entry set comprises one NodeInfo entry per tail-imminent node. This mandatory set is **always replayable in a single block** by the single-block-conservation invariant: on any single tail advance, exactly one active-chain block leaves the window. That dropping block already satisfied `block_size ≤ MAX_BLOCK_SIZE` when it entered the chain. A NodeInfo entry (per Section 7 of `moonblokz-blockchain-algorythm.md`, ≈ 48 bytes plus the 6-byte balance-payload header) is never larger than the structure that originally seeded that node in the dropping block: a registration transaction (which carries `new_public_key`, `new_node_id`, signatures, fee, vote, and other fields, all of which combined exceed the per-NodeInfo size budget) or a NodeInfo entry inside an earlier balance block (same per-entry size). Therefore the mandatory set carries the same or fewer per-node entries with strictly equal-or-smaller per-entry size, and fits inside `MAX_BLOCK_SIZE` by direct conservation. **Trigger 2 — Spacing-driven smoothing emission** (corresponds to Algorithm 16 of `moonblokz-blockchain-algorythm.md`, in MVP). Applicable only when (i) the active chain has reached steady-state length (chain length equals `W`; trigger 2 is disabled during the bootstrap-anchored growth phase per FR21) and (ii) no mandatory state-preservation obligation is pending on the next head block — i.e., trigger 1 is not firing, no FR49 chain-config replay is due, and no FR51 UTXO carry-forward replay is due. Let `N_active` be the current registered-node count (the FR34 `max_node_id` watermark plus one), `K_max` be the maximum NodeInfo entry count fitting in a single balance block (derived from `MAX_BLOCK_SIZE` minus block-header and payload-header overhead, divided by the per-NodeInfo entry size), and `W` be the snake_chain window size. Define `expected_balance_block_spacing = ⌈W / ⌈N_active / K_max⌉⌉` — the average number of blocks between consecutive balance blocks required to cover `N_active` nodes evenly across the window. Let `blocks_since_latest_balance_block = S_head − sequence_of_latest_balance_block_on_active_chain` (or `S_head − S_tail + 1` when no balance block currently resides on the active chain). When `blocks_since_latest_balance_block > expected_balance_block_spacing` and the other conditions hold, the module shall schedule a balance block emission at the head. The trigger-2 entry set is **empty for the mandatory portion** — there is no specific tail block to preserve — and the entire balance-block content is produced by the bonus-pack rule below operating from an empty mandatory baseline. Because the bonus-pack iterates registered nodes in ascending `seed_source_sequence` order (oldest seed source first), the resulting balance block naturally consumes first the NodeInfo entries of the active-chain balance block nearest to the tail (whose entries share the smallest `seed_source_sequence` value) and then continues with progressively newer seed sources until `MAX_BLOCK_SIZE` is reached. After acceptance, all affected nodes' `seed_source_sequence` updates to the new head's sequence; the consumed near-tail balance block, having no remaining nodes whose current seed source it serves, generates no replay obligation when it eventually drops from the window — and the balance blocks on the active chain are thereby continuously pushed toward an even distribution rather than retaining the roughly-random spacing that would otherwise result from registration drop-out timing. **Bonus-pack rule (shared across both triggers, mandatory by strict-determinism for FR63 replay equivalence).** After the trigger-specific mandatory entry set is placed in the balance block (which may be empty for trigger 2), the module shall pack **additional NodeInfo entries** for registered nodes not already in the mandatory set, in deterministic order: ascending `seed_source_sequence[N]`, then ascending `node_id`. Entries are added one at a time until the next-eligible entry would exceed `MAX_BLOCK_SIZE`; the addition stops at that point. The deterministic ordering plus `MAX_BLOCK_SIZE` cutoff yields a single canonical entry set for every (trigger condition, chain state) pair. A creator that emits a balance block whose entry set deviates from this canonical set — by reordering, by omitting an eligible entry that would have fit, or by including an entry that should not have appeared given the deterministic ordering and cutoff — produces exact evidence of invalidity per FR5, and the same canonical reconstruction is used during incoming-block validation. The mandatory bonus-pack is the mechanism that maximizes per-balance-block utilization: the chain produces few large balance blocks rather than many small ones, and bonus entries refresh nodes' seed sources opportunistically up to MAX_BLOCK_SIZE on every balance block emission regardless of which trigger fired. Because trigger 2's mandatory baseline is empty, its balance block is built entirely from the deterministic bonus-pack iteration — so trigger 2 is operationally a "pure bonus-pack emission" gated only by the spacing condition and the absence of other mandatory replay obligations on the next head block. NodeInfo snapshot semantics: every NodeInfo entry in a balance block represents the affected node's state at sequence `(this_balance_block.sequence − 1)`, i.e., the post-previous-block / pre-this-block state. The following effects of the balance block's own acceptance are therefore NOT reflected in any NodeInfo entry: (i) the balance block creator's mining-reward credit and transaction-fee credit per FR36 (transaction-fee credit is zero for a pure balance block but the rule applies uniformly when the balance block also carries content); (ii) the creator's accumulated-vote reset to zero per FR37 step (3); (iii) when the balance block is itself a deviation block (`first_voted_node ≠ creator` recorded in the header), the first_voted_node's grace-period accumulated-vote reset to zero per FR37 — the NodeInfo entry for the first_voted_node, if present, shall carry the pre-reset value (the same value that the deviation block's `consumed_votes_from_first_voted_node` header field records); (iv) the anti-capture vote-interest growth per FR37 applied to every node at this block's acceptance is also not reflected in NodeInfo entries (each affected node's `vote_count` shall represent its pre-anti-capture-growth value at sequence `block.sequence − 1`'s end). FR3 forward traversal seeds derived state from NodeInfo entries and then applies the balance block's own acceptance effects (creator credit, creator accumulated-vote reset, first_voted_node grace-period reset when applicable, anti-capture growth) on top of the seeded values exactly as for any other block. Validation invariant. Beyond the structural snake_chain-preservation invariants of FR6, every balance block's NodeInfo entries shall be byte-consistent with the candidate-projected per-node state at sequence `block.sequence − 1`; any NodeInfo entry whose `(balance, vote_count, public_key)` triple disagrees with the candidate projection's pre-this-block state for that node is exact evidence of invalidity per FR5. Regular transactions (`type=1` node transfer and the balance-input or balance-output sides of `type=3` complex transactions) do not by themselves preserve per-node balance state — they only modify the derived balance projection of FR34 forward from the latest seed source — and therefore do not trigger a balance-block emission; the trigger of this FR is solely the impending loss of a balance-entry or registration-based seed source. A single balance block does not enumerate every registered node and is not required to: a balance block's payload follows the `NodeInfo`-array structure of Section 7 of `moonblokz-blockchain-algorythm.md` (per-entry size ≈ 48 bytes plus the 6-byte balance-payload header) and is bounded by `MAX_BLOCK_SIZE`, so on the targeted embedded scope a single balance block can only carry a small subset of node entries; on a chain whose registered-node count exceeds that subset, full enumeration in any single balance block is structurally infeasible. The per-node coverage of registered-node state is therefore collective rather than per-block: across any active-chain window of length `W` (the configured `snake_chain` window size resolved per FR56), every registered node has at least one seed source within the window — either a balance entry in some balance block, or its registration transaction in some transaction block. The two sources are equivalent seeds for the per-node derived state of FR34: a balance entry seeds (balance, accumulated vote, public key) directly from its content, and a registration seeds (balance = 0, accumulated vote = 0, public key = `new_public_key`) since `registration_price` is absorbed by the network per FR6 and no balance is credited to the newly registered node. The trigger discipline of this FR is what realizes the collective coverage invariant in operation: by emitting a fresh balance entry whenever any node's latest seed source would otherwise fall out of the window, every active chain produced by a correct implementation continuously satisfies the per-node W-coverage, and the FR3 forward traversal can rely on at least one seed source for every registered node within any candidate segment of length `≥W`. The `max_node_id: u32` field carried in every balance block's payload is the global node-id watermark at that balance block's sequence (not a per-block subset count); the FR3 forward traversal initializes the `max_known_node_id` projection of FR34 from the earliest balance block in the candidate segment, increments it by exactly one on every subsequent registration encountered during forward traversal, and treats any later balance block whose `max_node_id` field disagrees with the forward-traversal-tracked watermark at that block's sequence as exact evidence of invalidity per FR5 / FR6's `snake_chain` preservation invariants. Node #0 is covered by the same general FR50 logic as any other registered node — it carries no special-case treatment for seed-source preservation, and the W-coverage invariant above guarantees that whenever node #0's previous seed source (including block #0 itself) is about to leave the window, the tail-imminent trigger naturally includes a NodeInfo entry for node #0 in the next emitted balance block, just as for any other affected node. The FR69 `node_zero_public_key` trust anchor independently governs signature verification for chain-config content per FR7; balance blocks carrying a NodeInfo entry for node #0 cross-check the entry's `public_key` against that trust anchor at FR9 Tier 1, and any mismatch is exact evidence of invalidity per FR16 / FR69.
- FR51: When a transaction block containing UTXO outputs is about to fall out of the active-chain window, the blockchain module shall identify the still-unspent outputs by reading the block's spent-bit vector (per ADR-016 and Algorithm 12): every output whose bit is 0 is an unspent UTXO that must be carried forward. The module shall schedule the creation of a zero-input complex transaction at the head whose outputs correspond **exactly and exhaustively** to these unspent UTXOs of the single dropping tail block (one carry-forward transaction per dropping tail block, no coalescing across multiple tail blocks). Each carried-forward UTXO's amount shall be reduced by the configured custodian fee; any UTXO whose amount would fall below the custodian fee shall be discarded rather than carried forward. Repeated carry-forward is therefore self-clearing: every preservation step strictly reduces each surviving carried-forward UTXO by the custodian fee, so retained carry-forward-only residue eventually disappears instead of accumulating forever. After the carry-forward transaction is included in a head block, the dropping block's spent-bit vector is released along with the block itself. Acceptance-time validation invariant — protection against "money creation from nothing": a zero-input UTXO carry-forward transaction is acceptable on the active chain **only when** the carrying head block's acceptance simultaneously drops a specific identifiable tail block from the active-chain window **and** every output of the carry-forward transaction can be validated against an actually-unspent UTXO of that single dropping tail block. Specifically, on the acceptance of a head block containing a zero-input UTXO carry-forward transaction, the module shall verify that: (i) the head block's acceptance advances the tail by exactly one block; (ii) the dropping tail block is itself a transaction block (`payload_type=1`) carrying UTXO outputs; (iii) the multiset of `(recipient_node_id, amount + custodian_fee)` pairs encoded in the carry-forward transaction's outputs is byte-identical to the multiset of `(recipient_node_id, amount)` pairs of the unspent UTXO outputs of that dropping tail block (as derived from its `utxo_unspent_bitfield` in the FR34 block-navigation-and-UTXO cache); (iv) any unspent UTXO of the dropping tail block whose amount falls below the custodian fee is omitted from the carry-forward transaction's output set (the discard-below-fee rule applied symmetrically by sender and validator); and (v) the carry-forward transaction's output set contains no additional outputs beyond those derived from the dropping tail block's unspent UTXOs. A carry-forward transaction whose outputs fail any of (i)–(v) is exact evidence of invalidity per FR5 and is rejected at block intake — this is the structural defense against synthesizing UTXO outputs not backed by an actual dropping unspent UTXO (i.e., "creating money from nothing"). Content composition of the head block: a block containing a carry-forward transaction may additionally be filled with ordinary mempool transactions up to `MAX_BLOCK_SIZE` per the content-assembly priority rule of FR45, but the block **shall not contain any registration transaction** (`type=2`) — this matches the FR6 / FR9 Tier 1 registration / complex-transaction mutual-exclusivity invariant: a carry-forward transaction is itself a complex transaction (`type=3`), and a single transaction block cannot mix `type=2` and `type=3` content. Vote-credit exception: zero-input UTXO carry-forward transactions are vote-neutral — their `vote` field does not contribute any `vote_scale` credit to per-node accumulated vote under FR37 step (2), regardless of the field's value. This prevents the same originating vote intent from being counted multiple times as the same UTXO output is repeatedly carried forward across the snake_chain window. See FR37's vote-accumulation step for the precise rule.
- FR52: The blockchain module shall not perform any explicit UTXO-saturation detection, status reporting, structured log emission, mempool admission backpressure, or replay-deferral mechanism. Under sustained high UTXO load — i.e. when the active-window's unspent UTXOs combine with `snake_chain` replay obligations to consume most or all of `MAX_BLOCK_SIZE` over many consecutive head blocks — the chain simply continues ordinary block creation per FR45 against whatever pending replay obligations exist; FR51's self-clearing custodian-fee mechanism eventually restores ordinary block-content capacity over many tail-advance cycles without any FR52-specific action. No FR-level distinction between "saturated" and "non-saturated" head blocks is made, no caller observes any saturation-specific outcome, and no admission rule of FR14 is altered by the saturation condition. Saturation does not constitute long-disconnect (FR60), does not deviate from FR63 replay determinism, and does not change FR21 / FR22 / FR45 / FR51 / FR57 mechanics.
- FR53: The `sequence: u32` field is a monotonically increasing unsigned 32-bit integer starting at `0` for the genesis block; every forward extension on the active chain increments `sequence` by exactly `+1`. **In MVP, the blockchain module shall explicitly refuse to create or accept any block with `sequence == u32::MAX`**: the highest sequence value that may legitimately appear on the active chain in MVP is `u32::MAX − 1`. Concretely: (i) block creation per FR45 shall not produce a block whose `sequence` would equal or exceed `u32::MAX` — once the active-chain head reaches `sequence == u32::MAX − 1`, the local node's head-advance is structurally suspended at that ceiling, with no replay obligation or ordinary mempool content forcing it past; and (ii) every inbound block whose declared `sequence == u32::MAX` is exact evidence of invalidity per FR16 and is rejected at intake regardless of its `previous_hash` linkage. This is a **deliberate MVP scope decision**: any realistic use case for the targeted embedded LoRa deployment is expected to remain far below `2^32 ≈ 4.29 billion blocks` over the project's intended lifetime, so the MVP does not implement sequence wrap-around. Reserving `u32::MAX` as an always-rejected sentinel value avoids any boundary-condition ambiguity at the ceiling — there is no legitimate `u32::MAX` block to which a wrap-around continuation could ever attempt to link. **Sequence wrap-around handling is a post-MVP feature** per the Project Scoping section: a future revision would introduce modular sequence-space semantics, a wrap-block / genesis discrimination rule, and ancestry-based comparison rules to support indefinite chain growth across the `u32` boundary. Within the MVP sequence space the chain never wraps, so every other FR's sequence comparison (FR2 stopping conditions, FR14 `anchor_sequence ≥ S_tail`, FR48 head-advance / tail-drop, FR59 out-of-window detection, FR9 Tier 1's `block.sequence > tx.anchor_sequence`, FR21 admissibility) is interpreted with simple unsigned-integer ordering of `u32` values; the more general ancestry-based interpretation only becomes necessary if the chain were ever to wrap, which the MVP prevents. Determinism — replay determinism per FR63 is preserved within the MVP sequence space: identical input event sequences against identical initial state produce identical sequence assignments up to the `u32::MAX − 1` ceiling, and identical rejection of any block at or beyond `u32::MAX`.

### Genesis & Bootstrap
- FR54: The `initiateGenesis(initial_total_network_currency, chain_config)` command is a local-interface bootstrap operation. **Caller-side precondition**: the command shall be accepted only when the local node's `local_node_id == 0` (per FR67). When invoked on any node where `local_node_id != 0`, the module shall return a deterministic error outcome to the caller and shall not attempt any block creation. On a valid invocation, the blockchain module shall create block #0 as a transaction block authored by node #0 containing a registration transaction for node #0 and a self-transfer carrying exactly the `initial_total_network_currency` value supplied as that command's parameter, and block #1 as the chain-configuration block authored by node #0 whose configuration content matches the `chain_config` parameter supplied to the same command. The bootstrap-only validation exceptions defined in this FR apply exclusively to the original genesis blocks identified by their fixed content (block #0: node #0 registration with `new_public_key == node_zero_public_key` per FR69 plus node #0 self-transfer carrying the chain's `initial_total_network_currency`; block #1: the chain-config block whose content matches the durable-locked configuration). **The bootstrap exceptions are scoped by a conjunction of sequence number AND content match** — they apply only when (i) the block has `sequence == 0` AND its content matches the FR54-fixed genesis-block-#0 description (a node #0 registration transaction with `new_public_key == node_zero_public_key` per FR69 plus a node #0 self-transfer carrying the chain's `initial_total_network_currency`, with `previous_hash` equal to the all-zeros sentinel), or (ii) the block has `sequence == 1` AND its content is a chain-config block whose content matches the durable-locked configuration with the FR7 content-signature verifying against `node_zero_public_key`. Any block at `sequence == 0` or `sequence == 1` whose content does not match the corresponding FR54-fixed description does NOT receive bootstrap relaxations and is validated under standard FR9 Tier 1/2/3 rules (and is rejected as Invalid-evidence per FR16 whenever those rules cannot pass). From `sequence == 2` onward every block on the active chain is validated under standard FR9 rules regardless. This conjunction-based scoping is forward-compatible with the post-MVP sequence wrap-around handling per FR53 / Project Scoping: a sequence-0 wrap-block produced after `u32::MAX` (hypothetically, only post-MVP) would fail the content-match arm and thus would not erroneously inherit genesis-bootstrap exceptions, without any further modification to this rule. Both genesis blocks shall be signed with the registering key. The initial total network currency of the chain is therefore defined by the genesis content of block #0, not by the chain-configuration content of block #1 and not by the `configuration_module`. **Genesis lifecycle**: on a valid `initiateGenesis(...)` invocation, the blockchain module creates blocks #0 and #1, durable-locks the chain configuration (sourced from the `chain_config` parameter) via the storage layer's set-once chain-configuration operation, and **immediately enters ready state** with these two blocks as the starting active chain. There is no FR2 collecting-state stopping-condition evaluation and no FR3 forward-traversal processing-state step in this path — the genesis node enters ready by construction because its starting active chain is the deterministic 2-block segment that it just built (the FR2/FR3/FR4 collecting → processing → ready lifecycle is what other nodes follow when they join the network later and receive blocks #0/#1 through FR10 intake). When constructing block #1, the blockchain module shall additionally produce the chain-config content-signature required by FR7 using the same registering key that signs the outer block. Bootstrap-only validation exceptions (apply uniformly to blocks #0 and #1 at sequences 0 and 1, regardless of whether they were created locally via `initiateGenesis(...)` or received through the FR9 / FR10 intake surface from the network during collecting): (a) signature verification uses node #0's public key directly — `node_zero_public_key` from the FR69 trust anchor is the canonical reference for verifying both block #0's and block #1's block-creator signatures and for verifying block #1's FR7 chain-config content-signature; the registration transaction inside block #0 carries `new_public_key` for node #0, and that field shall equal `node_zero_public_key` per FR69 (a divergence makes block #0 Invalid-evidence and rejected at FR9 Tier 1); (b) **block #0's `previous_hash` field shall equal the all-zeros sentinel (`0x00…00`)** — this is a mandatory structural invariant of block #0; the FR6 `previous_hash` linkage rule that requires the parent block to be locally stored does not apply (no preceding block exists), but the all-zeros sentinel itself is enforced; any block #0 candidate whose `previous_hash` is not all-zeros is Invalid-evidence per FR16; (c) the `block.sequence > anchor_sequence` rule of FR9 Tier 1 / FR6 does not apply to the genesis self-transfer in block #0 (the self-transfer's `anchor_sequence` may equal block #0's sequence of 0); (d) balance checks for the genesis self-transfer and the node #0 registration are bypassed (node #0 has no pre-existing balance to debit, and the `initial_total_network_currency` is created at genesis rather than transferred from another node); (e) fee calculations do not apply to either genesis block — no `mined_amount` credit and no transaction-fee credit are computed per FR36, consistent with the FR36 genesis exception; (f) the registration transaction for node #0 is exempt from the `initializer is an existing node` rule of FR6 (node #0 bootstraps itself); (g) the **chain-config-derived `MAX_BLOCK_SIZE`** and other chain-config-derived gating checks of FR9 Tier 1 / Tier 2 do not apply to blocks #0 and #1 prior to the durable lock — the chain-configuration is locked atomically with the acceptance of block #1, after which standard chain-config-derived rules apply from block #2 onward. However, **any compile-time / structural hard limit on block size** (e.g. the implementation-level absolute byte cap baked into the storage layer or cryptographic backend) **shall continue to apply** to both genesis blocks; the bypass covers only the chain-configurable value, not the structural hard limit. (h) `max_known_node_id` watermark initialization at genesis: the genesis path shall initialize the FR34 `max_known_node_id` watermark to 0 directly (no balance block exists in the genesis segment to seed it from per FR3's normal initialization rule), and the block #0 registration's `new_node_id == max_known_node_id + 1` rule of FR6 / FR9 Tier 3 is replaced by the explicit invariant `new_node_id == 0` for that single registration; the watermark is not incremented by block #0's registration (the post-genesis watermark equals 0, matching the highest-known-node-id semantics of FR50's `max_node_id` field). From block #2 onward (the first block that may contain a non-genesis registration), the standard FR6 / FR9 Tier 3 rule resumes: every accepted registration increments the watermark by exactly one, so the first post-genesis registration carries `new_node_id == 1`. (i) the genesis `vote: u32` field of every transaction in block #0 (the node #0 registration and the node #0 self-transfer) shall equal node #0's identifier (`vote == 0`) and shall not be treated as a no-self-vote violation or as a vote-target-not-on-active-chain violation under FR6 / FR9 / FR14 / FR37. The FR37 vote-accumulation rule still applies in the ordinary way on block #0's acceptance: node #0 receives the vote credits from those transactions, and node #0's accumulated-vote reset under FR37 step (3) (creator reset on block acceptance) zeros that accumulator at the same step, leaving node #0's post-genesis accumulated vote at 0. From block #2 onward the standard no-self-vote and vote-target validity rules resume, but two permanent exceptions defined in FR37 (vote-target validity rule) and FR6 (no-self-vote rule) remain in force chain-wide: `vote == 0` is always a valid vote target, and `initializer == 0` with `vote == 0` (node #0 self-vote) never violates the no-self-vote rule. These exceptions are no longer "bootstrap-only"; they are structural constants of the MoonBlokz chain semantics and exist precisely so that node #0 can issue valid registration transactions while it is still the only existing node. The exceptions list above is exhaustive: every other invariant of FR6 / FR9 (structural parseability, payload-schema match, `new_key_signature` validity for the node #0 registration, `new_node_id == 0`, `new_public_key` global uniqueness, FR7 chain-config content-signature validity for block #1) shall be enforced on blocks #0 and #1 regardless of origin.

### External Input Contracts
- FR55: The blockchain module shall expose a dedicated local transaction-creation surface, distinct from the generic transaction-submission surface of FR14 / FR10. Input contract — for each supported transaction type (`type=1` node transfer, `type=2` registration, `type=3` complex transaction), the caller supplies the complete transaction structure for that type, already fully assembled and already carrying the caller-produced signature bytes. **The transaction structure is the `moonblokz-chain-types` crate-defined transaction struct, the same struct used by the radio-layer transaction-submission surface (FR14 / FR10)** — there is no separate local-interface transaction format; the two surfaces accept byte-identical transaction structures. The blockchain module does not construct the transaction object, does not fill in any field, does not mutate any transaction field (including `vote`), and does not produce the signature on the caller's behalf. Vote-target rule: the caller is responsible for resolving the desired vote-target value (typically by consulting the external `scoring_module`) and committing it into the transaction's `vote` field before invoking this surface. The blockchain module **does not modify the `vote` field and does not consult the `scoring_module`** — however, the supplied `vote` value is subjected to the **same vote-target validation rules as ordinary FR14 / FR10 intake** (vote-target validity per FR37 — must reference a node currently on the active chain or fall under the permanent node #0 exception; no-self-vote per FR6; any other vote-related invariants); a vote that fails these checks produces the same Deferred or Rejected outcome as on the radio path. The signature scope therefore always covers the actually-included `vote` value. The blockchain module exposes no sentinel marker, no synchronous `scoring_module` invocation, and no two-phase assemble-then-sign workflow on this surface — every such resolution is performed entirely outside the blockchain module before the signed transaction reaches it. Caller-side post-acceptance protocol with the `scoring_module`: by external convention the caller obtains the vote value from the `scoring_module` <em>without</em> the `scoring_module` deducting that value from its internal score state at query time; only after this FR55 surface returns a non-`Rejected` outcome (Created or Held) does the caller commit the vote value back to the `scoring_module`, signalling that the vote was actually consumed by a transaction and that the score may now be deducted. This protocol is external to the blockchain module's contract — the blockchain module neither implements nor enforces it — but it is the rationale for the caller-driven, modify-nothing posture defined above. Validation contract — the supplied transaction shall be evaluated against the same readiness, structural, and semantic rules that govern ordinary transaction intake under FR14 / FR10, with the same active-chain-dependent checks for vote-target validity, no-self-vote, uniqueness, anchor-window bounds, UTXO-window bounds, and signature validity. Outcome contract — the surface returns exactly one of three top-level outcomes: Created, Held(reason), or Rejected(reason). Created means the transaction is accepted locally and inserted into the mempool as part of the same call in the evaluable Accepted-to-mempool sub-state per FR14; no separate submit step is required and the transaction is immediately eligible for inclusion in the next block creation per FR45. Held(reason) means the transaction has been inserted into the mempool but is not yet in the evaluable Accepted-to-mempool sub-state because some context required for full classification is still missing; the transaction is held with the FR14 Deferred internal not-yet-evaluable marker, will be re-evaluated automatically per FR15 when the missing context arrives, and may be promoted to ordinary mempool status (visible to FR40 as `In-mempool` throughout, without sub-state distinction) without further caller action. The sole Held reason in this PRD is `deferred`, corresponding to FR14's Deferred classification. Held is therefore the explicit FR55-surface signal that the transaction is in the mempool but not yet evaluable — distinct from Created (in mempool, evaluable) and from Rejected (not in mempool at all). Rejected(reason) covers every result that did not insert the transaction into the mempool. At minimum the rejection reasons shall distinguish: (a) `not-ready`, when the module is not in ready state; and (b) `validation-failed(kind)`, where `kind` is a deterministic classification of why the transaction was not inserted into the mempool. The `validation-failed(kind)` space shall cover the same semantic categories that ordinary intake would otherwise expose through FR14 / FR10 as non-mempool-insertion outcomes — including duplicate / already-confirmed cases and ordinary invalidity causes — but this surface shall expose them only as typed rejection reasons under the single Rejected top-level outcome. The FR14 Deferred case is intentionally not part of `validation-failed(kind)` because it does insert the transaction into the mempool; it is reported under the Held(deferred) top-level outcome instead, preserving consistency with FR40's `In-mempool` representation of the same physical state. The `scoring_module` (external, radio-message-sender-based scoring used upstream when the caller chooses the `vote` field of a locally created transaction) remains distinct from the blockchain module's internal vote module (see FR34–FR38), which owns per-node accumulated vote tracking — including anti-capture interest growth, creator reset on block creation, and grace-period reset — and determines the next expected block creator from that accumulated state.
- FR56: The blockchain module shall not own the parsing, interpretation, or runtime computation of chain-configurable parameters. All such parameters shall be obtained from an external `configuration_module`. **Resolution model.** The `configuration_module` exposes a **dedicated accessor function per parameter**. Every accessor returns the value of its parameter when invoked, and may accept input arguments (for example, current active-chain length, current registered-node count, current active node count, per-node balance or vote snapshots, or any other parameter-specific input); when an accessor takes arguments, the returned value is a function of those arguments. Internally this function-call interface is realized by a **mini virtual machine in the `configuration_module`**, which evaluates either a literal constant or a small program (bytecode) for each parameter — both forms are uniformly exposed as a function call to the blockchain module, which never needs to know which form is in use for any given parameter. (The mini-VM design is forward-compatible with a post-MVP smart-contract capability built on the same VM.) **Default values and config-block content.** A chain-configuration block carries a **collection of key-value pairs**; not every parameter must be present. For any parameter omitted from the chain-configuration block, a **code-baked default value** is used by the `configuration_module` (the default may itself be VM bytecode with the same input-argument semantics as a chain-config-supplied override). The accessor function hides this distinction from the caller: a parameter's accessor returns a value regardless of whether the chain-config block specified an override or the code-baked default was used. **Not-yet-available state.** Until a valid chain-configuration is loaded — either tentatively per FR8 during collecting state or durably per FR54 at genesis — **every accessor returns a documented `not-yet-available` outcome**. The blockchain module shall treat `not-yet-available` as a signal that the corresponding staged validation step (per FR9) cannot yet be performed and shall not advance the affected block beyond the latest stage that does not require the unavailable parameter. **Caching.** The blockchain module shall call these accessors at the moment a parameter value is needed and shall not cache returned values beyond the scope of the invocation that requested them, except where explicitly permitted by the parameter's documented stability guarantees. **Not chain-config (excluded from this FR).** The following are not chain-configurable parameters and shall not be exposed by the `configuration_module`: (i) initial total network currency — fixed by block #0 at genesis from the `initial_total_network_currency` argument of FR54's `initiateGenesis(...)` command, shall not appear in chain-config content; (ii) node #0's public key — supplied as the `node_zero_public_key` code-level initialization parameter per FR69, the trust-anchor rule of FR69 supersedes any chain-derived node-#0 public-key resolution path. **The following parameters are compile-time / node-level** (determined by the local node's memory and durable storage capacity, not by chain configuration), and therefore are not exposed by the `configuration_module` and are documented in their owning FRs rather than in this FR: mempool capacity (with the implementation-time constraint `mempool capacity ≥ MAX_BLOCK_SIZE` so that any single accepted-to-mempool transaction always fits — this guarantees FR33's Case 2 Stage 2 termination); block-tree capacity (equal to storage capacity); storage capacity (the durable block-storage slot count); verification horizon size `H` (per FR58; implementation-defined per node from available durable storage and the configured `W`, with default `⌊W / 10⌋` and the constraint `0 ≤ H ≤ W`). **Chain-configurable parameter list (minimum).** At minimum, the `configuration_module` shall provide accessors for: `MAX_BLOCK_SIZE` (no input); transactional block-fill threshold percentage of `MAX_BLOCK_SIZE` (no input); active-chain length `W` — the `snake_chain` window size (no input); grace-period window duration (no input); inter-block creation interval (no input); missing-parent re-query interval — the global scheduler-tick interval driving FR46's missing-parent re-query behavior (no input); `parent_recovery_per_head_retry_interval` (no input; the minimum wall-clock period between two consecutive parent-recovery requests emitted for the same Stored head, per FR19 / FR46); `parent_recovery_min_emit_interval` (no input; the module-scope global minimum wall-clock period between any two successive parent-recovery requests, per FR46); mempool replenishment interval (no input); custodian fee (no input — an ordinary input-less chain-config-derived value used at FR51 carry-forward); **registration price** (input: the current registered-node count — the registration price may grow with network size, computed from this input by the configured VM bytecode or constant default); per-byte transaction fee policy (no input; min/max bounds); `vote_scale` (no input; the numeric value of one received vote credit, the denominator of the anti-capture rule, and the maximum per-block anti-capture interest bump); `vote_interest` (no input; the anti-capture growth numerator used with `vote_scale`); approval majority threshold (no input; subject to the structural invariant `required_support ≥ 1`, to keep the deterministic subgroup-selection formula `m = min(2 · required_support − 1, |A|)` of FR12 / ADR-015 well-defined — `required_support == 0` would yield `m = -1`, an undefined subgroup size; a chain-config whose approval majority threshold is below 1 is rejected per FR8's chain-config block acceptance); deviation-replay insertion delay (no input; the inter-replay pacing parameter per FR29 that bounds how soon the proposer may emit consecutive `snake_chain` essential-state replay blocks on the deviation-bearing branch above the deviation block — applied before the first replay block as well as between subsequent replay blocks — to avoid flooding the radio layer when several replay obligations come due in close succession); `replay_block_reward` (no input; the chain-configurable creator credit applied when a block contains at least one essential-state replay obligation per FR49 / FR50 / FR51 — i.e., a chain-config replay block, a balance block emitted as `snake_chain` replay, or a transaction block carrying a zero-input UTXO carry-forward complex transaction; this is in addition to the ordinary `mined_amount` and is intended to compensate the creator for the maintenance work of carrying replay content); `max_block_UTXO_output` (no input; the chain-config-derived upper bound on the cumulative UTXO-output count of a single block, used as the basis for block validation per FR34's block-navigation-and-UTXO cache; subject to the structural invariant `max_block_UTXO_output ≤ UTXO_UNSPENT_BITS`, where `UTXO_UNSPENT_BITS` is the compile-time bit count of the cache's per-block `utxo_unspent_bitfield` byte array — a chain-config whose `max_block_UTXO_output` exceeds this compile-time bit count is rejected per FR8's chain-config block acceptance because the local node could not represent the unspent status of that many outputs; chain-config values smaller than the compile-time bit count are permitted). The `anchor_sequence` acceptance-window for mempool intake (FR14) is not a separate configurable parameter: its lower bound is the active-chain tail sequence `S_tail` (the oldest block currently on the active chain; when the chain is shorter than `W`, `S_tail` is the chain start at sequence `0` rather than a negative extrapolation of `active_chain_head_sequence − W`), as required for duplicate-check correctness — any tighter bound would needlessly reject valid transactions, and any looser bound would break replay protection because duplicates whose confirming block has dropped out of the active window become undetectable.

### Storage & Retention Policy
- FR57: When durable storage or the bounded block-tree is at its configured capacity and a newly admitted block would have no available slot, the blockchain module shall free space by evicting **a single side branch** in a deterministic priority order: the branch whose tip has the lowest cumulative branch value is evicted first. Ties are broken by lowest tip sequence, then by lowest tip creator node identifier, then by the lowest tip block hash interpreted as a big-endian unsigned integer. Eviction proceeds backward from the chosen tip toward the nearest shared ancestor that must remain because it is also part of another retained branch or the active chain. Eviction shall not remove blocks on the active chain. Each capacity-pressure event therefore triggers **exactly one branch eviction**: since every branch eviction removes at least one block (the side-branch tip itself), and the pressure was caused by exactly one incoming block needing a slot, the single eviction always resolves the immediate pressure. After each eviction event the branch-bookkeeping structures (tip list, ancestor mapping, capacity counters) shall be refreshed before the next intake event.
- FR58: The blockchain module shall retain, beyond the active `snake_chain` window of length `W`, an additional verification horizon of `H` prior active-chain blocks. `H` is an implementation-defined parameter — sized by each node from its available durable-storage capacity and the configured `W` — subject to the constraint `0 ≤ H ≤ W`. The default value when no implementation-specific tuning has been applied shall be `H = ⌊W / 10⌋`. `H = W` is a valid (and operationally generous) choice that retains an extra full chain-length of history beyond the active window, in line with the implementation-document recommendation of "roughly an extra chain-length worth of history" for nodes whose storage budget allows it. The `H` parameter is not chain-config-derived: each node may choose its own `H` independently, and the determinism guaranteed by FR63 is unaffected by per-node `H` differences (the choice of `H` only changes the local efficiency class of chain-switch reconciliation events, not the eventual active-chain selection — every node converges on the same active chain regardless of `H`). The verification horizon's purpose is to retain enough prior active-chain history to support `snake_chain`-preservation validation for chain-switch divergences within the active `snake_chain` window. For a candidate side branch with divergence point at sequence `D ∈ [S_tail, S_head]` (where `S_tail` and `S_head` are the current active-chain tail and head sequences), the divergence block's `snake_chain`-preservation invariant references the `D − W` historical block (the block that would have dropped out of the active window when the divergence block was accepted). The verification horizon retains `D − W` for divergences in the cheap zone `D ∈ [S_tail + (W − H), S_head]`. For divergences in the deep zone `D ∈ [S_tail, S_tail + (W − H) − 1]`, the `D − W` block has fallen outside the verification-horizon retention. Cheap-zone chain switch — when a candidate side branch's divergence point `D` is in the cheap zone and the candidate's branch value (computed per FR21 from header fields) exceeds the current active chain's branch value, the module shall execute the standard FR23 chain-switch reconciliation workflow with FR9 Tier 3 forward replay along the candidate from the common ancestor, in-place against the active-chain-derived projections. Deep-zone chain switch — when a candidate side branch's divergence point `D` is in the deep zone, in-place Tier 3 reconciliation is not possible (the `snake_chain`-preservation invariants cannot be validated against the missing `D − W` reference). The module shall treat the chain-switch attempt as a full-reconstruction event under the following two-part trigger discipline: (i) the candidate side branch's tip sits at least `W` blocks above the current active-chain tail — i.e., `side_branch.tip.sequence ≥ S_tail + W − 1` (simple unsigned-integer `u32` comparison per the MVP scope of FR53; no modular distance, no ancestry traversal across a wrap point); and (ii) the candidate's branch value (per FR21 header-field summation) exceeds the current active chain's branch value. Only when both conditions are simultaneously satisfied shall the deep-zone full reconstruction be initiated. Full-reconstruction path: the module transitions from ready state to processing state and executes a dedicated FR3 forward-traversal pass on the candidate side branch with the per-node seed rule and pre-seed auto-acceptance defined in FR3, exactly as in the collecting → ready initial-establishment path. On success, the candidate becomes the new active chain and the module returns to ready state. On failure (any FR3 / FR6 invariant violation triggering FR5 deletion-and-reversion within the candidate), the module falls back to the previously-active chain by executing a second dedicated FR3 forward-traversal pass on the originally-active chain (which remains intact in durable storage, since the deep-zone attempt did not modify the original active-chain blocks beyond the working-set reset of FR5). On the fallback pass's success, the originally-active chain is re-established as the active chain and the module returns to ready state. Only on the fallback pass's failure (a previously-valid chain failing reconstruction is unexpected and indicates corruption) does the module return to collecting state and re-evaluate FR2 dominant-chain acquisition stopping conditions on the remaining retained block-tree per the regular FR3 / FR5 rules. The deep-zone trigger discipline ensures that the high cost of full reconstruction is paid only when the candidate is mature enough (its tip is at least `W` blocks above `S_tail`) and presents an attestably greater branch value than the active chain. Stale side branch reclamation: a side branch is immediately eligible for deletion when its **divergence point `D` falls out of the active-chain tail** (i.e., when the active-chain tail advance moves `S_tail` past `D`, so that `D < S_tail`). At that moment the side branch can no longer reattach to the active chain — both the cheap-zone (`D ∈ [S_tail + (W − H), S_head]`) and the deep-zone (`D ∈ [S_tail, S_tail + (W − H) − 1]`) require `D ≥ S_tail`, so neither chain-switch path is reachable any more; the divergence-point's parent on the active chain is also outside the window. The module shall therefore reclaim the storage of every such tail-out-of-range side branch on each tail-advance step, without waiting for FR57 capacity pressure. In addition, side branches whose divergence has slipped below the current verification horizon but whose `D` is still within `[S_tail, S_tail + (W − H) − 1]` (i.e., in the deep zone) and which never accumulate enough length to satisfy the deep-zone trigger remain in durable storage as retained side-branch state per FR20 until either the divergence point drops out of the tail per the rule above, or FR57 capacity-pressure eviction reclaims them sooner; no chain-switch attempt is initiated against such side branches. A side branch that could in principle still grow into a valid deep-zone candidate may be evicted by FR57 capacity pressure before it reaches the trigger threshold; the module accepts this trade-off — capacity pressure takes precedence over hypothetical deep-zone candidacy, and no preservation guarantee is provided for in-progress side branches beyond the bounded block-tree budget. The verification horizon retention is bounded by the same FR57 capacity-pressure eviction policy as the rest of the retained block-tree: in extreme storage-pressure cases the verification horizon retention may be reduced (effectively lowering `H` temporarily) before any eviction of side-branch storage proceeds, consistent with the policy that the verification horizon is an efficiency aid for cheap chain-switch reconciliation rather than a correctness guarantee.

### Lifecycle & Recovery
- FR59: The durable storage shall persist only the following items: the node's own `node_id`, the node's own private key, the saved `chain_config` block (with a flag indicating whether it has reached its final/locked form per FR54), and the retained blocks of the block-tree (active-chain plus retained side branches per FR20, bounded by the FR57 capacity policy). No separate lifecycle-state marker, no derived FR34 projection, and no `snake_chain` replay buffer is persisted. On restart the module enters collecting state unconditionally and proceeds as follows: (1) it rebuilds the in-memory block-tree and the collecting-state bookkeeping — chain_heads list, ancestor mapping, branch bookkeeping per FR20 — from the retained durable blocks; (2) it evaluates the FR2 dominant-chain acquisition stopping conditions against the rebuilt block-tree; (3) when those conditions are satisfied, the module executes a full FR3 forward-traversal processing pass on the chosen active chain to derive all FR34 projections (registered-node set, balances, `seed_source_sequence`, scheduling state, etc.) from the active chain plus its `snake_chain` window, and then transitions to ready state; (4) when the FR2 stopping conditions are not yet satisfied, the module remains in collecting state and continues ordinary collecting-state intake per FR2 / FR9 until they are. A restart is therefore semantically equivalent to a fresh chain reconstruction from the retained blocks: no derived projection is ever read from durable storage, and any in-flight processing-pass state from the prior session is discarded. The mempool is not durable per FR30 and is empty on restart regardless of prior state, to be repopulated through ordinary FR14 / FR46 activity. The retained side-branch state per FR20 is preserved through restart as part of the block-tree, and remains eligible for re-evaluation under FR58's chain-switch trigger discipline after the module returns to ready state. During the restart-driven rebuild flow — from step (1) in-memory block-tree rebuild, through step (2) FR2 evaluation, through step (3) the FR3 processing pass when it runs, up to the moment the module enters either ready state (after a successful step (3)) or collecting-state idle (when step (2) determines that the FR2 stopping conditions are not yet satisfied) — the module shall not accept any requests or messages from the radio module or from the local interface; incoming intake is suspended for the duration of the rebuild flow. This suspension is implicitly enforced by the module's synchronous single-threaded execution model (no concurrent intake can occur while the rebuild flow is running), and is stated here as an explicit semantic requirement so that the radio and local-interface callers may rely on it independently of any future threading or scheduling reorganization. Ordinary intake resumes once the module reaches either ready state or collecting-state idle as defined above. Resumable partial processing is not a requirement of this module and will not become one; callers shall not assume it under any current or future MVP scope.
- FR60: Blocks received through the intake surface shall be classified as Out-of-Snake-Chain-Window per FR10 when their sequence cannot coexist with any locally retained active-chain block inside a single `snake_chain` window — specifically when `S_new ≥ S_head + W` (the incoming block is too far ahead to be bridged by any reachable ancestor chain) or `S_new < S_tail` (the incoming block is older than the local active-chain tail), where `S_head` and `S_tail` are the current local active-chain head and tail sequences and `W` is the configured `snake_chain` window size. In either case the block is not stored, not added to the block-tree, and not forwarded to any subsequent validation stage. Collecting-state applicability: this FR's silent-discard and Out-of-Snake-Chain-Window classification do not apply in collecting state, because no active chain exists and `S_head` / `S_tail` are undefined. In collecting state, every received block is admitted into staged validation per FR9 (at the Stored status) regardless of its sequence; the `long-disconnect-detected` log emission of this FR is also suppressed in collecting state. The FR10 four-outcome classification reduces to {Accepted-new, Already-known, Invalid-evidence} in collecting state; Out-of-Snake-Chain-Window is a ready-state-only outcome. In addition, the forward case (`S_new ≥ S_head + W`) constitutes diagnostic evidence that the broader network has advanced past the local window and that chain-state reconciliation is no longer possible: the module shall emit a structured `long-disconnect-detected` log record per FR64 identifying `S_new`, the incoming block hash, and the local `(S_tail, S_head)` at the moment of detection. The log record is purely diagnostic. It does not alter module state, does not trigger recovery, and does not suspend ordinary block-creation, mempool handling, or creator-role behavior — these continue unchanged against the local active chain. Because the local node continues to operate and create blocks on its own active chain, the detected long-disconnect condition transitions the local chain and the broader network into a permanent fork in the current model: the two chains evolve independently and reconciliation is no longer possible from chain state alone. Resynchronization from a long-disconnect state is out of scope for the MVP and requires external operator action.

### Module Boundary
- FR61: The blockchain module shall operate exclusively on whole serialized blocks. Fragment reassembly — combining multiple radio packets into a complete serialized block — is the responsibility of the radio layer and shall not cross into the blockchain module. The module's block-intake surface accepts only fully reassembled, byte-complete blocks; partial or mid-reassembly state shall not be visible to the module. Every block-shaped and transaction-shaped value that crosses the blockchain module's external boundary — both into and out of the module, on both the radio-layer surface and the local-interface surface — shall be represented using the canonical types defined in the `moonblokz-chain-types` crate: `Block` for blocks and `Transaction` for transactions. The radio-layer transaction-submission path (FR14 / FR10) and the local-interface transaction-submission path (FR55) accept byte-identical `moonblokz-chain-types::Transaction` values, and the block-intake / block-emission paths and the FR40-series local query surface accept or produce byte-identical `moonblokz-chain-types::Block` values; no alternative wire-only struct, alternative API-only struct, or alternative payload-shape is introduced at the module boundary. The single canonical `moonblokz-chain-types::Block` and `moonblokz-chain-types::Transaction` types are the module's external boundary contract for these data shapes.

### Simulation, Observability & Public API
- FR62: The simulator environment shall embed the same `moonblokz-blockchain` crate build that is used on the RP2040-LoRa runtime target, without a simulator-specific fork of `moonblokz-blockchain` and without conditional compilation paths inside `moonblokz-blockchain` that bypass validation, scheduling, or chain-switch reconciliation logic. The external crates that `moonblokz-blockchain` depends on (notably the storage and crypto backends, and the time driver) are customized between platforms via feature-flag selections on those external crates; the simulator and embedded builds therefore are not required to be byte-identical at the external-crate layer, and feature-flag differences between simulator and embedded builds at this layer are permitted. Such feature-flag differences shall be confined to covering platform-specific functionality and shall not introduce any substantive structural or call-interface difference at the boundary that `moonblokz-blockchain` consumes from these external crates: the trait contracts, function signatures, type shapes, and semantic behaviors exposed by those external crates to `moonblokz-blockchain` shall be identical across simulator and embedded builds. The simulator shall not be allowed to enable feature flags or select back-end implementations that relax deterministic behavior, reorder events, or weaken validation.
- FR63: The blockchain module shall accept a replay-friendly event sequence consisting of exactly the externally supplied event types of this module: block-intake events, transaction-submission events, top-mempool-items exchange events, support-message intake events, local transaction-creation events (the replayed payload is the full caller-supplied signed transaction of FR55; the vote-target value is represented solely through the transaction payload's `vote` field, since per FR55 the blockchain module never resolves the vote target itself and therefore introduces no non-deterministic external read on this surface), genesis-initiation events per FR54, and time-driver ticks per FR46. Any randomized behavior within the module (including mempool eviction per FR31/FR33) shall be driven by a seeded pseudo-random generator. The PRNG seed shall be supplied to the module at initialization time as an external construction parameter, and the module's PRNG state shall evolve deterministically from that seed for the lifetime of the module instance. In test and simulation environments the seed shall be initialized to a fixed, known value so that identical event sequences against an identical initial state and an identical seed yield byte-identical randomization outcomes (replay determinism). In real-world node deployments each node shall initialize the PRNG from a different seed source (for example, a hardware-noise source, a unique node-identity-derived value, or another per-node entropy source); this preserves the intended cross-node randomization divergence that downstream algorithms (e.g. mempool eviction tie-breaks per FR31/FR33) rely on. The seed value supplied at initialization is part of the replayable construction inputs of the module and is not part of the runtime event sequence; no other external input outside this event set and the initialization-time construction inputs shall influence module state during replay.

- FR65: The crate's public Rust API shall be `no_std`-compatible. The crate shall not depend on a heap allocator, shall not link the `alloc` crate, and shall perform no dynamic heap allocation; all memory usage shall be compile-time bounded — every internal buffer, queue, table, cache, and intermediate working-set shall have a compile-time-fixed capacity. The crate shall expose inbound events, outbound outcomes, state queries, and introspection accessors as distinct typed entry points (not a single generic process function), and shall represent all semantically meaningful distinctions through Rust enums and structs rather than stringly-typed or integer-coded values. Every external API function — including block intake, transaction submission, mempool exchange, support-message intake, local transaction creation, state queries, introspection accessors, time-driver tick, and genesis initiation — shall be synchronous (a plain, non-`async` function that returns its final outcome to the caller on the caller's thread); no external surface shall use `async fn`, futures, deferred-completion handles, or other forms of asynchronous return. Error conditions shall use `Result`-returning signatures with closed error enumerations. The crate shall never panic on the production code path: every invariant violation, every unexpected input, and every internal inconsistency shall be surfaced through the typed `Result` error path rather than through a panic, an `unwrap`, an `expect`, or any other panicking macro; only debug-only assertions under `#[cfg(debug_assertions)]` may exist, and even those shall be unreachable when the typed API contract is observed. Direct array indexing operations (e.g., `arr[i]`) are permitted on the production code path when the surrounding code guarantees the index is in bounds — i.e., when an explicit bounds check or local invariant precedes the indexing such that the operation can be reasoned about as provably non-panicking; this allowance exists for performance (avoiding the cost of `.get()` + `match` on a guaranteed-safe access). Indexing paths where bounds-safety cannot be locally proven shall use the `.get(i)` form with explicit handling of `None`. The introspection accessor surface shall be implemented behind a feature flag so that constrained embedded production builds can compile it out with zero runtime and code-size cost; the remaining public surface (inbound events, outbound outcomes, state queries per the FR40-series, time-driver tick, genesis initiation) shall remain available in every build.
- FR66: Every adjacent MoonBlokz component that needs blockchain-facing state — specifically the radio layer and the local interface — shall consume that state exclusively through the `moonblokz-blockchain` crate's public API surface. The storage layer is a service consumed by the blockchain module itself, not a consumer of blockchain-facing state from it, and is therefore not an adjacent state-consumer subject to this FR. No telemetry module exists in the MoonBlokz architecture as an adjacent state-consumer. The module shall provide, through that public API, sufficient coverage — block retrieval per FR42, transaction-state query per FR40, balance and UTXO queries per FR41, creator-role state per FR44, and the observation surface per FR64 — so that no adjacent component needs to maintain an independent projection of authoritative blockchain state. Adjacent MoonBlokz components shall not maintain external caches above the blockchain module's API (no caller-owned short-lived cache, no memoization layer, no projection mirror, no copy of any FR40-series query result); every read of blockchain-facing state shall be a fresh call through the module's public API. The authoritative state projections defined in FR34 (per-node balance, per-node accumulated vote, public-key mapping, per-block UTXO spent-bit vector, max-node-id watermark) shall therefore exist in exactly one place — inside the blockchain module — and shall be accessed only through the module's typed API on demand. Components shall not derive blockchain-facing truth from incidental sources or side channels (raw radio traffic, direct inspection of the storage layer that the blockchain module owns, mempool snooping); all such derivations shall go through the module's API.

### Initialization Parameters
- FR67: The blockchain module shall accept a code-level initialization parameter `local_node_id: u32` supplied at module construction time. This parameter is the canonical local node identifier referenced by every FR that distinguishes "the local node" from other nodes — including FR44's `local-is-current-creator` determination, FR45's block-creator field assignment and own-transaction prioritization, FR12's active-set / subgroup-membership self-check, FR13's mempool-ownership tie-break, FR27's proposer-self-check, and FR55's local transaction-creation surface. The parameter is not chain-config-derived, is not exposed by the `configuration_module`, and is not modifiable through any runtime event surface. The blockchain module performs no authority check on `local_node_id`: callers are responsible for supplying a value that corresponds to a node already registered on the network (or to node #0 when the module is operating the genesis bootstrap path of FR54); a `local_node_id` referencing a not-yet-registered node simply produces FR44 `local-is-not-current-creator` outcomes and prevents block creation until a registration transaction for that identifier is accepted onto the active chain. Replay determinism per FR63 is preserved because the same `local_node_id` across a replay reproduces identical outcomes. Misconfiguration consequence: a mistakenly supplied identifier produces blocks signed by FR68 against the wrong identity claim, which other nodes will reject under their own FR9 Tier 1 / Tier 3 signature checks; the local node's chain-following behavior remains correct, but its block-creation contributions will not be accepted by the network until reconfiguration.
- FR68: The blockchain module shall not hold or receive the node's local signing key in any form. All cryptographic signing on behalf of the local node is performed by the `moonblokz-crypto` crate, which is the sole owner of the local signing key inside the running node. For every artifact the blockchain module needs to sign — block-creator signatures over the header-plus-payload bytes per FR45 and FR54 (genesis bootstrap), support-message signatures per FR12, the chain-config content-signature per FR54 when the local node is node #0 and is creating block #1 via `initiateGenesis(...)`, and the registration `new_key_signature` per FR55 when the local interface submits a node-#0-self-issued registration during genesis — the blockchain module shall call the crypto module's `sign(...)` (single-signer artifact) or `multi_sign(...)` (aggregation-ready single-signer artifact, used where FR27 approval-evidence aggregation downstream applies) method per the `moonblokz-crypto::CryptoTrait`, passing the canonical bytes to be signed and using the returned `Signature` or `MultiSignature` artifact in the produced blockchain artifact. The blockchain module shall not access or inspect the private key bytes at any point. To verify that the configured crypto instance is paired with the correct local node identity, the blockchain module shall query the crypto module's `public_key()` accessor and compare the returned public key with the public key currently bound to `local_node_id` per FR34's per-node public-key projection on the active chain (or, during the genesis bootstrap when no active chain exists yet, with `node_zero_public_key` per FR69 if `local_node_id == 0`). When this consistency check fails, the blockchain module shall reject every FR45 / FR12 / FR54 / FR55 attempt at signature production with a deterministic error outcome rather than producing a signature against a mismatching identity. Replay determinism per FR63 is preserved because the crypto module's signing interface is deterministic against its instance state for a given input bytes. Misconfiguration consequence: a mismatched key prevents any locally-produced signed artifact from being accepted by the network and is reported through FR64 structured logs; recovery requires external operator action to install the correct key on the crypto-module side.
- FR69: The blockchain module shall accept a code-level initialization parameter `node_zero_public_key` supplied at module construction time. This parameter is the canonical, immutable trust anchor for node #0's identity for the lifetime of the module instance, with the same code-level / immutable / not-exposed characteristics as the FR67 init parameter (not chain-config-derived, not exposed by the `configuration_module`, not modifiable through any runtime event surface). Authoritative-anchor rule: any received or locally-created blockchain artifact whose content asserts a node #0 public key different from `node_zero_public_key` constitutes exact evidence of invalidity per FR16 and shall be rejected at the earliest evaluable point. The specific intake-time check sites that enforce this rule — registration transactions with `new_node_id == 0` (FR54 self-issued genesis registration), balance-block NodeInfo entries with `owner == 0` (FR50 balance blocks), and chain-config block content-signatures (FR7) — are specified at FR9 Tier 1 trust-anchor checks (i) (ii) (iii) respectively. Because `node_zero_public_key` is available from module construction onward — earlier than the FR8 chain-config tentative load and earlier than any active-chain projection — these checks are evaluable at Tier 1 intake-time without requiring connected-ancestry derivation. Misconfiguration. If the module is initialized with a `node_zero_public_key` that disagrees with the chain's actual node #0 — for example, after operator error in setting the parameter on a node joining an existing chain — every block on that chain will fail these checks and the local node will never converge. Recovery requires external operator action to re-initialize with the correct parameter.

## Non-Functional Requirements

### Performance
- NFR1: The module shall execute all steady-state intake, query, and scheduling paths with bounded memory usage and without unbounded queues or scans whose cost grows with total historical chain length.
- NFR2: Block-intake, transaction-intake, and query paths shall operate against retained state only and shall not require full-chain reconstruction during ordinary ready-state operation.
- NFR3: Mempool replenishment, parent-recovery, and block-creation scheduling shall remain lightweight enough for constrained embedded deployment and shall not require wall-clock polling loops beyond the external monotonic tick model.
- NFR4: Branch-value computation, chain-head selection, and reconciliation prechecks shall remain efficient over the retained block-tree and verification-horizon storage, with expensive full reconstruction reserved only for the explicitly defined deep-zone cases.

### Reliability
- NFR5: The module shall preserve deterministic authoritative-state reconstruction: identical retained inputs and identical replay inputs shall yield identical active-chain interpretation and identical derived projections.
- NFR6: Any failure during processing-phase validation or ready-state authoritative reconciliation shall leave no partially applied derived state visible to callers.
- NFR7: Restart during processing shall not corrupt durable blockchain truth; partial in-memory reconstruction state shall be safely discarded and recomputed.
- NFR8: The module shall tolerate partial, delayed, and conflicting network knowledge without requiring immediate global consistency, while still converging to the same defensible active-chain interpretation once sufficient information is available.

### Security and Integrity
- NFR9: All cryptographic validations used for authoritative acceptance decisions shall be performed against the canonical candidate-side or active authoritative projection defined by the PRD, not against incidental transport-time observations.
- NFR10: Durable blockchain storage shall follow the permissive intake model defined in FR16, while authoritative invalidation decisions shall require the explicitly defined later validation paths.
- NFR11: The module shall protect blockchain correctness against malformed, contradictory, replay-inconsistent, and state-invariant-violating inputs, preferring rejection/deletion-and-reversion over partial acceptance.
- NFR12: Chain-configuration integrity shall be preserved for the lifetime of the chain through durable lock semantics, content-signature validation, and mismatch rejection rules.

### Capacity and Resource Bounds
- NFR13: The blockchain module, together with the other required MoonBlokz runtime modules that must coexist on the same target, shall fit and operate on the RP2040-LoRa microcontroller within its available RAM, flash, and execution-budget constraints. This requirement applies to the combined runtime footprint, not just to the blockchain module in isolation.
- NFR14: The RP2040-LoRa deployment requirement shall be satisfied without removing correctness-critical blockchain behaviors, validation paths, replay handling, or observability mechanisms required by the MVP.
- NFR15: The module shall also be deployable on any `no_std` Rust-capable platform whose hardware capabilities are equal to or stronger than the RP2040-LoRa target, without requiring semantic changes to the module’s blockchain behavior.
- NFR16: The module shall remain operable within constrained embedded storage and memory budgets by using bounded active-chain retention, bounded verification horizon, bounded block-tree retention, and compact mempool storage.
- NFR17: Optional retained history beyond the active `snake_chain` window shall be treated as an efficiency optimization, not a correctness prerequisite.
- NFR18: Capacity pressure shall be handled through deterministic eviction and bounded retention rules rather than uncontrolled storage growth.
- NFR19: Large-network behavior shall degrade through the documented bounded mechanisms rather than through undefined failure modes.

### Integration
- NFR20: The module shall expose clear typed boundaries to adjacent components, including the radio layer, storage layer, scoring module, configuration module, mempool module, local interface, and simulator environment.
- NFR21: Integration contracts shall be stable enough that adjacent components can consume authoritative blockchain-facing truth without maintaining competing authoritative interpretations.
- NFR22: External dependencies shall remain semantically narrow: adjacent modules may provide data, timing, configuration, scoring, or storage services, but blockchain truth selection and validation semantics shall remain inside the blockchain module.
- NFR23: The simulator and replay environment shall exercise the same semantic contracts as runtime deployment, so integration behavior can be validated without a simulator-specific semantic fork.

### Observability and Testability
- NFR24: The module shall emit sufficient structured logs to reconstruct correctness-critical decisions, status transitions, reconciliation behavior, replay obligations, and deletion paths without requiring hidden internal inspection APIs.
- NFR25: The module shall support deterministic replay in test and simulation environments so that correctness failures can be reproduced from retained event sequences and construction inputs.
- NFR26: Non-deterministic production behaviors that intentionally vary across nodes shall remain explicitly bounded and test-harness-controllable.
