# MoonBlokz Glossary (Cross-Subsystem & Ambiguous Terms)

This glossary disambiguates terms that span more than one subsystem or that carry more than one meaning across the knowledge base. It is a navigation aid and is **not authoritative**: each entry links to the authoritative definition site, which wins on any divergence. Terms that are unambiguous within a single subsystem are intentionally omitted; see the [index](./moonblokz-index.md) for per-document scope.

| Term | Meaning in context | Authoritative definition site |
|---|---|---|
| **node** | An active participant in the blockchain (the consensus population); distinct from an address. | [Blockchain Concept](./moonblokz-blockchain-concept.md) — Network Entities |
| **address** | A passive endpoint for holding and transferring value, represented as UTXOs; distinct from a node (users can create many addresses). | [Blockchain Concept](./moonblokz-blockchain-concept.md) — Network Entities |
| **score — relay** | Radio metric for how much a node can improve message reach; drives the relay decision. | [Radio Algorithm](./moonblokz-radio-algorythm.md) §H4 |
| **score — vote target** | Radio-side per-node score computed from the senders of observed messages; selects the vote target embedded in a transaction before it reaches the blockchain. | [Blockchain PRD](./moonblokz-blockchain-prd.md) FR55 (`scoring_module` boundary) |
| **vote target — blockchain** | The `node_id` a transaction's `vote` field names, once embedded. It must name a node that exists on the chain — because registered node ids are contiguous, "exists" ⟺ within `[0, max_known_node_id]` — validated at FR6 candidate re-derivation and FR37 active-chain intake (permanent node-#0 exception). Distinct from `score — vote target` above, which is the radio-side selection of this value. | [Blockchain PRD](./moonblokz-blockchain-prd.md) FR6 / FR37 |
| **accumulated vote** | Blockchain vote-module per-node accumulated vote that names the next expected block creator (`interest_bump = min(floor(accumulated_vote × vote_interest / vote_scale), vote_scale)`, then checked addition). The term replaces earlier "vote score" / "accumulated vote score" usages; the bare word "score" is reserved for the radio-side senses (`score — vote target` and `score — relay`). | [Blockchain PRD](./moonblokz-blockchain-prd.md) FR37 / FR38, [Blockchain Algorithm](./moonblokz-blockchain-algorythm.md) |
| **`snake_chain`** | The bounded, forward-moving active-chain retention model: as blocks arrive at the head, old blocks drop from the tail so on-device state stays bounded. Blockchain-owned; storage persists it. Its retained span is the active-chain window below. | [Blockchain Concept](./moonblokz-blockchain-concept.md) — Consistency Under snake_chain |
| **active-chain window** (`W`) | The bounded-retention window of the active chain. Its length `W` is chain configuration and is identical on every node of a chain; the const generic `SNAKE_CHAIN_LENGTH_MAX` is only the capacity a build can hold, and acceptance requires `W ≤ SNAKE_CHAIN_LENGTH_MAX`. | [Blockchain Architecture](./moonblokz-blockchain-architecture.md) §5, [Configuration Module Specification](./moonblokz-configuration-specification.md) §4.1 |
| **verification horizon** (`H`) | The `H` blocks retained below the active-chain window so that every admissible chain switch stays verifiable in place; distinct from the active-chain window. Also the maximum switch depth (`D ≥ S_head − H + 1`). Chain configuration (`verification_horizon`), not a const generic. | [BC-FR58](./moonblokz-blockchain-prd.md), [Configuration Module Specification](./moonblokz-configuration-specification.md) §4.1, [Blockchain Architecture](./moonblokz-blockchain-architecture.md) §5 |
| **liveness credit** | FR37 step (4): `H` blocks after a block it created, a node gains `⌈vote_scale / vote_interest⌉`, the smallest accumulated vote that earns interest, so a live node left without votes climbs back (DEC-178). | [BC-FR37](./moonblokz-blockchain-prd.md) |
| **final (confirmation)** | An FR40 `Confirmed` transaction whose block is at least `H` deep and not disputed: no admissible chain switch reaches it, so it is irreversible on the reporting node. The published confirmation rule (DEC-182); node-local under a permanent fork. | [BC-FR40](./moonblokz-blockchain-prd.md) |
| **lifecycle phase** (collecting / processing / ready) | The blockchain module's operating phases. *Collecting* gathers blocks until an FR2 candidate exists; *processing* is the transient, non-resumable FR3 reconstruct-and-validate pass, never observable between calls; *ready* tracks an active chain. Node #0 enters ready directly at genesis. Not to be confused with a node or radio being "ready" in general. | [BC-PRD](./moonblokz-blockchain-prd.md) FR1–FR5, FR54; [Operating Model](./moonblokz-blockchain-operating-model.md#2-lifecycle-phases-and-transitions) |
| **block status** (Stored / Connected / Active) | A retained block's validation status: *Stored* = passed Tier 1 and kept; *Connected* = ancestry reaches the active chain and Tier 2 passed; *Active* = on the selected active chain, verified at Tier 3. *Stored* is a status, not a synonym for "persisted": every retained block is in durable storage whatever its status. | [BC-PRD](./moonblokz-blockchain-prd.md) FR9; [Operating Model](./moonblokz-blockchain-operating-model.md#41-statuses) |
| **Invalid** | A terminal classification, not a block status: the block and its transitive descendants are deleted, or never stored if the evidence arises at intake. | [BC-PRD](./moonblokz-blockchain-prd.md) FR5, FR9, FR16 |
| **Tier 1 / Tier 2 / Tier 3** | The three check sets gating block statuses: Tier 1 at intake (mostly decidable from the block's bytes, plus the durable-lock checks, the ready-state window, and the direct-head-extension rules) gates storage; Tier 2 (ancestry and lookups) gates Connected; Tier 3 (derived-state replay) gates Active. Not related to any storage or radio tiering. | [BC-PRD](./moonblokz-blockchain-prd.md) FR9; [Operating Model](./moonblokz-blockchain-operating-model.md#42-check-tiers) |
| **exact evidence** | Proof that a block or transaction is incorrect, as opposed to merely not-yet-evaluable. At intake its forms are exactly the Tier 1 failures; it is what entitles the module to refuse storage or delete. | [BC-PRD](./moonblokz-blockchain-prd.md) FR16, FR9 |
| **Deferred** | Three distinct uses. *Block* (FR10): the Tier 3 pacing soft-fail — the block stays stored, is not promoted, and the outcome carries `remaining_wait_time`. *Transaction* (FR14): not yet classifiable for missing context — held in the mempool with a marker and re-evaluated (FR15). *Local submit* (FR55): the same transaction state, reported as `Held(deferred)`. None of them is a rejection. | [BC-PRD](./moonblokz-blockchain-prd.md) FR9, FR10, FR14, FR15, FR55 |
| **head** | *Active head*: the tip of the selected active chain. *Head* in `chain_heads`: any block-tree tip, Stored, Connected or Active, each with its own entry. | [BC-PRD](./moonblokz-blockchain-prd.md) FR19, FR21 |
| **tail** | *`snake_chain` tail* (`S_tail`): the oldest block of the active-chain window, which advances as the head extends past `W`. *Tail-point* of a Stored `chain_heads` entry: the lowest-sequence block on that branch whose parent is missing, the target of parent recovery. Unrelated positions. | [BC-PRD](./moonblokz-blockchain-prd.md) FR19, FR48 |
| **switch bound** (formerly cheap zone / deep zone) | Which competing branches a ready node may switch to: divergence point `D ≥ S_head − H + 1` against its own head, always in place by the FR23 walk. DEC-159 removed the deep zone and its full FR3 pass; "cheap zone" in earlier story records means this bound. | [BC-PRD](./moonblokz-blockchain-prd.md) FR23, FR58; [Operating Model](./moonblokz-blockchain-operating-model.md#73-chain-switch) |
| **evidence block** (approval / twin) | Two block kinds share the word. *Approval evidence* (`payload_type=4`) is the deviation proposer's aggregate of `required_support` support signatures; it carries `supporter_vote_sum` and adds branch value. *Twin evidence* (`payload_type=5`) records a same-parent equivocation: the other twin's header as proof and, with a quorum, a bitmap verdict; it adds no branch value and starts the FR72 exclusion. | [BC-FR27](./moonblokz-blockchain-prd.md), [BC-FR71](./moonblokz-blockchain-prd.md) |
| **support message / twin vote** | Both are signed by members of an ADR-015-style subgroup. A *support message* endorses a deviation block for its proposer (FR12); a *twin vote* names the first-adopted of two same-parent twins (FR71), with a domain-separated seed over the state at the twins' shared parent. | [BC-FR12](./moonblokz-blockchain-prd.md), [BC-FR71](./moonblokz-blockchain-prd.md), [ADR-015](./blockchain-adrs/ADR-015-approval-subgroup-selection.md) |
| **release / lazy deletion** | Deleting a block frees its slot in memory only: storage has no delete, so the bytes remain until the slot is overwritten, and a block deleted before a restart can return in the rebuild. Applies to tail drop, eviction and invalidity deletions alike. | [Blockchain Architecture](./moonblokz-blockchain-architecture.md) §3.6; [BC-PRD](./moonblokz-blockchain-prd.md) FR48 |
| **chain configuration** | The parameter set carried by chain-config blocks and locked for the lifetime of the chain. It spans subsystems: blockchain parameters and the radio runtime-tuning parameters share one flat, permanent key registry, because every value in it must be identical on every node. Distinct from node-level configuration (private key, node id, storage geometry), which is local and never chain-derived. | [the Configuration Module Specification](./moonblokz-configuration-specification.md) §4 (repository root), [Blockchain PRD](./moonblokz-blockchain-prd.md) FR56 |
| **active configuration** | The configuration currently loaded in the configuration module, reached through an optional handle that also reports whether the commitment is tentative (FR8 collecting phase) or durable (locked for the chain's lifetime). Absent until the first valid chain-config content is loaded. | [Blockchain PRD](./moonblokz-blockchain-prd.md) FR56 / FR8 |
| **chain-info** | Quantities a configuration program may read from the active chain itself (identifier 1, the registered-node count, is allocated; per-node balance and aggregates such as average block fill are candidates), reached through a second host function behind the `GETCHAININFO` instruction. Its identifier space is separate from the chain-configuration parameter registry — a chain-info identifier is never declarable in a payload and burns no key byte — but equally permanent, because it appears inside permanent bytecode. Distinct from *chain configuration* (the declared parameter set) and from *active configuration* (the loaded handle). | [Configuration Module Specification](./moonblokz-configuration-specification.md) §4.6 |
| **`max_block_utxo_output`** / **`MAX_BLOCK_UTXO_OUTPUT`** | Same name, two things, distinguished only by case — the chain-configured *value* (a chain-configuration parameter, two bytes wide, default 255) versus the local build's *capacity* (the width of the per-block available-UTXO bitfield, 256 bits by default; the PRD and configuration specification call it `UTXO_UNSPENT_BITS` / `BuildLimits::utxo_unspent_bits`). Acceptance requires the value to fit the capacity, exactly as `W` must fit `SNAKE_CHAIN_LENGTH_MAX`; before the durable lock the capacity is also the Tier 1 cap on a block's UTXO outputs. | value: [Configuration Module Specification](./moonblokz-configuration-specification.md) §4.1; capacity: [System Constraints \& Limits Reference](./moonblokz-system-constraints.md) |
| **`block_size_limit`** / **`MAX_BLOCK_SIZE`** | Two limits on block size. `block_size_limit` is the chain's maximum block size — chain configuration (ID 3), identical on every node, and the limit every block-size rule of the PRD refers to. `MAX_BLOCK_SIZE` (2016 B) is the node's physical limit — the compile-time block buffer and storage-slot width; acceptance requires `block_size_limit ≤ MAX_BLOCK_SIZE`. | [Configuration Module Specification](./moonblokz-configuration-specification.md) §4.1 / §6 check 5; [BC-FR56](./moonblokz-blockchain-prd.md) |
| **backend — crypto** | A build-time-exclusive signature implementation family (Schnorr or BLS) behind one stable signing API; the choice trades RAM and airtime against aggregation capability. | [Crypto Concept](./moonblokz-crypto-concept.md) — Why MoonBlokz Keeps Multiple Backends |
| **backend — storage** | A build-time-exclusive persistence implementation (`backend-memory` for desktop/simulation, `backend-rp2040` for on-device flash) behind one storage contract. | [Storage Concept](./moonblokz-storage-concept.md) — Why the Two Backends Represent Two Different Conceptual Roles |
| **backend — radio device** | A build-time-selected radio transport implementation (echo, simulator, or RP2040 SX1262) behind the radio device interface. | [Radio Implementation](./moonblokz-radio-implementation.md) — Radio Device Backend Inventory |
| **message — radio** | The logical radio transmission unit that is relayed, duplicate-filtered, and CRC-checked as a whole; carried in one or more packets. Blockchain objects are wrapped into messages for transport. Distinct from a packet. | [Radio Algorithm](./moonblokz-radio-algorythm.md) §C — Current Message Model |
| **packet — radio** | The over-the-air fragment of a message; a message is split into one or more packets, each with its own header and CRC. Distinct from a message. | [Radio Algorithm](./moonblokz-radio-algorythm.md) §C3–C4 |
| **replay — blockchain** | Re-emitting essential state (chain-config, balances, UTXO carry-forward) in the head extension that would drop the block carrying it (BC-FR48), so bounded `snake_chain` retention never loses required state; a protocol mechanism, not maintenance. | [Blockchain Algorithm](./moonblokz-blockchain-algorythm.md) — Algorithms 11–12 |
| **replay — simulation & analysis** | Re-running recorded radio/message history or historical scenarios off-device for validation and analyzer timing. | [Simulator Concept](./moonblokz-simulator-concept.md) — Message-history reality; [Telemetry Algorithm](./moonblokz-telemetry-algorythm.md) §P4 |
| **nonce — crypto** | The Schnorr signing nonce, which MoonBlokz derives deterministically as a safety choice. | [Crypto Concept](./moonblokz-crypto-concept.md) — Deterministic Nonces as a Conceptual Safety Choice |
| **nonce — blockchain (none)** | MoonBlokz has no account/transaction nonce; `anchor_sequence` plus structural uniqueness replace the classical nonce role for ordering and anti-replay. | [Blockchain Concept](./moonblokz-blockchain-concept.md) — Transaction Uniqueness Without Global Time |
| **seed** | Three unrelated senses in the blockchain. *Seed source*: a node's balance entry or registration inside the window from which its derived state is rebuilt (`seed_source_sequence`, BC-FR50). *Subgroup seed*: `H(tail hash ‖ proposer ‖ proposed sequence)`, which orders the approval subgroup (ADR-015). *PRNG seed*: the per-node construction input that makes mempool eviction replayable (BC-FR63). | [Blockchain PRD](./moonblokz-blockchain-prd.md) FR50, FR63; [ADR-015](./blockchain-adrs/ADR-015-approval-subgroup-selection.md) |
